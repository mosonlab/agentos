Mechanical merge execution authenticates through a repository-scoped GitHub App and mints a fresh short-lived installation token for each run.

Background: `@agentos/merge-executor` currently reads `MERGE_INTEGRATOR_TOKEN_FILE` once during startup and carries that static GitHub token for the daemon lifetime. A dedicated outside collaborator cannot use a fine-grained PAT to contribute to the user-owned `mosonlab/agentos` repository, while GitHub App installation tokens expire and therefore cannot satisfy the static-token contract. This leaves the documented dedicated merge identity unprovisionable without weakening it to a classic PAT. The existing OS-principal isolation gate, exact-head authorization, decision table, confirmed-write/read-back defenses, and API/executor principal separation remain the authority boundaries.

Changes:
1. Replace the static GitHub token-file contract with GitHub App configuration: public App ID and installation ID plus an owner-only private-key file. Preserve the existing OS-user, peer-user, file-owner, mode, ancestor-directory, and refused-token-environment checks; remove the obsolete `MERGE_INTEGRATOR_TOKEN_FILE` path rather than supporting both credential modes.
2. Add a bounded GitHub App authentication component that creates a correctly bounded RS256 App JWT, exchanges it through the official installation-token endpoint, strictly validates the response token and expiry, and returns no secret material in logs or errors.
3. Mint a fresh installation token after each mechanical Run is claimed and immediately before constructing the GitHub merge surface. Do not cache an installation token across Runs. A key-read, signing, timeout, HTTP, response-validation, or mint failure must fail the Run before any merge write and must remain retryable only through the existing bounded Run contract.
4. Update executor configuration, startup wiring, environment documentation, security hygiene checks, harnesses, and affected tests to describe and exercise GitHub App credentials only. Keep the App private key out of process environments, command arguments, child processes, repository files, and emitted evidence.
5. Preserve the existing merge identity replay check using the configured App bot login, and preserve every exact-head/base, required-check, mergeability, authorization, disarm, confirmed-write, and read-back rule without semantic change.

Out of scope: changing API evidence-read credentials; changing readiness, authorization, merge-stop, decision-table, or pull-request target semantics; changing PR #46's feature diff; creating or installing the production GitHub App; provisioning the production OS user or LaunchDaemon; migrations; supporting PAT fallback or multiple credential modes.

Constraints: fail closed and name failures without leaking secrets; never fall back to a PAT, stale installation token, default identity, or unverified response; private-key custody remains behind the dedicated OS principal; App and installation identifiers may be environment configuration but private key bytes may not; no subprocess may receive GitHub credentials; remove obsolete static-token code and documentation in the same change.

Acceptance: focused tests prove JWT claims and signature inputs, one token mint per claimed Run, no mint before claim, no GitHub merge surface or merge write after any mint failure, bounded timeout and strict malformed/error response handling, secret redaction, private-key ownership/mode/ancestor refusal, refused token environment names, and unchanged replay identity behavior. `MERGE_INTEGRATOR_TOKEN_FILE` and static PAT token-shape authority are absent from tracked source and documentation. `npm run test -w @agentos/merge-executor`, affected API/runner/security suites, `npm run verify:secret-hygiene`, and the repository exact-head merge gate pass.
