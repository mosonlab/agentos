A salvage branch published for a LOST Run after its replacement Run already started is visible on the Task page and its board card, with a TaskActivity line recording the fact, instead of surviving only in a runner audit log line.

Background: When a Run is declared LOST, the platform enqueues a replacement Run at once, while the owning runner publishes the LOST Run's committed work to a salvage branch (`Run.pushedBranch`, set in `packages/api/src/run-lifecycle.ts`) only when it next reclaims its workspace. When reclaim loses that race, `repairReplacementAfterSalvage` (`packages/api/src/workspace-reclaim.ts`) returns `already-started` and `packages/api/src/routes/runner.ts` answers `409 Salvage is durable, but the replacement already started from its prior base`. The refusal is correct: it must not retarget a Run that is executing. But nothing records the outcome where an operator or reviewer looks: the board's run projection (`packages/api/src/board.ts`, `packages/db/src/board-contract.ts`) exposes `pullRequestUrl` and not `pushedBranch`, and the web Task page has no salvage surface. Observed twice: 2026-09-01 Run `cmtib9mj20nblmp02razlnkop` (task `cmti9iqdq0635mp02yiu02g59`, replacement `baseSha` equal to the LOST Run's base) and 2026-09-02 Run `cmtjrgvme13aympfikx1wiv1t` (task `cmtjklnnc0gnfmpfittxaxcyl`, during an API 503 busy window). The work survives on the branch; the replacement redoes it and nobody sees the branch. Moson decided on 2026-09-03 to take the minimal shape: visibility only. Holding the replacement, or retargeting it on the 409 path, is deferred and not part of this chain.

Definition used throughout: a Run is a stranded salvage when its status is `lost`, its `pushedBranch` is set, and a later Run of the same Task has `baseSha` equal to the LOST Run's `baseSha`. This is derivable from existing `Run` columns; no schema change.

Changes:
1. When `repairReplacementAfterSalvage` returns `already-started` on the salvage publication route, the API writes a TaskActivity on the Task naming the salvage branch, the LOST Run number, the replacement Run number, and the replacement's `baseSha`, stating that the branch is not consumed by the replacement. The 409 response is unchanged.
2. The board and task projections in `packages/api/src/board.ts` and their contract in `packages/db/src/board-contract.ts` carry, per Task, the list of stranded salvage branches (branch name and LOST Run number) computed by the definition above; the list is empty for every Task without one. The browser contract test that proves native projections serialize (PR #425) covers the new field.
3. The web Task page lists each stranded salvage branch by name and Run number; the board card shows a compact marker with the count when the list is non-empty and nothing when it is empty.

Out of scope: holding or delaying the replacement Run; retargeting a replacement on the `already-started` path; any change to the 409 refusal or to `repairReplacementAfterSalvage`; deleting or pruning salvage branches; the archived card `cmti5743j14dvmp49mzgjnabk` (a replacement that did inherit the salvaged base and dead-ended as `NO_CHANGES_PRODUCED`); a Prisma migration.

Constraints: no new database column; the projection derives the list from `Run` rows already loaded for the Task. The existing runner-facing 409 test keeps passing unchanged. `*.dbtest.ts` coverage is merge gate evidence and is not run inside a Run.

Acceptance:
- `packages/api` unit test on the salvage publication route: an `already-started` repair writes exactly one TaskActivity naming the branch, both Run numbers, and the replacement `baseSha`, and still answers 409 with the existing message; a `repaired` or `requeued` repair writes none.
- `packages/api` dbtest: a Task with a LOST Run carrying `pushedBranch` and a later Run whose `baseSha` equals that Run's base projects one stranded salvage entry; a Task whose later Run has a different `baseSha` projects none; a Task with no LOST Run projects an empty list.
- The projection serialization test in `packages/db` covers the new field.
- `apps/web` test: the Task page renders the branch name and Run number for a Task with one stranded salvage entry and renders no salvage section for an empty list; the board card renders the marker only when the count is non-zero.
- `npm run test -w packages/api`, `-w packages/db`, `-w apps/web` are green; `lint` and `typecheck` for those workspaces are green.
