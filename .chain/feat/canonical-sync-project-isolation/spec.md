Canonical prompt sync treats each project as its own unit of work: a structural drift in one project refuses only that project and is reported in the deploy notice, and the rule that a canonical-named Agent or template is canonical-managed is stated where operators create them.

Route: implementation=senior-dev - transaction-boundary semantics that run unattended inside every auto-deploy, where a wrong boundary either blocks the whole fleet's deploy or silently rewrites another project's prompts; the dbtest suite can witness the commit boundaries but not the deploy-time interaction.

Background: This brief is based on `origin/main` at `d2314b91b02937b88b9af22279cfae122a3efe61`. Since PR #370 (A2), `packages/db/prisma/sync-canonical-prompts.ts` repairs every project. `synchronizeAgents` selects all Agents whose `name` is a canonical role name with no project filter (`:444-459`), throws on any structural difference in any project (`:486-491`), and rewrites `foundationalPrompt` and `rolePrompt` keyed by Agent id (`:569-580`); `runtimeConfigCustomized` protects only model and runner preference. `syncCanonicalTemplates` selects templates by name across projects the same way (`:593-597`). The whole run is one `prisma.$transaction` (`:875-954`), so one project's refusal rolls back every project, and `scripts/deploy/quiet-window-deploy.mjs:799-806` runs the sync without arguments on every deploy and fails the deploy on a non-zero exit (`canonical-prompt-sync-refused`). Today word-factory's four canonical-named Agents match the canonical text exactly, so the sync is a no-op there; the exposure is the next deploy after any project drifts (card cmtjd7hs405e9mp602oenb0zz, Sol verification 2026-09-02).

The decision for this chain is deliberately narrow: a canonical name means canonical-managed. A project that wants its own prompt gives the Agent or template a non-canonical name. No opt-in flag, no digest registry, no schema change.

Changes:
1. Split the sync into one transaction per project: the canonical source project (`agentos-example`) first, then every other project in slug order, each in its own `prisma.$transaction`. Within a project the existing all-or-nothing semantics stay. `--install-full <projectId>` runs inside that project's transaction.
2. A refusal in the canonical source project keeps today's behaviour: the process exits non-zero and nothing else is attempted. A refusal in any other project is recorded and the sync continues to the next project; at the end the process prints one line per refused project in the form `REFUSED <slug>: <reason>` and one line per synced project with its counters, then exits 0 when the canonical project succeeded. The refused project's rows are left exactly as they were.
3. `scripts/deploy/quiet-window-deploy.mjs` captures the sync's stdout and, when it contains `REFUSED` lines, includes them verbatim in the deploy's Inbox notice (the same notice that today reports `success: <from> -> <to>`), so a foreign-project refusal is visible without reading deploy logs. A canonical-project refusal keeps failing the deploy as now.
4. State the rule in `agents/README.md` and `docs/install.md` next to where canonical Agents and templates are described: an Agent or task template whose name is a canonical name is rewritten to the canonical text on every deploy; a project that needs a different prompt uses a different name. Keep `scripts/release-docs.test.mjs` green with an assertion for that sentence.
5. Extend `packages/db/src/canonical-prompt-sync-multi-project.dbtest.ts`: a drift in a non-canonical project leaves that project untouched, still syncs the canonical project and a third healthy project in the same run, and prints the `REFUSED` line; a drift in the canonical project still exits non-zero with nothing written. Extend `scripts/deploy/quiet-window-deploy.test.mjs` with a sync stdout containing a `REFUSED` line reaching the Inbox notice text.

Out of scope: `packages/db/src/canonical-template-transition.ts` and the legacy-template rollover mechanism, `runtimeConfigCustomized` semantics, the verifier's partial mode, migrations, the runner, the API, `scripts/merge-gate.sh`, `scripts/run-scope-guard.sh`, `scripts/host-proof-slot.sh`, `package.json`, `CONTRIBUTING.md`, and `packages/runner/**`; other chains own those concurrently. Do not add a per-Agent or per-project flag, and do not compare prompts against historical digests.

Constraints: Fail loudly inside a project: a structural difference, an invalid runtime configuration or a database error refuses the whole project. Never write a partial project. The order of projects is deterministic (canonical first, then slug order). Exit codes: non-zero only when the canonical project refused or the process itself failed.
