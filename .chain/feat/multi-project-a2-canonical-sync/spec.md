Canonical prompt synchronization covers every Project, with an operator opt-in that completes any Project's canonical Agent and template inventory and a verifier that can validate that Project independently.

Route: implementation=senior-dev - cross-Project canonical migrations must preserve partial inventories and existing transition semantics across one all-or-none transaction boundary that the acceptance suite cannot fully witness.

Background: At `origin/main` commit `15130554d19d438679423eba6435cdabafd75619`, both `packages/db/prisma/seed.ts` and the production command `packages/db/prisma/sync-canonical-prompts.ts` load `agents/` sources and write canonical Agent fields. The sync command loads all three canonical template sources, plans over every same-name TaskTemplate row, and applies prompt and recognized structural transitions across Projects, but its Agent query, role-completeness check, prompt/runtime synchronization, and the migrations that create `regression-verifier` and `spec-revalidator` are scoped to the Project whose slug is `agentos-example`. It runs one Prisma interactive transaction with `timeout: 120_000` and no explicit isolation level, then prints a flat JSON counter summary; `packages/db/prisma/verify-agent-template.ts` likewise selects only `agentos-example`, requires its complete canonical inventory, and runs unconditional compound/direct special checks. `packages/db/src/canonical-template-installation.ts` already owns canonical template creation, binds steps to active in-Project Agents, and declares `variables: ["branchName"]`; `packages/db/prisma/seed.ts` owns the source-to-Agent field mapping and source-declared collaboration edges. This chain starts only after A1 has delivered the third canonical template `pr-engineer-workflow`, Project bootstrap with one `local` Environment plus its four specified Agents and that template, and the `@anneal/db` exports of `planCanonicalInstallation` and `applyCanonicalInstallation`. A2 depends on those A1 contracts and on no additional A1 behavior.

Changes:
1. Ordinary canonical Agent synchronization covers every Project. For each active Agent whose name is present in `loadAgentSources`, it enforces the current canonical rules: `title`, `inboxAccess`, and the source-declared collaborator names are structural; `foundationalPrompt` and `rolePrompt` are restored from source; an uncustomized `model` or `runnerPreference` adopts the source default; a customized runtime pair is preserved and receives the current `runtimeConfigDriftNoticeFingerprint` notice behavior; and structural drift or an invalid model/runner pair refuses the whole run. The complete active-role inventory remains required only in `agentos-example`. Other Projects may hold any subset: absent roles are skipped and are not created by ordinary synchronization.
2. Ordinary canonical template synchronization preserves partial inventories outside `agentos-example`. The canonical Project holds the complete post-A1 canonical template set, and an absent canonical row there is restored through canonical installation. In every other Project, each canonical template row the Project holds receives the current prompt synchronization, structural validation, protected/in-use refusal, and registered rollover behavior, while canonical templates it lacks are neither an error nor created. A Project with no canonical template rows is valid.
3. The existing assignee, `baseFromStepIndex`, and step-name transition tables retain their current cross-Project scope: matching rows in every Project adopt those transitions, including the current safe regression-task reassignment rules. The special migrations that create `regression-verifier` and `spec-revalidator`, copy their source Agent settings, and copy Repo grants remain scoped to `agentos-example`; ordinary sync does not create either Agent in another Project.
4. `db:sync-canonical-prompts -- --install-full <projectId>` produces the complete post-A1 canonical Agent and template inventory in the addressed Project while filling missing objects only. An unknown id is refused before the transaction opens; inside the transaction, the Project and its Environments are re-read before the first mutation, and a missing Project, zero or multiple Environments, or any archived same-name canonical Agent refuses before any mutation. With those preconditions satisfied, ordinary synchronization retains all of its normal update, rollover, preservation, and refusal effects, after which the same transaction creates only the target's missing canonical objects. Each new Agent is bound to the sole Environment and uses the seed's exact create mapping: source `name`, `title`, `model`, `runnerPreference`, `inboxAccess`, shared `foundationalPrompt`, role `rolePrompt`, source-declared collaborators, `runtimeConfigCustomized: false`, `runtimeConfigDriftNoticeFingerprint: null`, `codexServiceTier: DEFAULT`, `disabledTools: []`, and `archivedAt: null`. Missing templates are created through the A1-exported `planCanonicalInstallation` and `applyCanonicalInstallation`; the canonical installer remains the owner of `variables: ["branchName"]` and step binding. The install phase does not overwrite an existing object, resurrect an archived Agent, or create a Repo, `AgentRepoAccess`, `AgentSecretGrant`, or any other grant. A second successful run is a no-op.
5. Ordinary sync and optional full installation remain one all-or-none, 120-second interactive transaction with the current isolation semantics and no explicit `Serializable` setting; every refusal rolls back mutations for every Project. The final summary line is one JSON object of this exact shape: `{ "projects": { "<slug>": ProjectCounters }, "totals": ProjectCounters }`. `projects` contains every Project, including zero-change Projects, with slug keys emitted in lexical order. `ProjectCounters` has `templates`, `createdCanonicalTemplates`, `createdAgents`, `createdAgentRepoGrants`, `adoptedAssignees`, `adoptedStepBases`, `adoptedPriorOutputDeclarations`, `renamedSteps`, `migratedTasks`, `adoptedAgentDefaults`, `runtimeDriftNotices`, and `updated` integer fields; `preservedTaskAssignments` with integer `archived`, `nonTodo`, `started`, and `output`; `updatedSteps` keyed by every canonical template name and then every source step index; and `updatedRoles` keyed by every canonical role name. Missing activity is represented by zero, `updated` keeps its current meaning as the sum of mutation counters and all `updatedSteps`/`updatedRoles` counts, and each field in `totals` is the corresponding sum across `projects`. A validation or refusal after a Project is known starts with `Project <slug>:` and identifies an existing Agent as `<name> (<id>)`, a template as `<name> (<templateId>)`, and a step as `<templateName> step <stepIndex> (<stepId>)`; missing-object errors use the canonical name or requested id that was available. Source-load failures and unknown Project ids name the failing source or requested id without inventing a slug or database object.
6. `db:verify-agent-template -- --project <id>` accepts a partial canonical inventory and verifies exactly the canonical objects that the addressed Project holds; an unknown id refuses. For each active canonical-named Agent present, it checks `name`, `title`, `inboxAccess`, source-declared collaborators, `foundationalPrompt`, and `rolePrompt`; `model` and `runnerPreference` must equal source unless `runtimeConfigCustomized` is true, and a customized pair receives the same model-catalog/runner compatibility check as the existing canonical verifier. It does not require absent canonical Agents or templates and ignores noncanonical inventory. For each canonical template present, it checks source `name` and `description`, installer-owned `variables: ["branchName"]`, exact step count, and every step's `stepIndex`, `name`, `layer`, Agent name, derived `assigneeType`, inherited `runner`, `approvalGate`, `outputKind`, `prompt`, `spawnPolicy`, `opensPullRequest`, `requiresCommit`, `attachmentsFromPrevious`, `priorOutputKinds`, and `baseFromStepIndex`. Existing compound special checks run only when `compound-engineer-workflow` is present, and existing direct merge-tail/binding checks run only when `direct-engineer-workflow` is present. With no `--project` argument, selection by `agentos-example`, complete Agent/template inventory requirements, special checks, customized-runtime treatment, and success output remain unchanged apart from the post-A1 third-template count.
7. `agents/README.md` and `docs/install.md` describe per-Project synchronization, partial verification, and `--install-full`, and separate full-tail readiness into three categories. Repository files are `scripts/merge-gate.sh`, `scripts/regression-verification.sh`, `scripts/gate-worker/gate-dispatch.sh`, and `scripts/gate-worker/lib.sh` in the target repository. Control-plane prerequisites are an in-Project Repo for the target and `AgentRepoAccess` for every effective template assignee. Operator infrastructure comprises the required model CLIs and runner-host authentication, authenticated `gh`, `GITHUB_READ_TOKEN`, an SSH-reachable gate worker selected through `RUNNER_GATE_SERVER`, and the private merge-executor GitHub App installed on the target repository with its isolated executor service. The docs state that provider authentication is runner-host infrastructure and do not claim that `AgentSecretGrant` is required.

Out of scope: changing `POST /projects`, its A1 bootstrap operation, or `POST /onboarding`; automatic Repo, `AgentRepoAccess`, `AgentSecretGrant`, or other grant creation; per-Project transactions, partial commits, retries, locks, or an explicit transaction isolation level; changing the `agentos-example` canonical-Project concept; web changes; changes to canonical template step documents; changes to gate, regression, merge-lease, gate-worker, or merge-executor scripts and services; provisioning operator infrastructure; database schema migrations.

Ordinary sync creates no missing Agent outside the two existing canonical-Project-only special migrations; `--install-full` is the only A2 path that fills another Project's missing canonical inventory. Existing canonical rollover blockers, in-use Task protections, customized runtime preservation, runtime drift notices, transition tables, and special-migration grant semantics remain authoritative.
