Runner: A Codex Run survives a provider disconnect by resuming inside the Run

A Codex child process that dies with a transient network signature before its terminal event is resumed in place against the same Run and session, up to three times, instead of settling the Run as a failure.

Route: implementation=senior-dev - the new loop sits between the provider child's exit and the single `evidence` value that every downstream verdict is computed from, on the boundary where the run lease stops renewing, where the walltime and stall budgets are attributed, and where a second `FINAL_OUTPUT` row decides a session's token and cost columns; a misplaced relaunch loses the terminal event or double-counts usage without any focused suite witnessing it.

Background: This brief was researched against `main` commit `9a52c6ada5cea5a309e53d87912dd33c5249fae5`.

Codex reports reconnect progress through the same `error` event shape it uses for terminal provider failures, so `parseCodexEvent` deliberately does not latch `state.sawError` for a message matching `isCodexReconnectStatus` and keeps it only as `state.providerError` evidence (`packages/runner/src/adapters/codex.ts:168-177`; the pattern and the incident that produced it are in `packages/db/src/provider-terminal.ts:1-17`). That is the whole of today's in-Run tolerance: the CLI reconnects internally a few times, and when it gives up the child exits. `executeClaim` awaits that exit once — `const evidence = await completedHandle.exit` (`packages/runner/src/runner.ts:484-486`) — and every later decision in the function reads that single value: the regression handoff read, the task-output remediation block, `agentExecutionSucceeded`, the post-delivery-disconnect tolerance test, the failure envelope, and `session.finish` (`packages/runner/src/runner.ts:513`, `669-675`, `869-928`). A disconnect death is `exitCode === 0`, `signal === null`, `terminationReason === null`, `terminalEventSeen === false`, which `classifyRuntimeError` reaches only at its last-but-one branch and calls `PROTOCOL_ERROR` (`packages/runner/src/adapters/runtime.ts:457-459`). Over the last twelve days about 8-10% of Codex Runs ended in protocol-error and roughly six in ten of those were network disconnects; PI, which retries in process, was about 1%.

The stored conversation identity that would make recovery possible already exists, but only the next claim can use it. `parseCodexEvent` records `thread_id` from `thread.started` into `state.providerConversationId` (`packages/runner/src/adapters/codex.ts:138-140`); the flush loop sends it with every event batch (`packages/runner/src/runner.ts:267`); `appendRunEvents` writes it onto the `Session` row once and never overwrites it (`packages/api/src/run-lifecycle.ts:343-348`; `Session.providerConversationId` at `packages/db/prisma/schema.prisma:1092`). A later claim pairs it with `Session.resumeInput` into `priorResume` and hands it back as `claim.resume` (`packages/api/src/run-claim.ts:939-942,1120`), which `executeClaim` turns into `adapter.resume` at launch (`packages/runner/src/runner.ts:424-426`). So the recovery costs a whole new Run: a new claim, a new workspace clone, a new provisioning phase, and a `Run.runNumber` against `maxRunsPerTask`.

Nothing about a second provider launch inside one Run is new. The task-output remediation path already does exactly that: it calls `runLease.launch(() => adapter.resume({ ...spec, providerConversationId, input }))`, reassigns the mutable `handle`, awaits the new child's exit, and emits its own `TASK_OUTPUT_REMEDIATION_STARTED` / `_FINISHED` events (`packages/runner/src/runner.ts:565-625`). `codexArgs` already builds `exec resume --json … <providerConversationId> -` and the Codex preflight already proves the CLI supports it (`packages/runner/src/adapters/codex.ts:99-107,194-202,205`). `spawnAdapterRuntime` builds a fresh `AdapterState` per child, so `sawError`, `stdout`, `stderr` and `finalOutput` do not leak from a dead child into its successor (`packages/runner/src/adapters/runtime.ts:299-322`).

Three attribution facts decide whether this is safe, and all three already hold. First, usage: `recomputeSessionUsage` sums every `FINAL_OUTPUT` event of a session and writes absolute columns under an advisory lock, which is exactly what makes a multi-child session correct — "a resumed session accumulates for free (each attempt's `FINAL_OUTPUT` is its own row)" (`packages/db/src/usage.ts:580-647`, `sumUsage` at `445-473`); it is triggered whenever an ingested batch contains a `FINAL_OUTPUT` (`packages/api/src/run-lifecycle.ts:360-366`). Codex's usage rides on `turn.completed`, which is the only event that emits `FINAL_OUTPUT` and the only one that sets `terminalEventSeen` (`packages/runner/src/adapters/codex.ts:178-182`; the decoder branch at `packages/db/src/usage.ts:292-294,334-360`). A child that dies from a disconnect therefore emitted no `FINAL_OUTPUT` and reported no usage at all — its tokens are already unrecoverable today, and resuming neither loses nor duplicates anything. `Session.costUsd` is NULL for every Codex session and cost is derived from the summed token columns at `run.model` pricing (`packages/api/src/costs.ts:29-30,276-291`; `packages/db/src/cost.ts:133`), so cost follows the columns automatically. Second, walltime: the execute-phase budget is evaluated against `executionStartedAt = handle.startedAt` captured at the first launch (`packages/runner/src/runner.ts:430,437-448`), so resumes consume the same `maxDurationMin` budget rather than restarting it, while the heartbeat evidence closure reads the mutable `handle` and therefore follows whichever child is current (`packages/runner/src/runner.ts:434-436`). Third, the gap: `evaluateBudget` returns `{allowed:false, gate:"stall"}` whenever `processAlive` is false, but line 449's `&& snapshot.processAlive` guard means a heartbeat landing between two children cannot set `budget.refusal` (`packages/runner/src/budget.ts:32-34`; `packages/runner/src/runner.ts:449-452`).

The gap is nevertheless the hazard that bounds this whole feature. `heartbeatRun` extends `leaseExpiresAt` only when the body reports `processAlive: true` (`packages/api/src/run-lifecycle.ts:189-204`), and every fenced write the runner still needs — event append, activity, completion — requires `leaseExpiresAt > now` (`packages/api/src/run-fence.ts:100-107,133`), while `reconcileDatabaseRuns` treats an expired lease as a candidate for loss (`packages/api/src/reconcile.ts:110-115,190-194`). The default lease is 60 s and the default heartbeat interval is `max(5000, leaseSeconds * 500)` = 30 s (`packages/runner/src/config.ts:106,133`), so at the moment a child dies the last renewal may already be 30 s old: the time spent dead is spent against roughly 30 s of remaining lease in the worst case. A backoff calibrated like a network retry loop, not like an outage wait, is a correctness requirement here.

One classification fact is easy to get wrong. `isTransientNetworkError`'s pattern list does not match Codex's reconnect wording: `Reconnecting... 3/5 (stream disconnected before completion: tls handshake eof)` matches none of `fetch failed`, `unexpected EOF`, `connection (reset|closed|timed out|lost)`, `ECONNRESET`, `ETIMEDOUT`, `EAI_AGAIN` or the 5xx forms (`packages/runner/src/network-retry.ts:3-16,30-40`), which is precisely why such an exit lands on the `PROTOCOL_ERROR` fallback today. Reusing that predicate alone would resume almost nothing; the qualifying signature must also accept `isCodexReconnectStatus(evidence.providerError)`, and `network-retry.ts`'s own pattern lists — shared with git delivery and cloning — must not be widened to carry provider wording.

Changes:
1. Add a Codex-owned predicate that decides, from `ExitEvidence` plus the dead child's `providerConversationId`, whether an exit is an in-Run resume candidate. It returns true only when every one of these holds: `terminalEventSeen === false`; `signal === null`; `terminationReason === null`; `providerConversationId !== null`; no disqualifying provider error was seen earlier in the same child (see Change 9); and the exit carries a network signature, defined as `isCodexReconnectStatus(evidence.providerError)`, OR the bare disconnect wording the Codex adapter already owns and latches — `stream disconnected before completion: …`, the form pinned at `packages/runner/src/adapters.test.ts:1563-1570`, which is what the CLI reports when it stops reconnecting — OR `isTransientNetworkError` over the concatenation of `providerError` and `stderr`. That bare form matches neither `isCodexReconnectStatus` (it is not `^Reconnecting\.\.\.`) nor any pattern in `network-retry.ts:3-16` (`unexpected EOF` does not match `tls handshake eof`), so omitting it would leave the commonest disconnect death unresumed. It returns false whenever `classifyRuntimeError(evidence).failureClass` is any of `BINARY_NOT_FOUND`, `AUTH_REQUIRED`, `TOOL_FAILED`, `RATE_LIMITED` or `CANCELLED_OR_TIMED_OUT`, so an unauthenticated CLI, a missing binary, a rate limit and a runner-initiated kill are never resumed even if their text happens to contain a matching token. Exit code is deliberately not part of the signature beyond what those classes already exclude: a disconnect can exit 0 or nonzero. Do not add Codex wording to the pattern lists in `network-retry.ts`.
2. Expose that predicate at the `CliAdapter` seam (`packages/runner/src/adapters/runtime.ts:105-112`) as an optional capability derived from `AdapterDeclaration`, set only by `codexDeclaration`. `runner.ts` must not branch on `RunnerKind`; an adapter that does not declare the capability takes today's path with no added call, no added event and no added await. `claudeDeclaration` and `piDeclaration` are not edited.
3. Replace the single `const evidence = await completedHandle.exit` (`packages/runner/src/runner.ts:484-486`) with a loop that yields the final evidence, leaving every downstream consumer — `producedOutput`, the regression handoff read, the remediation block, the delivery block, the completion outcome — reading that one final value exactly as today. Each iteration relaunches through `runLease.launch(() => adapter.resume({ ...spec, providerConversationId, input }))`, reassigns `handle`, and awaits the new child's exit. `providerConversationId` comes from the session-level value of Change 10. The loop stays at that call site: the two paths that already settle a Run whose product exists sit on either side of it — the fenced regression handoff read immediately after the exit (`runner.ts:487-513`) and the post-delivery-disconnect detection inside delivery (`runner.ts:668-720`) — so the loop cannot simply be moved after them. Instead, before the first resume it calls a terminal-product probe: the detection each of those two paths performs today, extracted into one shared helper that both of them then call. The probe answers one question — does a durable product of this Run already exist (a persisted regression output handoff, or a delivered output identity whose commit matches the captured workspace HEAD) — and when it does, there are zero resumes and control falls through to the existing paths, which reach their present outcomes by their present route. Extraction is behaviour-preserving: the two paths keep their own events, their own error handling and their own authority, and their existing tests pass unmodified.

4. Before each relaunch the loop proves the Run still has lease to spend rather than reading a flag. `runLease.checkpoint()` is not that proof: it only awaits the in-flight renewal, the cancellation task and the pending transitions and returns the authority already adopted (`packages/runner/src/run-lease.ts:188-193`); it never sends anything. `runLease.deadline` is not that proof either: it is the delivery budget deadline and throws outright before the deliver phase (`run-lease.ts:254-257`; `packages/runner/src/network-retry.ts:189-192`). Add one seam to the run lease instead: `renewNow()` performs a single renewal round-trip through the existing `options.send` path, adopts the resulting authority exactly as the interval renewal does, and returns that fresh authority together with the remaining lease TTL. The TTL is derived from the last renewal the control plane actually accepted as extending the lease — `heartbeatRun` extends `leaseExpiresAt` only for a `processAlive: true` body (`packages/api/src/run-lifecycle.ts:189-204`), so the lease tracks that timestamp separately from `renewedAt` and a dead-window renewal confirms authority and cancellation without inventing lease time. The relaunch gate is then four conjuncts: `renewNow()` returned a held authority; the remaining TTL is above a floor of 15 s; the execute-phase walltime against `executionStartedAt` still has room for another attempt; and no cancellation is pending. A failed renewal, a refused authority, or any gate failing means no resume: the loop stops, no child is spawned, and the existing failure path proceeds on the evidence in hand — the same fall-through the first launch uses at line 427. Budget and stall state carry across children: the heartbeat evidence closure must not treat a fresh child's `lastProgressEventAt` — reset to that child's `startedAt` by `createAdapterState` (`packages/runner/src/adapters/runtime.ts:157-179`) — as progress, so a Run stalled before the disconnect stays stalled after the resume.

5. Cap in-Run resumes at 3 per Run and pace them with `transientBackoff(attempt)` from `packages/runner/src/network-retry.ts:78-81` for attempts 1, 2 and 3 — jittered ceilings of 1 s, 2 s and 4 s, worst case about 7 s of total wait. The cap and the pacing are not tunable by configuration. The rule they encode: the whole time this Run spends with no live child must stay far inside the remaining run lease, because a `processAlive: false` heartbeat does not renew `leaseExpiresAt`.
6. Emit `PROVIDER_RESUME_STARTED` with `source: "RUNNER"` immediately before each relaunch, carrying the attempt number, the cap, the `providerConversationId`, the backoff milliseconds actually waited, and the dead child's exit facts in the shape `exitEvidencePayload` already produces (`packages/runner/src/runner.ts:119-125`). Emit `PROVIDER_RESUME_EXHAUSTED` once, with the same identifying fields, when a qualifying exit arrives with the cap already spent. Neither kind may be `FINAL_OUTPUT`: that string is the trigger for `recomputeSessionUsage` and the unit of usage summation.
7. The resume input is a continuation instruction, not the original prompt and not the remediation prompt: it states that the provider stream dropped, that the conversation is being continued in the same Run and workspace, that already-completed work and already-written files must not be redone or reverted, and that the agent should carry on from where it stopped and finish the task normally. Model it on `missingOutputRemediationInput` (`packages/runner/src/runner.ts:103-108`) and keep it a module-level function so a test can assert the bytes reaching stdin.
8. Leave `session.start`, the launch manifest and `promptHash` computed once from the first launch (`packages/runner/src/runner.ts:463-478`). The per-spawn record is the `PROCESS_STARTED` event `spawnAdapterRuntime` already emits with its own pid, argv and prompt hash (`packages/runner/src/adapters/runtime.ts:370-377`), plus the events from Change 6.

9. Give `ExitEvidence` the disqualifying-error history the predicate needs. `parseCodexEvent` overwrites `state.providerError` on every `error` event (`packages/runner/src/adapters/codex.ts:167-176`), so a child that reported a real provider error and then a reconnect notice exits carrying only the reconnect string, and the predicate of Change 1 would resume a Run that a later status merely papered over. The adapter state records whether any non-reconnect provider error was seen and the first such message, `spawnAdapterRuntime` carries both into `ExitEvidence` alongside the existing fields (`packages/runner/src/adapters/runtime.ts:343-353`), and the predicate returns false whenever that flag is set. A later reconnect status must never be able to overwrite the fact that a disqualifying error occurred.

10. Hold `providerConversationId` once per session rather than per child. Today the flush loop reads `handle?.providerConversationId` (`packages/runner/src/runner.ts:267`) and the remediation block reads `completedHandle.providerConversationId` (`:546`), while a fresh `AdapterState` starts that field at `null` (`packages/runner/src/adapters/runtime.ts:157-179`), so a batch flushed after a relaunch would send `null` and `appendRunEvents` — which writes the column once and never overwrites (`packages/api/src/run-lifecycle.ts:343-348`) — could leave `Session.providerConversationId` unset for the whole Run. Introduce one session-level value that is set by the first child reporting an id and updated only by a later child that reports a non-null one; every consumer — event flush, each resume of Change 3, and the remediation launch — reads that value. Backoff and the clock are injectable seams on the same path so the timing rules of Changes 4 and 5 are testable without wall-clock waits.

Out of scope: `packages/api/src/run-claim.ts` and the claim-time resume path in every respect, including `priorResume`, `Session.resumeInput`, `Session.resumableUntil` and `Session.resumeAttempt` — the in-Run counter is process-local and must not be written to that column; the requeue and retry mechanism (`Run.retryOfRunId`, `packages/api/src/reconcile.ts`); the Claude and PI adapters and `packages/runner/src/adapters/pi.ts`'s own usage folding; the Codex CLI's internal reconnect count and any `-c` flag that would change it; the pattern lists, attempt counts and profile constants in `network-retry.ts` (only `transientBackoff` and `isTransientNetworkError` are consumed, unmodified); the task-output remediation resume at `packages/runner/src/runner.ts:565-625`, which keeps its own single launch, its own events and its own workspace-snapshot rule and changes only by reading the session-level conversation id of Change 10; the post-delivery-disconnect tolerance block at `packages/runner/src/runner.ts:668-841` and `packages/db/src/post-delivery-disconnect-audit.ts`, whose outcomes, events and audit records are unchanged — the only edit either it or the regression handoff read receives is calling the shared detection helper of Change 3 in place of its inline detection; `classifyRuntimeError`'s branch order and the `FailureClass` set; `evaluateBudget` and every budget gate; the lease wire protocol beyond the `renewNow()` seam of Change 4 — `heartbeatRun`'s `processAlive` condition, the heartbeat body and the reconciler are unchanged; `Session` and `Run` schema, including any new column counting resumes; the board, the costs surfaces and `packages/db/src/usage.ts`; `docs/operator-api.md` and every HTTP route.

Constraints: A Run with no qualifying exit must be byte-identical to today — same events, same evidence, same outcome, same `session.finish` body. A resume never happens for a Claude or PI Run. A resume never happens after `terminalEventSeen`, which is what guarantees the dead child produced no `FINAL_OUTPUT` and therefore contributed no usage to double-count; the summation in `recomputeSessionUsage` stays the only aggregation point and is not touched. Walltime and `maxRunsPerTask` accounting must continue to run against the first launch's `startedAt` and the same `Run.runNumber`; a resume must not extend, reset or exempt any budget. A lost or revoked lease, a cancellation, and a budget refusal each end the loop immediately and hand control to the existing path — the resume loop never overrides a stop the platform asked for, and each of those three is decided on an acknowledged renewal, never on a cached `runLease.held`. A Run whose terminal product already exists resumes zero times. The regression handoff read and the post-delivery-disconnect check are not moved and not reordered; their detection predicate is extracted into one shared helper that the resume loop consults before its first relaunch and that both paths then call, without changing either path's outcome, events or authority — the existing tests for both must pass unmodified. A disqualifying provider error seen anywhere in a child's life disqualifies that child's exit, whatever the last message on the stream was. The Run has one conversation identity for its whole life; no code path may publish `null` for it after a child has reported one. Failures inside the loop fail loud: a `runLease.launch` that throws propagates to the existing outer catch rather than being swallowed into "keep the old evidence". When the cap is spent, the Run is settled from the last attempt's evidence through the unchanged completion path, with the same `FailureClass` it would carry today; the resume events are the only record that earlier attempts occurred.
