The runner dependency cache retains the active dependency-key population within a bounded host-wide storage budget without recurring entry-count churn.

Route: implementation=senior-dev - ten runner processes share one cache directory, so byte accounting and eviction must be serialized against concurrent restore and publication under the existing `flock` ownership window

Background: PR #335 raised `DEPENDENCY_CACHE_ENTRY_LIMIT` from 4 to 12, but the post-deploy delta is 228 hits, 40 misses, and 18 evictions, improving the hit ratio from 0.73 to 0.85 while evictions continue. Every eviction has `condition: "entry-limit"`; two keys were evicted twice. In the untimestamped log, 63 misses cover 40 distinct keys. That population is not a ceiling: anneal, word-factory, and vibeville run chains, and every PR that changes a lockfile creates another identity because `package-lock.json` is a required hashed input (`packages/runner/src/dependency-cache.ts:371-405`) and the cache key hashes all inputs plus npm configuration and toolchain (`packages/runner/src/dependency-cache.ts:489-510`). Raising the count to 40 would encode a transient observation and resume churn as repositories advance.

This is one host-shared cache, not one cache per runner: the launch wrapper assigns every service the same `shared/dependency-cache` root (`scripts/deploy/launchd-service-wrapper.mjs:245-256`), while `loadRunnerConfig` consumes it (`packages/runner/src/config.ts:105-144`). The ten runners therefore share 12 entries, not 120. Publication clones each present root and workspace `node_modules` target into `trees/` and writes the full file manifest to `metadata.json` (`packages/runner/src/dependency-cache.ts:884-920`). The 12 live entries measured on 2026-09-02 are about 503 MiB apparent each; allocated usage ranges from 544 MiB to 560 MiB, totals 6.39 GiB, and each manifest is 2,836,472 bytes. Forty entries at the measured maximum would need about 21.9 GiB, but the host volume is 460 GiB at 85 percent with 67 GiB free (records/AUDIT-host-resources-20260901.md), and the 40 keys are a two-day accumulation that includes lockfile versions from branches since merged, not a simultaneously live population. Select a 16 GiB host-wide byte budget: about 29 entries at the measured maximum, two and a half times the present live count, while keeping the cache under a quarter of the free space.

Changes:
1. Replace the exported 12-entry limit and count-triggered retention with a fixed 16 GiB byte budget. Account each immutable entry by summing `Stats.blocks * 512` for every inode in its directories, `metadata.json`, and complete `trees/` contents. Use `lstat`, count symlink inodes without following them, preserve the existing safe-symlink validation, and reject special files. Keep usage-marker recency as the LRU ordering, preserve the current key during its retention pass, and evict least-recently-used entries only until total accounted bytes are at or below the budget.
2. Keep all runners on the existing shared cache and make budget enforcement one atomic cache-root operation. Size enumeration, ordering, deletion, marker deletion, and the final at-or-below-budget assertion must run while holding the cache root's exclusive `flock`. Do not retain the current nonblocking lock-contention return at `packages/runner/src/dependency-cache.ts:803-850`; wait for concurrent shared restore/publication owners, then enforce the budget before returning success. Existing shared-lock protection at `packages/runner/src/dependency-cache.ts:769-781` and publication convergence remain intact.
3. Preserve the dependency-cache audit schema and the existing `hit`, `miss`, `publication`, `integrity-refusal`, and `eviction` event names and fields (`packages/runner/src/dependency-cache.ts:70-76` and `packages/runner/src/dependency-cache.ts:121-123`). Byte-driven removals emit `{event:"eviction", key:<16-character-prefix>, condition:"byte-budget"}` so the parked card's grep and `.event` tally continue to work unchanged.
4. Fail loudly after emitting `integrity-refusal` when a selected cache entry, retention entry, usage marker, or size walk is malformed or unsafe; do not install dependencies as an implicit corruption fallback. If one protected entry alone exceeds 16 GiB, or safe evictions cannot restore the budget invariant, remove any just-published over-budget entry while exclusively locked and reject the materialization with a named error. Never report a successful cache result while the cache remains over budget.
5. Replace count-retention coverage with byte-budget tests and extend corruption and concurrency coverage in `packages/runner/src/dependency-cache.test.ts`. Synthetic accounted-size cases must exercise the production retention decision without allocating GiB-scale fixtures, while filesystem fixtures cover size walking and deletion. Together they must prove LRU refresh ordering across differently sized entries, multiple evictions in one pass, exact-budget retention, oversized-entry rejection, malformed size-walk rejection, blocking enforcement after lock contention, stable audit payloads, and successful concurrent convergence without deleting an entry being restored or published. The existing count-specific assertions at `packages/runner/src/dependency-cache.test.ts:668-739` must be removed rather than preserved as a compatibility path.

Out of scope: Cache compression, content deduplication, per-repository quotas, operator-configurable budgets, age-based expiry, npm download-cache behavior, HTTP routes, deployment topology, and changes to `scripts/regression-verification.sh`, `scripts/gate-worker/*`, `scripts/merge-gate.sh`, or `packages/runner/runtime-tools` are excluded. Do not raise the entry-count limit again or retain entry count as a second eviction threshold.

Constraints: Retain the current cache identity, immutable entry layout, usage-marker LRU semantics, 16-character audit key prefix, publication convergence, and workspace restore behavior. Cache corruption and an unenforceable byte budget are errors, never cache misses or permission to continue uncached. All entry inspection is non-following and confined beneath the canonical cache root. The exclusive retention lock must cover the invariant-changing window across processes; no runner may size one snapshot and delete from another.
