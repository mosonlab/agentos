Agents: canonical roles run on Codex instead of PI

Every canonical Agent role runs on the Codex runner at the same model and effort it ran on under PI, and no canonical role file or contract test names a PI runner or an `openai-codex/` model.

Route: implementation=senior-dev-luna - the whole change is four frontmatter model strings and the test pins that freeze them; the contract this touches is already asserted mechanically by `packages/db/prisma/agent-contract.test.ts` and the canonical-sync dbtests, and no runtime code path is modified.

Background: This brief was researched against `main` commit `7dd8a60db8431683a828afce650b1618b1f545ef`.

An Agent's runtime identity is two columns, `model` and `runnerPreference` (`packages/db/prisma/schema.prisma:283-287`), and the model string carries both the model id and its reasoning effort. `splitModel` is the grammar: the last colon separates model from effort, a model may itself contain colons, and a leading colon is part of the model rather than an empty name (`packages/db/src/model-routing.ts:63-66`). The catalog lists the same underlying GPT-5.6 models twice, once per runner: `gpt-5.6-sol` and `gpt-5.6-luna` are `CODEX` entries, and `openai-codex/gpt-5.6-sol` and `openai-codex/gpt-5.6-luna` are the `PI` entries of the same models (`packages/db/src/model-routing.ts:44-48`). The `openai-codex/` prefix is what makes a model string a PI model: `catalogRunnerForModel` answers `CLAUDE` for a `claude-` prefix, `PI` for an `openai-codex/` prefix, and `CODEX` for a `gpt-` prefix, and returns `null` only for the mechanical merge sentinel (`packages/db/src/model-routing.ts:80-86`). So the Codex form of a PI model is the same string with the `openai-codex/` prefix removed and the effort suffix kept: `openai-codex/gpt-5.6-sol:xhigh` becomes `gpt-5.6-sol:xhigh`. `xhigh` and `max` are valid on both sides — `CODEX_EFFORTS` is `none, minimal, low, medium, high, xhigh, max` (`packages/db/src/model-routing.ts:35`) against `PI_EFFORTS`'s `off, minimal, low, medium, high, xhigh, max` (`packages/db/src/model-routing.ts:37`) — so no role changes effort in this chain. `agents/roles/senior-dev.md:4-5` is the shape to copy: `model: gpt-5.6-sol:high` with `runner: codex`, and `agents/roles/regression-verifier.md:4-5` is the same shape at `xhigh`.

Four canonical role files still name PI models: `agents/roles/review-coordinator.md:4-5` and `agents/roles/review-coordinator-sol.md:4-5` at `openai-codex/gpt-5.6-sol:xhigh` with `runner: pi`, and `agents/roles/librarian.md:4-5` and `agents/roles/spec-revalidator.md:4-5` at `openai-codex/gpt-5.6-luna:xhigh` with `runner: pi`. No canonical template step file declares a `runner` or `model` key at all — the frontmatter contract for a step carries neither (`agents/README.md:35-47`), and the Agent row is the single runtime authority (`agents/README.md:55-60`) — so no file under `agents/templates/` is in scope. The invariant that binds a role's two frontmatter values is `assertCanonicalAgentSources`, which throws when `catalogRunnerForModel(role.model)` disagrees with the declared `runnerPreference` (`packages/db/src/agent-contract.ts:18-29`); the same equality is asserted per named role in `packages/db/prisma/agent-contract.test.ts:94-114`. That test asserts the relation, not the values, so it passes both before and after this change and cannot by itself freeze the outcome; the value pins that exist today are `packages/db/prisma/agent-contract.test.ts:162-163` for `regression-verifier` and `packages/db/prisma/agent-contract.test.ts:182` for `implementation-plan-executioner`.

Deploy sync propagates a canonical role change to every project through `packages/db/prisma/sync-canonical-prompts.ts`, and it treats a row differently depending on one boolean. For each canonical-named Agent row it computes the differences against the role source, splits them into runtime differences (`model`, `runnerPreference`) and structural ones, and refuses the whole project pass on any structural difference (`packages/db/prisma/sync-canonical-prompts.ts:331-334`). A runtime difference is adopted — the row is rewritten to the canonical `model` and `runnerPreference` and its drift fingerprint cleared — only when `runtimeConfigCustomized` is false (`packages/db/prisma/sync-canonical-prompts.ts:340-364`). When `runtimeConfigCustomized` is true the row is never rewritten: sync records a fingerprint of the canonical-versus-production pair and raises one operator Inbox message per distinct pair, and otherwise leaves the row exactly as the operator set it (`packages/db/prisma/sync-canonical-prompts.ts:365-403`). `runtimeConfigCustomized` is set to true by any `PATCH /agents/:agentId` that changes `model` or `runnerPreference` (`packages/api/src/routes/agents.ts:291-295`) and is cleared only by `POST /agents/:agentId/reset-runtime-config`, which rewrites the row from the canonical role source (`packages/api/src/routes/agents.ts:301-331`).

Converging a customized row is therefore an operator action, not a code change, and it is outside this chain. The one row that had drifted onto a PI model — the Anneal project's `regression-verifier`, which read `openai-codex/gpt-5.6-luna:max` while the canonical file and the Word Factory row read `gpt-5.6-luna:xhigh` — has already been reset through `POST /agents/:agentId/reset-runtime-config` and now reads `gpt-5.6-luna:xhigh` with `RunnerPreference.CODEX` and `runtimeConfigCustomized` false. The standing rule this chain relies on: the operator resets any remaining customized row through that route before the deploy that carries this change, so every canonical-named Agent row reaches the deploy uncustomized and the sync's ordinary adoption path writes the new model strings. This chain adds no sync logic and no migration of its own.

PI itself is unaffected. It stays a supported runner kind in the platform, with its adapter, its enum values, its catalog entries and its console surfaces intact, because it may front other providers later. What ends is only the routing of OpenAI models through it: after this chain no canonical role runs through PI, and an operator who wants a PI Agent still selects one.
