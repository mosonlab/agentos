Goal: A merge tail parked in blocked-downstream after a semantic or gate regression FAIL inside a base-drift recovery attempt can be sent into the ordinary review-fix or gate-fix repair round by an explicit operator request, charged against the chain's existing automatic repair budget, without any fabricated marker or database write.

Background: `handleRegressionCompletion` in packages/api/src/merge-tail-actions.ts records a failing verdict and, when `recovery` is set, calls `stopMergeTail` and returns; only the non-recovery path counts prior `repairAttempt` markers against `MAX_MERGE_TAIL_REPAIR_ATTEMPTS`, picks the fixed-implementation assignee, and calls `createMergeTailRepairTask`. `RECOVERY_TRANSITIONS` in packages/db/src/merge-tail.ts allows BLOCKED_DOWNSTREAM only to REPAIRING, and the sole driver is `reopenAfterHeadAdoption` in packages/api/src/merge-readiness-worker.ts, which requires a head-adoption refusal code and a passing verdict. A fresh regression run is refused by packages/api/src/regression-repair-handoff.ts because no `repairResult` marker binds the failing head to its base, and `PATCH /tasks/:id` refuses chain statuses. Observed on 2026-09-03 (word-factory chain 3a8aee90-89cc-477d-a81a-7329769b5e38, regression task cmtl7r6ks001hmp2ojtj58wal, aggregate cmtldk4dk089tmp2oeogpjdu2): recovery attempt 1 found a real defect at 5a769702 against 5d2b64fc and the chain had no path back except a canonical successor chain. Recovery stays non-repairing by design; this brief adds the operator-driven reentry only.

Changes:
1. Add `POST /tasks/:taskId/merge-tail/repair` with required JSON `requestId` (string) and optional `reason`. `taskId` names the chain's regression verification task. The route resolves the chain's latest MergeRecoveryAttempt for that regression task and requires: status BLOCKED_DOWNSTREAM, `refusalCode` null, `regressionTaskId` equal to `taskId`, the regression task's stored TaskStepOutput produced by the aggregate's `recoveryRunId` with a `review-fail` or `gate-fail` verdict, regression, readiness and integrator tasks all in REVIEW, and no active Run on any of them. Any other state refuses with `409 Conflict` and a specific code (`merge_tail_repair_not_blocked`, `merge_tail_repair_verdict_missing`, `merge_tail_repair_active_run`, `merge_tail_repair_refusal_pending`).
2. On acceptance, inside one transaction: count prior `repairAttempt` markers for that repair kind exactly as the non-recovery path does and refuse with `409` code `merge_tail_repair_budget_exhausted` when `MAX_MERGE_TAIL_REPAIR_ATTEMPTS` is reached; otherwise call the same `createMergeTailRepairTask` with the recovery run as `sourceRun`, the verdict's head, base and summary, and the fixed-implementation assignee resolved the same way as the automatic path, then transition the aggregate BLOCKED_DOWNSTREAM to REPAIRING through `transitionMergeRecovery` and clear `failureReason`. Record an operator TaskActivity on the regression task with `requestId`, `reason`, the repair kind, head and base, and the created repair task id.
3. Idempotency: a repeated request with the same `requestId` returns the original result and creates nothing; a request whose `sourceRunId`-matching `repairAttempt` marker already exists is refused with `merge_tail_repair_already_open`.
4. After the repair task completes and the regression re-runs with the recovery context, `handleRegressionCompletion` must behave as it does today: a pass proceeds through `awaitAuthorization`; a further FAIL stops the tail again and the operator may request another round until the budget is exhausted. Add or adjust whatever the recovery context resolution needs so that the re-run regression is attributed to the same recovery attempt (aggregate `recoveryRunId` updated to the new regression Run in the same place the automatic recovery path sets it), and write the repair result marker exactly as the non-recovery path does so `regression-repair-handoff` accepts the re-run.
5. Tests in packages/api/src for the route and the completion path: refusal for a non-blocked aggregate; refusal when the verdict is a pass or comes from a run other than `recoveryRunId`; refusal when an active Run exists; acceptance creates one repair task with the right assignee and one `repairAttempt` marker with `sourceRunId` = recovery run, moves the aggregate to REPAIRING, and a repeated `requestId` is a no-op; budget exhaustion refuses; a completed repair followed by a passing regression reaches `awaitAuthorization`, and a completed repair followed by a second FAIL parks the aggregate in BLOCKED_DOWNSTREAM again with the stop notice.
6. docs/operator-api.md: document the route, its refusal codes, and add a subsection under "Recovering a merge tail stopped after its repair budget" that states a FAIL inside base-drift recovery is reentered with this route before a successor chain is considered; README route handbook rule applies (same change).

Out of scope: any automatic repair inside recovery; changes to `MAX_MERGE_TAIL_REPAIR_ATTEMPTS`, `MAX_AUTOMATIC_BASE_DRIFT_RECOVERIES`, or `RECOVERY_TRANSITIONS` beyond what Change 2 uses (BLOCKED_DOWNSTREAM to REPAIRING already exists); `reopenAfterHeadAdoption` and its refusal codes; refresh-conflict verdicts (a refresh conflict inside recovery keeps its current stop); UI; any change to `regression-repair-handoff` validation rules; writing repairResult markers from the route itself.

Constraints: The route creates no marker that the automatic path would not create at the same point, and never writes a `repairResult`; the repair task's genuine completion writes that. Every refusal is a typed 409 with no side effect. All writes happen in a single serializable transaction with the chain lock the automatic path takes. Fail loud: an inconsistent aggregate (for example REPAIRING with no open repair task) is refused, not repaired. No new configuration.
