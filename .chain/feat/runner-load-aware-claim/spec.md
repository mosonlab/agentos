Each runner remains available to finish existing work while refraining from starting new work on a CPU-saturated host.

Route: implementation=senior-dev - a process-level poll-loop change on the shared runner host whose failure mode (runners silently never claiming again) the unit suite cannot fully witness.

Background: This brief targets `origin/main` at `75ea468446df55fd60c564bcae1f38f13dc0f782`, verified with `git rev-parse origin/main` on 2026-09-01. In production from 10:00-10:45Z that day, one 10-core macOS host ran 12 runner processes with five active chains. Its 1-minute load average reached 88-90; API `GET /version` calls took 8-20 seconds and `GET /inbox/messages` timed out at 60 seconds. In the same window, Runs 1-2 for task `cmtihqd3c08qkmpm6cs9i6dbb` became LOST with `Runner heartbeat starved after ...`; run `cmtih6ba20726mpm6ua49q6zx` timed out with `stall: tool inactivity deadline exceeded: command_execution`; and two Runs failed with protocol errors ending in `Reconnecting 5/5 (request timed out)` or `stream disconnected`.

The cost is repeated work, not just noisy status. Over the preceding seven days, 232 of 832 Runs, or 28%, were not their Task's final Run. That population included 38 `protocol-error` failures averaging 26.8 minutes before failure, 19 `transient-provider` failures averaging 30.3 minutes, 12 LOST Runs averaging 32.0 minutes, and three `budget-exceeded` timeouts averaging 36.7 minutes. Each attempt restarts from scratch or a salvage ref. Runner CPU demand is bursty because model-provider waits are nearly idle, while agent-invoked `tsc`, `eslint .`, and test commands create short host-wide bursts. L2 separately narrows those commands to the affected workspace; L1 must reduce claim admission pressure without depending on L2.

The runner currently has no host-load admission boundary. `RunnerConfig` is declared at `packages/runner/src/config.ts:27-57`; `loadRunnerConfig` parses `RUNNER_POLL_INTERVAL_MS` with a 5000 ms default at `packages/runner/src/config.ts:79-102`. The top-level loop calls `sweepWorkspaces`, then `pollForTask`, then waits `config.pollIntervalMs` when no task ran or polling failed (`packages/runner/src/index.ts:89-114`, functions `sweepWorkspaces` and the `while (!stopping)` loop). `pollForTask` immediately calls `controlPlane.claim(config)` and, after a claim, awaits `executeClaim` (`packages/runner/src/runner.ts:936-945`). Consequently, admission can be withheld before a claim without touching a Run already executing. The shared maintenance lock is held outside and across that loop and released only after it ends (`packages/runner/src/index.ts:52-73,116-120`). At the pinned SHA, `git grep -n -E 'os\.(loadavg|cpus)\(' origin/main -- packages/runner/src` returns no matches.

The current test style is source-adjacent Node `test` plus strict assertions. Config environment fixtures save, mutate, and restore individual variables (`packages/runner/src/config.test.ts:155-172`), while runner fixtures inject `ControlPlane` and other dependencies rather than contacting production surfaces (`packages/runner/src/runner.test.ts:109-123`; `ExecuteClaimDependencies` is defined at `packages/runner/src/runner.ts:150-165`). There is currently no `index.test.ts` or loop test under `packages/runner/src`, and `pollForTask` is not directly referenced by a test. The smallest polling-loop unit must therefore become importable without executing the `index.ts` startup side effects.

Changes:
1. Add exactly one required `RunnerConfig` field, `claimMaxLoadAverage`. Parse it from new environment variable `RUNNER_CLAIM_MAX_LOAD_AVERAGE`. When the variable is absent, compute the startup value as `os.cpus().length * 1.5`; when present, accept decimal or integer text only if converting the complete value yields a positive finite number. Zero, negative values, empty text, `NaN`, infinities, numeric prefixes with trailing text, and every other malformed value fail startup with a `RUNNER_CLAIM_MAX_LOAD_AVERAGE must be a positive finite number` error. Do not use `parseInt` or retain a default after an explicit invalid value.
2. Before every `controlPlane.claim` attempt, after that iteration's workspace reclaim sweep, read the 1-minute load average from `os.loadavg()[0]`. If load is strictly greater than `config.claimMaxLoadAverage`, skip the claim and wait the ordinary `config.pollIntervalMs`; equality is admitted. Keep a single process-local transition flag only for logging: emit `Runner claim overloaded: load=<load> threshold=<threshold>` once when entering overload and `Runner claim recovered: load=<load> threshold=<threshold>` once when a later reading is at or below the threshold. Repeated overloaded or admitted polls emit no duplicate state line. Workspace reclaim remains eligible on every scheduled sweep, and overload neither exits the runner nor releases its shared maintenance lock.
3. Expose the smallest polling-loop unit needed to test several iterations without importing the top-level entrypoint. Inject the load reader and test clock/wait, claim, reclaim, stop, and log effects through explicit parameters with production defaults or entrypoint adapters, following the existing dependency-injection style. The production load reader is exactly the Node `os.loadavg()[0]` read. Keep the admission check outside `executeClaim`; once `pollForTask` receives a claim, its existing `await executeClaim(...)` path runs to completion regardless of later load readings. On Windows, where Node reports zero load averages, admission is deliberately a no-op and this is the only documented degraded case.
4. Document `RUNNER_CLAIM_MAX_LOAD_AVERAGE`, its `CPU count * 1.5` default, strict-positive override contract, and Windows no-op beside the runner polling variables in `.env.example:47-51`. Add no API endpoint, metric, Inbox notice, or other observability surface; the two transition log lines are sufficient.

Out of scope: changing the number of runner processes or launchd services; scheduling, priorities, prediction, hysteresis, or per-task, per-chain, or quota-based admission; any control-plane or API change, including changing the rule that work goes to whichever runner asks; changing heartbeat, lease, stall, retry, or LOST semantics; changing commands agents run or taking a dependency on chain L2; auto-deploy quiet-window behavior; gate worker capacity.

Constraints: Keep every runner process and its shared lock alive while overloaded. Fail loudly on malformed configuration and on unexpected implementation errors; provide no silent fallback other than the documented Windows zero-load no-op. Preserve the ordering `reclaim, admission check, claim, execute or ordinary wait`, and preserve the current no-delay continuation after a successfully executed claim. The overload state is only a one-bit log dedupe flag, not hysteresis or a scheduler. Use Node built-ins only, add no dependency, and keep production code to a few dozen lines plus source-adjacent tests and required `RunnerConfig` fixture updates.
