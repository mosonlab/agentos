Runner: A runner serves only the runner kinds it declares

A runner declares which RunnerKind values it serves, and the control plane hands it queued Runs of those kinds only, while an undeclared runner keeps today's behavior exactly.

Route: implementation=senior-dev - the filter lives inside the serializable claim transaction's ranking window and next to the backend circuit check, where a misplaced predicate starves a whole kind or lets a concurrent retry hand out a foreign-kind Run without any focused suite witnessing it.

Background: This brief was researched against `main` commit `9a52c6ada5cea5a309e53d87912dd33c5249fae5`. Every runner daemon today is interchangeable: `RunnerConfig` carries no statement about which backends this host serves, only a `binaries` map built for every kind in `RUNNER_KINDS` (`packages/runner/src/config.ts:60,167-170`; `packages/runner/src/adapters.ts:226`), and the claim request body carries `runnerId`, `leaseSeconds` and four telemetry fields and nothing about capability (`packages/runner/src/api.ts:131-143`). The control plane's `claimInput` accepts exactly those fields (`packages/api/src/run-claim.ts:75-80`). A `Run` row pins its backend in `runner RunnerKind` (`packages/db/prisma/schema.prisma:919`), but the ordinary-runner candidate selection never reads it: the ranking query filters on Run status, readiness, agent and task state, integrator output kind and chain holds, orders by unfinished-chain priority then `readyAt` then `createdAt`, and takes `LIMIT 20` (`packages/api/src/run-claim.ts:348-382`); the per-candidate loop then decides on execution mode (`packages/api/src/run-claim.ts:613-619`) and backend health (`packages/api/src/run-claim.ts:668-673`). So any polling runner can be handed any agent Run of any kind. Today's failure model has two distinct halves, and neither is a claim that fails on a missing binary: a host that lacks one CLI does not silently claim that kind and fail it, because its own availability monitor reports the CLI missing and opens that kind's circuit for every host in the deployment (see below); and a host that has all three CLIs installed but is meant to serve only some of them has no way to say so, so it claims the kinds it was not meant to serve and takes that work away from the host that owns it.

The second half of the problem is the backend circuit. `RunnerBackendState` is keyed by `runner RunnerKind` alone — one global row per kind, with no runner or host column (`packages/db/prisma/schema.prisma:1170-1182`). Every daemon probes and reports every kind unconditionally: `probeSupportedCliAvailability` iterates the module constant `SUPPORTED_RUNNERS`, which is `RUNNER_KINDS` (`packages/runner/src/availability.ts:8,55-63`), and `runStartupPreflight` and `reportCliAvailabilityHeartbeat` loop over the same constant to report availability and preflight for all three (`packages/runner/src/runner.ts:1083-1110,1129-1156`), the heartbeat being started once per daemon at boot (`packages/runner/src/runner.ts:1159-1180`; `packages/runner/src/index.ts:78-80`). An `available: false` report is not scoped to its reporter: `recordAvailability` upserts the single row for that kind, writes the unavailable reason onto every TODO/DOING Task with a QUEUED Run of that kind through `fanOutFailureReason`, and opens an operator Inbox alert (`packages/api/src/runner-backend-health.ts:150-193,136-148`), after which `runnerBackendAllowsClaim` refuses that kind for every runner in the deployment (`packages/api/src/runner-backend-health.ts:129-131`). A host that deliberately does not install one CLI therefore opens that kind's circuit globally and blocks the hosts that do serve it — the whole deployment stops taking that kind before any claim of it is ever attempted. Declaring the served set must scope the probing so an undeclared, uninstalled CLI is never reported at all; it must not add a second state model.

Mechanical Runs are untouched by both mechanisms and must stay so. The merge executor claims through a separate principal and body (`packages/merge-executor/src/agentos.ts:126-134`), its candidates come from the other branch of the query (`packages/api/src/run-claim.ts:323-342`), the ordinary ranking query already excludes integrator output kinds, `claimantMayTake` is the final authority on who may take which mode (`packages/db/src/merge-integrator-db.ts:1117-1126`), and the backend circuit is deliberately consulted only for `executionMode === "agent"` because a mechanical Run spawns no CLI and its `runner` value is an inert artifact of the sentinel Agent (`packages/api/src/run-claim.ts:668-673`).

One parsing hazard is specific to this body. The four existing telemetry fields are wrapped in `telemetry()`, which catches a schema failure, logs `Discarded runner telemetry` and yields `undefined` (`packages/api/src/run-claim.ts:63-73`). A served-kind declaration that degraded that way would silently widen the runner back to all kinds — the exact failure this chain exists to prevent — so it must be an ordinary validated field. Finally, `/runner/*` is an internal protocol that the handbook coverage test does not require a route section for (`scripts/operator-api-docs.test.mjs:20-22`), but the handbook already documents the machine-only claim body in prose (`docs/operator-api.md:1873-1886`), and that is where the new field belongs.

Changes:
1. Add `RUNNER_SERVED_KINDS` to `loadRunnerConfig`, parsed into a new `servedKinds: readonly RunnerKind[] | null` field on `RunnerConfig`. An unset variable yields `null`, meaning every kind in `RUNNER_KINDS`. A set variable is a comma-separated list of exact `RunnerKind` names; entries are trimmed, duplicates collapse, and the result is normalized into `RUNNER_KINDS` order. A value that is set but names no kind (empty, whitespace, only separators) and any entry that is not an exact `RUNNER_KINDS` member both throw at load, naming the variable, the offending entry and the accepted names — a runner that serves nothing must refuse to start, not poll forever. Leave the `binaries` map covering all kinds.
2. Scope local probing to the declared set. `probeSupportedCliAvailability`, `runStartupPreflight` and `reportCliAvailabilityHeartbeat` iterate the config's served kinds (`config.servedKinds ?? RUNNER_KINDS`) instead of the module constant `SUPPORTED_RUNNERS`, so no availability report and no preflight report is ever sent for an undeclared kind. Remove the `SUPPORTED_RUNNERS` export and its uses rather than leaving both paths; the returned `Record<RunnerKind, …>` shapes of the probe and of `runStartupPreflight` narrow to the served kinds, and the daemon's startup log line prints only those kinds.
3. Carry the declaration on the claim. `claimRequestBody` includes `servedKinds` only when `config.servedKinds` is non-null; with no declaration the body is byte-identical to today's. `claimInput` gains an optional `servedKinds` field: an array of `RunnerKind`, at least one entry, at most `RUNNER_KINDS.length`. It must not use the `telemetry()` wrapper — an unparseable declaration is a 400, never a discarded field. The merge executor's body is unchanged.
4. Filter the ordinary-runner candidate selection by the declared set. Add the predicate to the ranking SQL, so a declared runner's `LIMIT 20` window contains only Runs it serves; putting the check only in the per-candidate loop would let twenty higher-ranked Runs of an undeclared kind consume the window and starve the work this runner exists to take. Add the same check in the per-candidate loop as the transaction-boundary guard, beside the existing backend-circuit check and under the same `executionMode === "agent"` condition, skipping the candidate rather than refusing the claim. Leave the merge-executor branch of the query and every mechanical path untouched.
5. Update `docs/operator-api.md` in the machine-only `POST /runner/tasks/claim` prose: the optional `servedKinds` array, that omitting it means every kind, that a declared claim is offered agent Runs of those kinds only, that mechanical claims are unaffected, and that an unknown kind is a 400.

Out of scope: systemd or launchd unit rendering, install and deploy scripts, and `scripts/os-isolation/*` (chain L1); `scripts/host-proof-slot.sh`, `packages/runner/src/dependency-cache.ts` reflink, default `RUNNER_PATH`, checksum tooling, and gate dispatch slot counts (chain L2); any change to how `RunnerBackendState` is keyed, including per-runner or per-host circuit state, backend health projections, or the preflight recovery lease (`packages/api/src/routes/runner.ts:112-133`); runner-side rejection of a Run whose kind it did not declare — the control plane is the sole enforcement point in this chain; `RunnerPreference`, agent routing, or how `Run.runner` is chosen at enqueue; the runner registry snapshot (`packages/api/src/runners.ts`) and any board or web surface that would display declared kinds, beyond what the named tests require; the merge executor's claim body; `docs/install.md`, `docs/release/support-matrix.md`, and any Linux support status.

Constraints: The `packages/runner/src/config.ts` edit must be minimal and additive, confined to its own block, because three chains from the same plan touch that file concurrently; do not reformat, reorder, or refactor the surrounding parsing helpers or the returned object. An undeclared runner must be indistinguishable from today's runner — same request body, same candidate ranking, same reports. A declared runner must never be handed an agent Run of an undeclared kind, including when the serializable claim transaction retries under conflict. Configuration errors fail loud at daemon startup; no bad value may degrade into "serves everything". Nothing in this chain may make a mechanical Run's claim, ranking, or completion depend on `servedKinds`. A kind that no live runner declares leaves its Runs QUEUED and untouched — not failed, and not flagged with a failure reason. The deployment intent that motivates this work — a VM declaring `CODEX,PI` and a Mac declaring `CLAUDE` — is an example of operator configuration only: no host name, host role, or specific kind combination may be hardcoded, defaulted, or special-cased in code, tests, or fixtures.

Acceptance:
1. Runner config tests prove: unset `RUNNER_SERVED_KINDS` gives `servedKinds === null`; `"CODEX,PI"` gives `["CODEX","PI"]`; `" PI , CODEX "` and `"CODEX,CODEX"` normalize to `RUNNER_KINDS` order without duplicates; and each of `""`, `" "`, `","`, `"codex"`, `"GPT"` throws an error naming `RUNNER_SERVED_KINDS`, the offending entry and the accepted names.
2. A runner test proves `claimRequestBody` omits `servedKinds` entirely when the config declares none and emits the normalized array when it declares some, with the remaining fields unchanged in both cases.
3. A runner test proves the daemon's startup log line names exactly the served set: with a declaration it prints those kinds and no others, and with no declaration it prints every kind in `RUNNER_KINDS`.
4. Runner tests prove that with `servedKinds: ["CODEX"]`, `runStartupPreflight` and one `reportCliAvailabilityHeartbeat` tick each produce exactly one availability report and at most one preflight report, both for CODEX, and none for CLAUDE or PI; with `servedKinds: null` both still report all three.
5. A named API dbtest file proves each case with a real claim over HTTP: (a) with one queued CLAUDE Run and one queued CODEX Run, a claim declaring `["CODEX"]` returns the CODEX Run and a second such claim returns 204 while the CLAUDE Run stays QUEUED with `failureReason` null; (b) with more than twenty queued CLAUDE Runs ranked ahead of one CODEX Run, a claim declaring `["CODEX"]` still returns the CODEX Run, proving the filter is applied inside the ranking window; (c) a claim omitting `servedKinds` returns the highest-ranked Run whatever its kind; (d) a merge-executor claim with its unchanged body still claims its integrator Run; (e) a claim whose `servedKinds` contains an unknown string is refused with 400 and claims no Run.
6. A concurrency dbtest proves that two claims issued concurrently against one queued CODEX Run — one declaring `["CODEX"]`, one declaring `["CLAUDE"]` — end with exactly one claimed Run, held by the CODEX-declaring caller, and the CLAUDE-declaring caller receiving no work.
7. A `runner-backend-health` dbtest proves that `POST /runner/availability` reporting CODEX unavailable from a CODEX-only runner leaves the CLAUDE `RunnerBackendState` row absent, leaves `runnerBackendAllowsClaim` true for CLAUDE, and leaves every CLAUDE-Run Task's `failureReason` null, while the CODEX Tasks receive the unavailable reason as they do today.
8. `docs/operator-api.md` documents the `servedKinds` field in the machine-only claim paragraph, and `npm run test:operator-api-docs` passes.
9. `npm run lint`, `npm run typecheck -w @anneal/runner`, `npm run typecheck -w @anneal/api`, `npm run test -w @anneal/runner` and `npm run test -w @anneal/api` are green, and no file named in Out of scope is modified.
