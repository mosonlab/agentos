Adding a repository to an existing Project is safe and complete in one call, the web Inbox and its badge show the selected Project plus global messages, and operators have a checkable end-to-end guide for running the Project's pull-request workflow.

Route: implementation=senior-dev - repository preflight must complete before the database transaction opens while Repo and AgentRepoAccess writes commit atomically, and the acceptance suite cannot witness that lock-window boundary.

Background: `POST /projects/:projectId/repos` in `packages/api/src/routes/agents.ts` currently trims and shape-validates its body, checks only that a referenced credential Secret exists and is enabled, and writes one Repo; remote safety, branch validity, reachability, default-branch existence, and push authority are discovered only after a Run starts. First-run onboarding in `packages/api/src/onboarding.ts` applies `parseRepoRemote` to the untrimmed value and accepts its complete policy: HTTPS without userinfo, SSH/scp-like remotes with no account or the `git` account, and local `file:///` remotes, while rejecting credentials, whitespace, control characters, query/fragment data, option-like values, unsupported schemes or SSH accounts, missing host/path, and overlong values. `isValidBranchName` in `packages/api/src/branch-name.ts` is the API's branch authority, and `preflightOnboardingRepository` in `packages/api/src/onboarding-preflight.ts` checks the API host's ambient Git identity, the remote and default branch, and a dry-run push. For an existing Project, `POST /agents/:agentId/repos/:repoId/access` is the only general operator API for grants, while `instantiateTemplate` in `packages/api/src/templates.ts` requires every effective step Agent to hold a Repo grant. `GET /inbox/messages` in `packages/api/src/routes/inbox.ts` has an optional four-relation Project filter, but the summary is global; `InboxPage`, `InboxThreadPage`, and `Shell` in the web app all request unfiltered Inbox data even though sender names are Project-scoped. `docs/install.md` lacks an add-project procedure.

Changes:
1. Strengthen `POST /projects/:projectId/repos` without changing `PATCH /repos/:repoId`. Preserve the submitted `remoteUrl` long enough to run the complete onboarding `parseRepoRemote` policy on the raw value before any trim or transform, deliberately applying onboarding's SSH-account restriction to this ordinary Repo route; validate the defaulted branch with `isValidBranchName`. Update the `SSH_ACCOUNT` policy comment in `packages/api/src/onboarding.ts` so it no longer claims that a self-hosted account rejected by onboarding remains accepted through the ordinary Repo route. An invalid remote returns exactly `400` with `{ "error": "Repository remote is invalid", "code": "repository-remote-invalid", "reason": <the parseRepoRemote rejection reason> }`; an invalid branch returns exactly `400` with `{ "error": "Repository default branch is invalid", "code": "repository-default-branch-invalid" }`. Neither response echoes the rejected value, neither opens the Repo/grant transaction, and neither invokes preflight. Add through `RouteDeps` an injectable preflight operation whose only input is `{ remoteUrl, defaultBranch }`, with the exact raw remote and validated/defaulted branch from the request; its release default reuses the existing Git identity, `ls-remote`, default-branch, fetch, and dry-run-push checks. The operation receives no `credentialSecretId`, never reads or decrypts that Secret, and uses the API host's ambient Git identity. It completes before the database transaction opens. A `RepositoryPreflightError` returns exactly `422` with `{ "error": "Repository preflight failed", "code": "repository-preflight-failed", "reason": <the existing failure reason> }`; other failures surface through the existing error path.
2. Add optional boolean `grantAgents`, default `false`, to that POST body. When it is `true`, create the Repo and one `GIT_WRITE` `AgentRepoAccess` for every Agent in the Project satisfying `archivedAt: null` and `name` not equal to `INTEGRATOR_AGENT_NAME`; every grant uses the created Repo's `mountPath`. Perform the Repo and all grant writes in one database transaction and return `201` with `{ repo, grants }`, where `grants` is exactly the created access rows. Any write failure rolls back the Repo and every grant. When `grantAgents` is omitted or `false`, create no grants and return the existing Repo-row `201` shape. A duplicate `(projectId, name)` continues to return the existing `409` body `{ "error": "Unique constraint violated" }`.
3. Define one shared Inbox Project predicate and use it in both `GET /inbox/messages` and `GET /inbox/messages/summary`. With `projectId`, a row is in scope when its Agent, Task, Goal, or Session belongs to that Project, or when `agentId`, `taskId`, `goalId`, and `sessionId` are all null; the latter are global rows, including history whose nullable relation was removed. The list retains its top-level-message behavior, and the summary retains its open, top-level, needs-reply behavior. With no `projectId`, both endpoints remain unfiltered by Project. In the web app, `InboxPage` and `InboxThreadPage` request `/inbox/messages?projectId=<selected Project>` and `Shell` requests `/inbox/messages/summary?projectId=<selected Project>`; all three use the current unfiltered path when no Project is selected.
4. Add `docs/runbooks/add-a-project.md` for only the pull-request workflow delivered by A1. It gives literal operator API commands to create a Project with `POST /projects`, explains that A1 creates its `local` Environment, four workflow Agents, and `pr-engineer-workflow`, adds a Repo with `grantAgents: true`, obtains the created Repo and template ids, and instantiates that template with a body containing `repoId` and `variables: { branchName }`; it ends with the operator reviewing and merging the resulting pull request by hand. State the runtime prerequisites: a supported GitHub remote, authenticated `gh`, and installed, authenticated Codex, Pi, and Claude Code runtimes for the four A1 roles. Add a dedicated include for the runbook to `public-snapshot.json`; link it from `docs/install.md`; and add under README `## Status` a Markdown link with visible text `Add a project` and target `docs/runbooks/add-a-project.md`.
5. Update `docs/operator-api.md`: the Repo POST section documents the raw remote and branch validation policies, the exact `400`, `409`, and `422` bodies, ambient credential/preflight semantics, `grantAgents`, and both `201` response shapes; the Inbox list and summary sections document `projectId`, the shared Project-plus-global scope, and no-parameter behavior. Extend `scripts/operator-api-docs.test.mjs` with content assertions for these route contracts and the runbook, install-document, README, and snapshot-manifest requirements in Change 4.

Out of scope: a Repo-creation or grant UI; changes to A1's `POST /projects` bootstrap operation, four Agents, or `pr-engineer-workflow`; `POST /onboarding`; Secret creation or grants; changes to `credentialSecretId` validation; `PATCH /repos/:repoId`; changes to the checks performed by repository preflight; Inbox message detail, reply, decision, or close routes; new Inbox relations; database schema migrations; installation of any additional template or delivery infrastructure.

Constraints: this brief runs only after A1 is delivered and depends only on A1's Project bootstrap creating `senior-dev-luna`, `review-coordinator-sol`, `review-coordinator-opus`, and `senior-dev`, its canonical `pr-engineer-workflow`, and that template's required `branchName` variable. No Prisma schema change. Callers that omit `grantAgents` and submit a remote accepted by the newly adopted policy retain the Repo-row response shape. Refusal bodies never echo a remote. A preflight that cannot run is a refusal or surfaced error, never a skipped check or success fallback. Repo and grant atomicity may not change the existing duplicate-name collision response.
