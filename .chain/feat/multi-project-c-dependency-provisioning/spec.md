Each repository has an explicit dependency-provisioning policy that operators set and every run enforces without inference or fallback.

Route: implementation=senior-dev - the change combines a schema migration with an API-to-runner claim-contract change whose version-skew behavior the acceptance suite can witness only partly.

Background: `Repo` in `packages/db/prisma/schema.prisma` currently records the remote, mount, default branch, and credential but no dependency policy. In `registerAgentsRoutes` in `packages/api/src/routes/agents.ts`, `repoInput` defaults several existing properties, `repoPatch` is its partial form, and `RepoResponse` comes from `packages/db/src/wire-contract.ts`; consequently the POST and PATCH routes cannot distinguish a repository that needs npm from one whose dependencies belong to its task. Chain B will have strengthened `POST /projects/:projectId/repos` with raw-remote validation, an injectable repository preflight, `grantAgents`, exact `400`/`409`/`422` bodies, and bare-Repo versus `{ repo, grants }` `201` shapes. Those properties are inputs to this chain as delivered by chain B, not contracts to redesign. `claimRun` in `packages/api/src/run-claim.ts` includes `repo: true` and returns `candidate.repo` through `POST /runner/tasks/claim` in `packages/api/src/routes/runner.ts`, while `ClaimedTask.repo` in `packages/runner/src/api.ts` and `WorkspaceProvisionClaim` in `packages/runner/src/workspace.ts` hand-write the runner side of that contract. `provisionWorkspace` currently calls `materializeWorkspaceDependencies` unconditionally. In `packages/runner/src/dependency-cache.ts`, `inspectDependencyProject` infers applicability from root `package.json`; `deriveDependencyCacheKey` requires `package-lock.json`; and `materializeWorkspaceDependencies` reports `root-package-manifest-missing` as not applicable or runs the existing `npm ci --prefer-offline --no-audit --no-fund` path. Production has exactly three Repo rows, all in the Anneal Example Project: `agentos` with `remoteUrl` `https://github.com/mosonlab/agentos.git` (the Anneal repository under its pre-rename GitHub name; the GitHub redirect to `mosonlab/anneal` still resolves it), `vibeville` with `remoteUrl` `https://github.com/mosonlab/vibeville.git`, and `word-factory` with `remoteUrl` `https://github.com/mosonlab/word-factory.git`.

Changes:
1. Add Prisma enum `DependencyProvisioning` with exactly `NONE` and `NPM_CI`, and add required `Repo.dependencyProvisioning` in `packages/db/prisma/schema.prisma` with no default. One migration under `packages/db/prisma/migrations` creates the enum and column, backfills, and makes the column non-null without leaving a database default. Its deterministic Anneal predicate is a case-insensitive `remoteUrl` path suffix matching either `mosonlab/agentos` or `mosonlab/anneal` (the repository's pre-rename and current GitHub names), accepting the ordinary HTTPS, SSH URL, and scp-like forms and an optional `.git`; matching rows become `NPM_CI` and every other existing Repo becomes `NONE`. Thus the production `agentos` row becomes `NPM_CI` while the `vibeville` and `word-factory` rows become `NONE`. Every typed Repo construction site or fixture required by the new non-null Prisma input must supply an explicit value; none may acquire a fallback.
2. Extend `repoInput`, `repoPatch`, `RepoResponse`, and the Repo handlers in `packages/api/src/routes/agents.ts` so `dependencyProvisioning` is required on `POST /projects/:projectId/repos`, optional and editable on `PATCH /repos/:repoId`, and present in GET list rows, PATCH responses, chain B's bare-Repo `201`, and chain B's `{ repo, grants }` `201` under `repo`. Missing or unknown POST values, and unknown PATCH values, return exactly `400` with `{ "error": "Repository dependency provisioning is invalid", "code": "repository-dependency-provisioning-invalid" }`; PATCH omission means no change. Preserve, as delivered by chain B, its raw `remoteUrl` policy, `grantAgents` behavior, duplicate-name `409`, other preflight `422` bodies, transaction boundary, and both `201` shapes.
3. Extend the chain-B repository preflight in `packages/api/src/onboarding-preflight.ts` and its Repo-route integration with the submitted `dependencyProvisioning`. For `NPM_CI`, it must prove that the exact fetched default-branch commit contains a regular root `package-lock.json`. The proof must reuse the commit from the existing depth-one fetch used for the dry-run-push probe, add no second fetch or clone, and refuse a missing or non-blob path before the dry-run push with exactly `422` and `{ "error": "Repository preflight failed", "code": "repository-package-lock-missing", "remedy": "Commit package-lock.json at the repository root on the default branch, or choose dependencyProvisioning NONE." }`. For `NONE`, omit only this dependency-specific check; all chain-B remote, branch, identity, reachability, and push-authority checks still apply.
4. Carry the persisted field across the claim boundary: `claimRun` in `packages/api/src/run-claim.ts` must include it in `candidate.repo`, `ClaimedTask.repo` in `packages/runner/src/api.ts` must require it, and `WorkspaceProvisionClaim.repo` in `packages/runner/src/workspace.ts` must retain it through `executeClaim` and `provisionWorkspace`. A post-C runner receiving a claim with the property absent or outside `NONE | NPM_CI` must refuse before workspace provisioning or adapter launch, complete the claim non-retryably as `PROTOCOL_ERROR`, and expose condition `dependency-provisioning-missing`; it must never coerce that skew to either enum value.
5. Make `materializeWorkspaceDependencies` in `packages/runner/src/dependency-cache.ts` consume the required declaration. `NONE` returns `{ status: "not-applicable", condition: "dependency-provisioning-none" }` and emits the same dependency-cache progress report form used for `root-package-manifest-missing`, without calling `inspectDependencyProject`, probing Node/npm, reading package manifests, restoring a cache entry, or invoking npm. `NPM_CI` follows the existing code path with behavior unchanged, including cache identity and integrity rules, reports, retry and timeout semantics, the `root-package-manifest-missing` result, and the exact install command.
6. Update the Repo POST and PATCH sections of `docs/operator-api.md` to document the required/patchable field, `NONE` and `NPM_CI`, `repository-dependency-provisioning-invalid`, and the POST-only `repository-package-lock-missing` body and remedy. In `docs/runbooks/add-a-project.md` as delivered by chain B, add `"dependencyProvisioning": "NPM_CI"` to the literal Repo POST body and one line saying to choose `NPM_CI` only for repositories whose default branch has a root `package-lock.json`, otherwise `NONE`. Extend `scripts/operator-api-docs.test.mjs` with content assertions for these exact handbook and runbook facts.

Out of scope: any third enum value; a custom setup command; Python or any other package-manager provisioning; a web UI for this field; changes to dependency-cache keying, target selection, cache format, or install command; removal of word-factory's existing `package-lock.json`; changes in D1/D2/D3 territory, including runner-shipped regression scripts, canonical templates, or `DEFENSE_EXACT`; any request, response, preflight, or documentation change to `POST /onboarding`.

Constraints: There is no default in the API, Prisma schema, database column, claim decoder, workspace contract, or runner. Every creation and test fixture states `NONE` or `NPM_CI` deliberately. Unknown and missing values fail loudly; they are never inferred from repository contents, `package.json`, Project identity, or historical behavior. The B-delivered POST contract remains otherwise exact. The `NPM_CI` path is behaviorally byte-for-byte identical to the pre-C path, while `NONE` performs no dependency provisioning at all. The fixed R2 card shape must not be recreated: a manifest without a lockfile is valid under `NONE`, and language dependencies under `NONE` remain the task's responsibility. Schema-compilation adjustments to existing internal Repo writers must not add the field to the `POST /onboarding` contract or change that route's observable behavior.
