Templates: A template step can be optional and a project can skip optional steps

A `TaskTemplateStep` can be marked optional, a project carries one boolean that decides whether optional steps are instantiated, and a project with that switch on runs the canonical direct and compound chains without their blind review step while every downstream step, output contract, and chain projection stays coherent.

Route: implementation=senior-dev - omitting a step changes two cross-module contracts that no single-module suite witnesses: the claim-time prior-output gate that parks a task when a declared kind is absent (`packages/api/src/run-claim.ts:809-825`) and the mechanical `fixed-implementation` completion contract that today hard-requires exactly one blind-findings sibling and indexes `reports[1]` unconditionally (`packages/api/src/canonical-task-output.ts:245-278`); a wrong cut there does not fail the diff, it parks or rejects a live chain in its merge tail.

Background: This brief was researched against `main` commit `9809558fabf7a74057ad8922d1f3bc39fdd3f816`.

A template's execution graph is `TaskTemplateStep` rows: `stepIndex`, `layer`, `outputKind`, `priorOutputKinds`, `attachmentsFromPrevious`, `baseFromStepIndex`, `approvalGate` and the rest (`packages/db/prisma/schema.prisma:511-539`). Canonical templates are not authored through the API; their structure lives in Markdown frontmatter under `agents/templates/<name>/` and `packages/db/src/template-sources.ts` is the live authority for each template's file count, contiguous step indexes, layer vector and accepted frontmatter keys (`agents/README.md:44-52`). `STRUCTURAL_FIELDS` is an exact-match key list — a frontmatter document whose sorted keys are not exactly that list is refused (`packages/db/src/template-sources.ts:54-67,204-208`), so a new structural field appears in every canonical step file of every template, not only the ones it is set on.

Instantiation is a single choke point. `instantiateTemplate` (`packages/api/src/templates.ts:251`) is called by the operator instantiate route (`packages/api/src/routes/templates.ts:216`), the manual/webhook fire paths (`packages/api/src/routes/templates.ts:145,413`) and the test fixture (`packages/api/src/parallel-review-fixture.ts:186,221,250`). Merge-tail repair tasks are not template instantiations at all — they are chain-detached tasks built directly with their own prior-output kind list (`packages/api/src/merge-tail-actions.ts:606-634`), so this brief does not reach them.

Conditional omission already exists and is the mechanism to extend. On `direct-engineer-workflow`, an unbound instantiation drops the `revalidation` step: `conditionalRevalidation` is found by output kind, `omitRevalidation` is true when there is no `afterTaskId`, and `instantiatedTemplateSteps` is `template.steps` minus that row; an empty result is refused with `template_has_no_instantiable_steps` (`packages/api/src/templates.ts:366-374`). The task-creation loop then writes `chainIndex: step.stepIndex - conditionalOrdinalOffset` and `chainLayer: step.layer - conditionalOrdinalOffset`, where the offset is `1` exactly when the revalidation row was dropped (`packages/api/src/templates.ts:638-665`). That constant offset is correct only because the dropped row is the first step in the first layer; it is not a general renumbering scheme, and it is the one piece of the existing path that assumes only step 1 can be missing.

Renumbering is, however, not required. Sparse chain coordinates are already first-class: `chainProgress` computes `total` as the row count and not `max(chainIndex) + 1` precisely so that "a template with sparse step indices would otherwise read step 9 of 3" cannot happen, and it derives the layer ordinal with `denseOrdinals`, documented as tolerating layers that are "sparse, zero-based, or one-based" (`packages/api/src/chain.ts:88-118`). `denseOrdinals` ranks the distinct layer values present in the actual rows (`packages/db/src/chain-order.ts:47-52`), and the same helper is the layer authority for chain execution control (`packages/db/src/chain-control.ts:384`) and for the console's chain view grouping (`apps/web/src/components/chain-list.tsx:112-116`). Ordering itself is `compare` over effective layer, then index, then id (`packages/db/src/chain-order.ts:39-43`) — none of it requires contiguity. Within the loop, `targetBranch: index === 0 ? repo.defaultBranch : branchName` and the `dispatchAfterTaskId` binding key off the position in `effectiveSteps`, not `stepIndex` (`packages/api/src/templates.ts:661-664`), and the first-step-is-an-agent check reads `effectiveSteps[0]` (`packages/api/src/templates.ts:632-635`). So an omitted step can simply not become a Task, leaving a gap in `chainIndex`.

Three readers resolve an exact ordinal rather than a relative one, and a gap changes what they see. `run-completion.ts` re-queues a documentation step after a regression repair only when the regression task's `chainIndex` and its `templateStep.stepIndex` both equal the canonical regression ordinal, then finds the documentation task by both `chainIndex` and `stepIndex` (`packages/api/src/run-completion.ts:804-825`, ordinals from `packages/db/src/canonical-template-transition.ts:493`); keeping the template `stepIndex` as the `chainIndex` is exactly what preserves that equality, and renumbering would silently disable the branch for every step after an omission. `merge-base-drift-worker` reads its predecessor as `chainIndex: task.chainIndex - 1` (`packages/api/src/merge-base-drift-worker.ts:141`) and the integrator's predecessor-activity route addresses only `ownIndex` and `ownIndex - 1` (`packages/api/src/routes/session.ts:217-226`); both are exercised in the merge tail, whose steps are never optional in this chain, but neither tolerates an omitted immediate predecessor. `baseFromStepIndex` is the one reference that is already omission-aware: `pinnedImplementationRange` resolves it through `templateStep: { stepIndex: … }` and not `Task.chainIndex`, with a comment saying conditional instantiation may omit an earlier step (`packages/db/src/run-open.ts:278-294`); a missing referenced task throws `PinnedBaseCommitError`, which the claim path turns into a `candidate-activation-failed` park (`packages/api/src/run-claim.ts:782-794`).

One console surface reads a raw index: `chainStepPosition` falls back to `frontier.chainIndex + 1` without the clamp its last-resort branch applies (`apps/web/src/lib/chain-aggregate.ts:80-88`), so a sparse chain would show a frontier step number above the aggregate's `stepCount` (itself a row count, `packages/api/src/board.ts:440`). Separately, the new-task panel already advertises `template.steps.length` and previews every step without accounting for the existing revalidation omission (`apps/web/src/components/new-task-panel.tsx:249,290`); that desynchronization predates this work.

Two consumers do not tolerate a gap at all, and both are about the blind review specifically.

First, the claim-time prior-output gate. `run-claim` reads `templateStep.priorOutputKinds` — there is no per-task copy — collects the matching `TaskStepOutput` rows from earlier `chainIndex` values in the same chain, and if any declared kind produced no row it parks the task in Backlog with `PRIOR_OUTPUT_MISSING_REASON` and raises an operator Inbox item (`packages/api/src/run-claim.ts:795-832`). In the direct template, step 5 declares `[sol-findings, blind-findings]` and step 6 declares `[implementation, sol-findings, blind-findings, fixed-implementation]` (`agents/templates/direct-engineer-workflow/05-apply-review-fixes.md`, `06-regression-verification.md`); the compound template's steps 8 and 10 declare the same pairs (`agents/templates/compound-engineer-workflow/08-apply-review-fixes.md`, `10-regression-verification.md`). Omitting step 4 therefore parks step 5 today. The blind step itself is exempt from the whole lookup (`blindReviewTask` at `packages/api/src/run-claim.ts:795,800`).

Second, the mechanical `fixed-implementation` completion contract. It locates the review layer as the greatest `chainLayer` below the fix step, reads every task in that layer, and then requires, for each of `sol-findings` and `blind-findings` in turn, exactly one matching sibling with an immutable output backed by a successful run — otherwise `fixed-implementation requires exactly one immutable <kind> sibling output` (`packages/api/src/canonical-task-output.ts:198-268`). It then compares `reports[0]!.reviewedBase !== reports[1]!.reviewedBase` with no arity check (`packages/api/src/canonical-task-output.ts:276-278`), so a one-report chain would compare against `undefined`. This contract, not the prompt, is what makes the fix step's output acceptable.

The prompts assume two reports as well. Every canonical file that names the blind review or demands both reports is `agents/templates/direct-engineer-workflow/04-code-review-opus-blind.md`, `05-apply-review-fixes.md`, `06-regression-verification.md`; `agents/templates/compound-engineer-workflow/07-code-review-opus-blind.md`, `08-apply-review-fixes.md`, `10-regression-verification.md`; `agents/templates/pr-engineer-workflow/03-code-review-opus-blind.md`, `04-apply-review-fixes.md`; and the role file `agents/roles/review-coordinator-opus.md`.

The project-level switch has an exact precedent to mirror and must not grow a second mechanism. `specGateDefault` and `mergeGateDefault` are two `Boolean @default(false)` columns on `Project` (`packages/db/prisma/schema.prisma:240-241`) added by a purely additive migration (`packages/db/prisma/migrations/20260901020000_project_gate_defaults/migration.sql:1-3`); they are in the shared wire contract (`packages/db/src/wire-contract.ts:72-73`), which the console re-exports rather than redeclaring (`apps/web/src/lib/types.ts:58`); they are writable through `projectPatch` and not through the create input (`packages/api/src/routes/admin.ts:27-31`, `packages/api/src/project-bootstrap.ts:17-29`); they are read under the project row mutex inside the instantiation transaction (`packages/api/src/templates.ts:166-176,317`, `packages/db/src/locks.ts:48-58`); and the console renders one `Toggle` per column with a single-key PATCH (`apps/web/src/pages/Projects.tsx:157-163,196-203`).

Changes:

1. No backfill, no constraint, no data migration: every existing row is non-optional.

2. Add `skipOptionalSteps Boolean @default(false)` to `Project` in the same migration file, as one further `ALTER TABLE "Project" ADD COLUMN`. Add it to the `Project` wire contract in `packages/db/src/wire-contract.ts`; do not add it to `projectFields`/`projectInput` in `packages/api/src/project-bootstrap.ts`, so creation relies on the database default exactly as the gate defaults do. Add it to `projectPatch` in `packages/api/src/routes/admin.ts` so `PATCH /projects/:projectId` writes it, and extend `lockProjectGateDefaults` in `packages/db/src/locks.ts` to select it under the same `FOR UPDATE`, so the instantiation transaction reads it under the same row mutex that serialises it against a concurrent PATCH. Do not introduce a second project-configuration mechanism, a per-template setting, or a per-instantiation override.

3. Expose `optional` on the template read and write surfaces. Add it to `TaskTemplateStep` in `packages/db/src/console-contract.ts`; add a required `optional: z.boolean()` to `replaceTemplateStepInput` in `packages/api/src/routes/templates.ts` (the object is `.strict()` and every other structural field is required — keep that shape rather than defaulting it, and update the handbook's curl example and any authoring fixture in the same change); carry it through the authoring step type and the replace write in `packages/api/src/template-authoring.ts`; and render it in the console's template step preview in `apps/web/src/components/new-task-panel.tsx` as a per-step marker beside the existing gate marker, with new `en`/`zh` locale keys. No other template UI.

4. Add four authoring validator refusals in `packages/api/src/template-authoring.ts`, each `422` with a stable code and the offending `stepIndex`, consistent with the existing validator refusals: `first_step_optional` when step 1 is optional (the first instantiated step is the chain entry point and carries the `afterTaskId` binding and the default-branch target); `base_step_optional` when any step's `baseFromStepIndex` names an optional step (a retained step must never pin its base to a step that may not exist); `gate_slot_step_optional` when an optional step occupies the specification or merge-readiness gate slot as decided by `gateSlotOf` (`packages/db/src/gate-slot.ts:14-18`), because the `gates_spec_step_absent` / `gates_merge_step_absent` refusals and the three-layer gate resolution both address a slot that must be present; and `optional_step_precedes_merge_tail` when an optional step's `stepIndex + 1` names a step whose `outputKind` is `merge-authorization` or `merge-result`, because those two steps resolve their predecessor by exact `chainIndex - 1` (`packages/api/src/merge-base-drift-worker.ts:141`, `packages/api/src/routes/session.ts:217-226`) and must never face a gap.

5. Add `optional` to `STRUCTURAL_FIELDS`, to the parsed step type, and to the field-by-field drift comparison in `packages/db/src/template-sources.ts`, parsed with the existing boolean parser. Because the frontmatter key set is an exact match, add `optional:` to the frontmatter of every canonical step file in all three templates — 8 files under `agents/templates/direct-engineer-workflow/`, 12 under `agents/templates/compound-engineer-workflow/`, 4 under `agents/templates/pr-engineer-workflow/` — set to `true` only on `agents/templates/direct-engineer-workflow/04-code-review-opus-blind.md` and `agents/templates/compound-engineer-workflow/07-code-review-opus-blind.md`, and `false` everywhere else including `agents/templates/pr-engineer-workflow/03-code-review-opus-blind.md`. Add the key to the template step frontmatter block in `agents/README.md`. Enforce the same four rules of item 4 inside `template-sources.ts`'s canonical validation, so a canonical source that violates them fails at load.

6. Skip optional steps at instantiation through the existing omission mechanism in `packages/api/src/templates.ts`. Read the project's `skipOptionalSteps` alongside the gate defaults under the same lock, and extend the filter that produces `instantiatedTemplateSteps` so it drops both the conditional revalidation row and, when the switch is on, every step with `optional: true`; keep `template_has_no_instantiable_steps` as the refusal when nothing remains. Retained steps keep their original `stepIndex` and `layer` values: `chainIndex` and `chainLayer` are written exactly as today, `conditionalOrdinalOffset` keeps its current meaning and value, and an omitted step leaves a gap in `chainIndex` rather than triggering a renumbering. Do not add a general renumbering scheme. `stepOverrides` and the `Route:` line continue to validate against `template.steps` (all steps), so naming an omitted step is not a new refusal; a resolved override for an omitted step simply has no task.

7. Make the claim-time prior-output gate tolerant of a kind whose only producer was omitted, and only that. In `packages/api/src/run-claim.ts`, before the missing-kind park, resolve the set of `outputKind` values declared by the task's template's steps that have no task in this chain, and treat a declared prior kind in that set as satisfied by absence. A declared kind whose producing step does exist in the chain but has not produced its output keeps today's behavior exactly: the task is parked with the same reason, activity, and Inbox item. Absence-by-omission must never be an error and must never be logged as a failure; a chain that omits nothing must take a byte-identical path.

8. Make the mechanical `fixed-implementation` contract validate against the review siblings actually present. In `packages/api/src/canonical-task-output.ts`, require exactly one immutable, run-backed output for each of `sol-findings` and `blind-findings` whose step is present in the review layer, and treat a review kind with zero matching sibling tasks in that layer as not required; keep every existing refusal string and check for a kind whose sibling is present. Replace the unguarded `reports[0]`/`reports[1]` reviewed-base comparison with one that requires all present reports to agree on `reviewedBase` and holds trivially for a single report. The disposition-coverage check already derives its source ids from the collected reports and needs no arity assumption. At least one review sibling must remain: zero present review outputs is a refusal, not an empty pass.

Constraints: A project with `skipOptionalSteps` false must be byte-identical to today on every path — same request bodies, same chain rows, same `chainIndex`/`chainLayer` values, same prior-output query, same completion refusals, same prompts for steps that are not the four named in item 9. The skip decision is resolved once, inside the instantiation transaction, under the project row mutex, and is never re-derived afterwards: a chain already created is unaffected by a later PATCH, exactly as the gate defaults are. Failures stay loud: the only tolerance added anywhere is "this kind's producing step has no task in this chain"; every other missing output, missing sibling, malformed report, or unknown field keeps its current refusal, code, and operator Inbox behavior, and no code path may fall back to "skip the check" when it cannot determine whether a step was omitted. Sparse `chainIndex` is a supported state, not a defect to be repaired: no code added by this chain may assume contiguity, and none may renumber existing rows. The invariant this chain preserves in place of contiguity is that a retained task's `chainIndex` equals its template step's `stepIndex` minus the existing revalidation offset, so `run-completion`'s documentation rollover keeps matching on both fields and `pinnedImplementationRange` keeps resolving through `stepIndex`. The two schema columns land in one migration; a migration chain must not run concurrently with another migration chain, so this chain is dispatched only when no other migration-bearing chain is in flight. Write-surface overlap with the five chains now in flight is limited to `docs/operator-api.md`, which `feat/runner-served-kinds` also edits — this brief only appends to the Projects and task-template sections and must not reformat, reorder, or touch the `POST /runner/tasks/claim` prose; no other file in this brief is touched by `feat/linux-systemd-deploy`, `feat/runner-linux-portability`, `feat/gate-dispatch-local-slots`, `feat/runner-served-kinds`, or `feat/codex-in-run-resume`.
