Gate: A host contributes a configurable number of local gate slots, tried before its remote workers

An operator can give one machine more than one local merge-gate slot and have a Run's Regression step use that capacity ahead of an ssh worker, without inferring from a hostname whether the configured gate server is this machine.

Route: implementation=senior-dev - gate slots are a lock-ownership window that meters how much of one machine concurrent gates may occupy; a leftover slot name, an off-by-one count, or a round that takes a local slot before releasing a remote one lets two gates spend one gate's worth of host, and every dispatcher fixture still passes.

Background: This brief was researched against `main` commit `9a52c6ada5cea5a309e53d87912dd33c5249fae5` on 2026-09-03. Every citation below was read on that commit; locate them by name if lines shift. It is a sibling of `BRIEF-runner-linux-portability-20260903.md`, which owns the runner's other Linux portability items and touches none of the files named here; the two chains can land in either order.

Gate capacity is rationed by named lock files under `${XDG_CACHE_HOME:-~/.cache}/gate-dispatch/`, outside any repository because the slots belong to the machines rather than to a checkout (`packages/runner/runtime-tools/gate-worker/gate-dispatch.sh:20-28,88`). An explicitly configured primary worker contributes two slots and a fallback worker one; the local machine contributes exactly one, named `local`, and only with `--allow-local` or `AGENTOS_GATE_ALLOW_LOCAL=1`, tried after both remote workers (`gate-dispatch.sh:12-18,164-170,394-425`). None of those counts is configurable: `PRIMARY_SLOTS` is a literal array and the local slot is a bare literal. `gate_slot_try` distinguishes a busy slot from a lock that cannot be operated at all, and that distinction decides whether the dispatcher waits or reports no verdict (`gate-dispatch.sh:52-69,262-272`); slot names are ordinary strings in that accounting (`scripts/gate-worker/gate-dispatch.test.mjs:81-158`).

What a Run gets today is one remote slot and no local capacity. `AGENTOS_GATE_SERVER` collapses the dispatcher to a single remote worker with a single slot (`gate-dispatch.sh:80-84,164-170`), and that is exactly what the runner sets: it validates `RUNNER_GATE_SERVER` as an ssh destination (`packages/runner/src/config.ts:110,137`), exports it as `AGENTOS_GATE_SERVER` into the session (`packages/runner/src/adapters/environment.ts:22-45`), forwards it across the run-as boundary (`packages/runner/src/adapters/runtime.ts:252-256`) and protects it from task Secrets (`packages/runner/src/adapters.ts:40-41`). There is no runner-owned way to ask for local capacity.

A local dispatch is not an ssh path and never was: it runs `scripts/merge-gate.sh` in the workspace directly (`gate-dispatch.sh:314-317`), which the Regression step is authorised to do — it dispatches under `AGENTOS_RUN_SCOPE_BYPASS=regression-verification` (`packages/runner/runtime-tools/regression-verification.sh:519-520`), the one credential `scripts/merge-gate.sh:169-184` accepts inside a Run. So "run locally instead of over ssh" needs no new transport, only capacity the operator can state. Two concurrent local gates are already a supported shape: the merge gate binds its throwaway PostgreSQL to a loopback ephemeral port and names its container by pid (`scripts/merge-gate.sh:33`, `:191`), and a gate worker already runs two at once when its worker-capacity file says 2 (`packages/runner/runtime-tools/gate-worker/run-gate.sh:47-52,190`). The remaining ordering fact is economic: a local gate needs neither the mirror push nor the ssh round trip that a remote attempt takes first (`gate-dispatch.sh:321-342`), so with local capacity configured, trying remote workers first leaves the cheaper slots idle.

The alternative design — deciding locality by comparing the configured `RUNNER_GATE_SERVER` against this machine's hostname, ssh aliases or addresses — is rejected: it is a heuristic whose wrong answer silently sends a gate to the wrong host or spends a slot that does not exist, and the dispatcher already has an explicit local mode to configure instead.

Changes:
1. Make local gate capacity configurable in `packages/runner/runtime-tools/gate-worker/gate-dispatch.sh`: `AGENTOS_GATE_LOCAL_SLOTS` (default 1) sets how many slots the local machine contributes when local dispatch is enabled, named `local-1` … `local-N` under the existing slot root. A non-numeric or zero value is a usage error reported on the same path as `--timeout-minutes` and `GATE_DISPATCH_POLL_SECONDS` (`gate-dispatch.sh:172-174`). This is a one-cut rename: the bare `local` slot name is removed, not kept as an alias. The busy/broken distinction, the round accounting, and the 75-versus-76 exit contract (`gate-dispatch.sh:52-69,363-458`) are unchanged; each `local-N` slot participates in them exactly as the single `local` slot did. The startup capacity line prints the literal `local(1, explicit)` today (`gate-dispatch.sh:308`) and must print the configured count instead, so an operator reading a Run's gate log can tell how much capacity that dispatch actually had.
2. Try local slots before remote workers in each dispatch round whenever local dispatch is enabled, rather than after both workers (`gate-dispatch.sh:394-425`). Local eligibility — HEAD at the requested commit and a clean tree (`gate-dispatch.sh:290-297`) — and the explicit opt-in are unchanged: the local machine still contributes nothing unless asked, and an ineligible local machine still falls through to the workers rather than occupying a slot. Update the header comment (`gate-dispatch.sh:12-18,30-33,415-416`) and `docs/runbooks/gate-worker.md:104-116,296-308` to state the new order and the new variable.
3. Let a Run reach that capacity: add `RUNNER_GATE_LOCAL_SLOTS` to `packages/runner/src/config.ts` beside `RUNNER_GATE_SERVER` (`:110,137`), validated as a positive integer and refused loudly otherwise. When it is set, `packages/runner/src/adapters/environment.ts:22-45` exports `AGENTOS_GATE_ALLOW_LOCAL=1` and `AGENTOS_GATE_LOCAL_SLOTS`; both names are added to `COMMON_LAUNCHER_ENVIRONMENT` (`packages/runner/src/adapters/runtime.ts:252-256`) so they survive the run-as boundary, and to `COMMON_PROTECTED_SECRET_ENVIRONMENT` (`packages/runner/src/adapters.ts:40-41`) so a task Secret can neither set nor raise them. Unset means today's behaviour exactly: no local slot and neither variable in the child environment. Document the setting beside `RUNNER_GATE_SERVER` in `.env.example:66-70` as a commented optional value.

Constraints: the new variables are inert when unset, so an existing deployment that does not set them dispatches exactly as it does today, with no local slot and no new environment entry — this is the property that lets the chain land before the host it was written for exists. Replacement is one cut: no `local` alias, no dual-read of an old and a new name, no compatibility path for a leftover `local.slot` file. An invalid count fails loud as a usage error before any lock is touched; nothing silently clamps, rounds, or falls back to 1. Capacity is stated by configuration and never inferred from a hostname, alias, or address comparison. The dispatcher must remain the only writer of its slot accounting: a local gate still runs `scripts/merge-gate.sh` in the workspace, under the caller's environment, so the Regression step's bypass keeps authenticating exactly as it does now. `packages/runner/src/config.ts` is written concurrently by two sibling chains — `BRIEF-runner-linux-portability-20260903.md`'s default `PATH` branch and L3's served-kinds setting — so this chain's edit there is minimal and additive: add the parser and the new field as their own block beside `RUNNER_GATE_SERVER`, with no reformatting, no reordering of the returned object, and no rewrite of an existing parser. Landing order between the three chains must not matter: nothing here depends on another chain's line numbers.
