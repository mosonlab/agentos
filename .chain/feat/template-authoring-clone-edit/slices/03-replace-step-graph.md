# 03: Atomic whole-graph replace with in-use and canonical guards

**What to build:** An operator calls `PUT /projects/:projectId/task-templates/:templateId/steps` with `{ "steps": Step[] }` (every step field except `stepIndex`; `baseFromStepIndex` names a 1-based position in the submitted array) and receives `200 { "template", "warnings" }` where `template` is the read-route projection with dense server-assigned `stepIndex` 1..n and `warnings` is an array (empty until slice 07 adds warning rules). Add, remove, reorder and per-field edit are all this one call; the old step rows are deleted and the new ones created in one Serializable transaction that first takes a row lock on the `TaskTemplate` row through a new template-row lock helper placed with the platform's other lock helpers (and added to the documented lock order ahead of Task rows). Inside that locked transaction the route refuses `template_not_in_project` (404), `template_canonical` (409, name resolves through the canonical identity registry), and `template_in_use` (409, any Task references the template or one of its steps, with a message that says to clone again); the in-use count happens under the lock. The graph validator module is created here as a pure function over the normalized graph plus resolved Agent facts, returning the first error or the full warning list, with the spec's fixed check order laid out and `graph_empty` implemented (later slices insert their checks at their spec positions; agent facts are read by id inside the transaction so the validator can see other-project agents). The request schema bounds the payload: at most 64 steps, step names bounded like template names, prompts bounded like the existing large-text inputs, `spawnPolicy` null or object. A shared dbtest fixture helper (project, environment, several Agents including one named `merge-integrator`, a Repo with grants, a non-canonical template, and request helpers for clone, replace and instantiate) is created here for slices 04 to 08 and 10 to reuse. The handbook gains the route entry with the fields, `200` shape, the three refusal codes and `graph_empty`, and a `curl` example.

**Blocked by:** 01-authoring-refusal-envelope

- [ ] Submitting a graph that adds a step, removes a step, and reorders the remaining steps yields `200` with `stepIndex` 1..n in array order, and reading the template back shows exactly the submitted steps; verified by a new authoring replace dbtest at the HTTP seam.
- [ ] An edit of each editable field (`name`, `assigneeType`, `assigneeAgentId`, `prompt`, `outputKind`, `priorOutputKinds`, `layer`, `approvalGate`, `opensPullRequest`, `baseFromStepIndex`, `attachmentsFromPrevious`, `requiresCommit`, `spawnPolicy`, `runner`) round-trips through replace and read-back, including `spawnPolicy: null`; verified by the same dbtest.
- [ ] `baseFromStepIndex` follows array positions: a reorder that moves the base step changes the persisted `baseFromStepIndex` to the new position without the caller renumbering; verified by the same dbtest.
- [ ] A template in another project answers `404 template_not_in_project`; a template named `compound-engineer-workflow` and one named by the legacy-name helper both answer `409 template_canonical`; after one instantiation a structural replace and a prompt-text-only replace both answer `409 template_in_use` with a message naming clone as the recovery; in every refusal the step rows are byte-identical to before; verified by the same dbtest.
- [ ] `{ "steps": [] }` answers `422 graph_empty` and leaves the graph untouched; a 65-step payload or an over-long prompt is a `400` request-schema rejection; verified by the same dbtest.
- [ ] A successful replace persists nothing but template and step rows (no warning rows, no activity rows, no Task rows); verified by row counts in the same dbtest.
- [ ] The handbook documents `PUT /projects/:projectId/task-templates/:templateId/steps` with request fields, the `{ template, warnings }` response, `404`/`409`/`422` codes and a `curl` example, and the sentence claiming there is no create-template route is removed; verified by reading the section (automated assertion lands in slice 10).
