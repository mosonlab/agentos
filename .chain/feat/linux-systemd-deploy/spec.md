Deploy: Anneal services install and deploy as systemd units on Linux

Deploy tooling renders, installs, health-probes, restarts and rolls back the full service inventory as system-level systemd units on Ubuntu 24.04, and the os-isolation scripts provision and verify the same runner accounts there, while the macOS/launchd path stays byte-identical and is selected by runtime platform detection.

Route: implementation=senior-dev - the change installs privileged system units and a sudoers grant on a live host and must be able to revert them exactly, and the hazard is a two-stage privilege boundary whose failures (a unit installed but never `daemon-reload`ed, a revert that leaves a system file behind, a restart silently denied by sudo) are not witnessable by a stub acceptance suite running unprivileged on either platform.

Background: This brief was researched against `main` commit `9a52c6ad`; locate every citation by name if a line has shifted. Two scoping facts come first. The `deploy/` directory is not tracked in this repository — `git ls-files deploy` returns nothing and `deploy/restart.sh` is matched by `.git/info/exclude:7` — so it is operator-local, invisible inside a Run, and nothing in this chain may edit or test it; any restart path this chain needs lives in tracked `scripts/deploy/`. And the merge executor is not one of the services this chain installs: it is absent from `SERVICE_LABELS`, the auto-deploy runbook already states that the release artifact carries its runtime but that it sits outside the activation set (`docs/runbooks/quiet-window-auto-deploy.md:9-13`), and its Linux unit already exists as an operator procedure (`docs/runbooks/merge-executor.md:283-327`).

Every service-management path that is tracked is macOS-only, in three separable layers.

The first layer is the definition format. `scripts/deploy/com.agentos.service.plist.in` carries the whole per-service environment contract in one `EnvironmentVariables` dict: `PATH`, `DEPLOY_NODE_BINARY`, `AGENTOS_REPOSITORY_ROOT`, `AGENTOS_SHARED_ROOT`, `AGENTOS_SHARED_ENV_FILE`, `AGENTOS_CURRENT_POINTER=current`, `AGENTOS_RELEASES_DIRECTORY=releases`, `AGENTOS_SERVICE_LABEL`, and the `__RUNNER_ENVIRONMENT__` hole that `renderServiceLaunchdPlist` fills with `RUNNER_ID`/`RUNNER_PATH` for runner labels (`scripts/deploy/com.agentos.service.plist.in:15-33`; `scripts/deploy/install-launchd.mjs:297-317`). `scripts/deploy/com.agentos.auto-deploy.plist.in:14-30` carries the deployment scheduler's own set — `AGENTOS_REPOSITORY_ROOT`, `PATH`, `QUIET_WINDOW_POLL_SECONDS=60`, `DEPLOY_NODE_BINARY`, `DEPLOY_GIT_BINARY`, `DEPLOY_NPM_BINARY`, `DEPLOY_SOURCE_REMOTE` — plus `__BACKUP_ENVIRONMENT__`, which `backupEnvironment` expands to either `DEPLOY_PG_DUMP_MODE=host` with `DEPLOY_PG_DUMP_BINARY`, or `DEPLOY_PG_DUMP_MODE=container` with `DEPLOY_DOCKER_BINARY`, `DEPLOY_PG_DUMP_CONTAINER` and `DEPLOY_CONTAINER_PG_DUMP_BINARY` (`install-launchd.mjs:171-186`). `RunAtLoad`, `KeepAlive`, `ProcessType`, `StandardOutPath`, `StandardErrorPath` and `StartInterval=300` are launchd lifecycle keys with no plist-free spelling.

The second layer is installation and control. `installLaunchdServices` renders the labels, refuses a rendered set that still contains a placeholder, a wrong `Label`, a missing path environment or an empty string (`install-launchd.mjs:323-344`), writes a per-entry manifest with original and installed SHA-256 digests plus backups so `--revert --apply` restores exactly what it replaced (`install-launchd.mjs:512-656`), and targets `~/Library/LaunchAgents` and `~/Library/Logs/Anneal` (`install-launchd.mjs:522-528`). `installLaunchd` renders and bootstraps the auto-deploy job through `/bin/launchctl` (`install-launchd.mjs:658-736`). Both entrypoints refuse to run as root: `install-launchd.mjs:660` and `scripts/deploy/install-launchd-services.mjs:33` throw `launchd-installer-refuses-root`, because a root-written LaunchAgent would be an unusable, operator-unowned file. That refusal is correct for launchd and directly contradicts a system-level systemd install, which must write into `/etc/systemd/system` as root. At deploy time the same launchd dependency reappears: `scripts/deploy/quiet-window-deploy.mjs:360-369` binds every control call to `/bin/launchctl` and `gui/<uid>`, `serviceState` decides liveness by matching `state = running` in `launchctl print` output (`quiet-window-deploy.mjs:525-531`), `verifyStableServicePaths` proves the wrapper boundary by finding the wrapper path inside that same output (`quiet-window-deploy.mjs:534-566`), and restart and rollback iterate `launchctl kickstart -k` (`quiet-window-deploy.mjs:838`, `:875-882`).

The inventory itself is a frozen literal in two places, deliberately duplicated so the wrapper stays a standalone artifact, with a fixture asserting the two stay in lockstep: `scripts/deploy/launchd-service-wrapper.mjs:20-40` and `scripts/deploy/quiet-window-lib.mjs:5-18` both spell out `com.agentos.runner` plus `runner-2` … `runner-10`, and `scripts/deploy/launchd-service-wrapper.test.mjs:140` compares them. Ten runner labels are baked into the count checks at `install-launchd.mjs:324`, `:503` (`SERVICE_LABELS.length + 1`) and `launchd-service-wrapper.mjs:344`, and into `patch-runner-plists.sh:39-48,101-129`, which fails when the number of runner plists on disk differs from `RUNNER_COUNT`. The target host runs sixteen runner services over eight isolated accounts, so the count must become configuration rather than a literal.

The third layer is host account provisioning. `scripts/os-isolation/provision.sh` reads and writes the account database exclusively through `dscl` and `dseditgroup` (`provision.sh:87-88`, `:183-208`), inspects ownership and modes with BSD `stat -f '%Su' / '%Sg' / '%Lp'` (`provision.sh:166`, `:302-324`), installs directories as `root:wheel` (`provision.sh:216-233`), defaults the account shell to `/bin/zsh` (`provision.sh:38`), and stages the sudoers file with `mktemp -t agentos-sudoers` (`provision.sh:260`), which GNU coreutils rejects for having no `XXXXXX` template. `verify.sh` adds `PlistBuddy` and three `launchctl print` readers whose whole point is that the loaded daemon, not the file on disk, answers the question (`verify.sh:44-83`). `rollback.sh` deletes records with `dscl` and resolves the operator home through `dscl ... NFSHomeDirectory` (`rollback.sh:39-47`, `:101-113`). `patch-runner-plists.sh` edits the installed definitions in place with `PlistBuddy`, records the before/after value of every key it manages in a per-label manifest so `--revert` restores those keys and nothing else, and refuses root for the same reason the installer does (`patch-runner-plists.sh:48-56`, `:75-84`, `:194-244`, `:296-303`). `reclaim-orphan-workspaces.sh` is portable apart from one `stat -f '%Su'` (`reclaim-orphan-workspaces.sh:124`).

The account model is per-account and self-contained, which bounds what this chain must do about CLI credentials. `patch-runner-plists.sh:400-402` sets each runner service's `RUNNER_RUN_AS_PREFIX` to `sudo -u <account> -E --` and its `RUNNER_HOME` to `$HOME_BASE/<account>` — the same account's own home, created at `install -d -o <account> -g <group> -m 700` (`provision.sh:210-212`). `config.home` is exactly that `RUNNER_HOME` (`packages/runner/src/config.ts:109`), so when `provisionIsolatedSessionConfig` copies `join(config.home, ".codex", "auth.json")` (`packages/runner/src/adapters/codex.ts:256`) or `join(config.home, ".pi", "agent", "auth.json")` (`packages/runner/src/adapters/pi.ts:319`) through `runCommand(config.runAsPrefix, …)` (`packages/runner/src/adapters/session-config.ts:17-22`, `:108-119`), the reading account is the owner of the file it reads. No account traverses another account's home, and the same home also holds the per-account Git and GitHub state that `workspaceEnvironment` pins with `HOME` and `GIT_CONFIG_GLOBAL=<home>/.gitconfig` (`packages/runner/src/adapters/environment.ts:27-32`) and that `packages/runner/runtime-tools/git-credential-runner.sh:29-37` re-exports as `HOME` before calling `git credential`. Ubuntu's `HOME_MODE` default is therefore irrelevant provided the Linux branch keeps creating each home explicitly at mode 700 rather than letting `useradd` create it, and provided `RUNNER_HOME` keeps pointing at the real per-account home.

Two things are already portable and must stay that way. `scripts/deploy/launchd-service-wrapper.mjs` — the process every definition actually starts — contains no macOS API at all: pointer resolution (`:106-155`), the shared-`.env` parse with its non-override rule and the five persistent-path defaults (`:188-259`), the invocation builder that exports `AGENTOS_RELEASE_*`/`DEPLOY_RELEASE_*` into the child (`:271-330`), and `verifyServiceInventory`'s injectable start/readiness adapters (`:337-373`) are all plain Node. And `install-launchd.mjs:346-399` already keeps plist mutation working on the Linux merge-gate worker by falling back from `/usr/bin/plutil` to `/usr/bin/python3` with `plistlib`, so the launchd tests in `npm run test:auto-deploy` (`package.json:34`, run by the gate at `scripts/merge-gate.sh:1198`) are real Linux-executed coverage of the macOS path.

One documentation fact corrects an assumption this chain inherited: `docs/runbooks/merge-executor.md:283-327` already ships a complete Linux systemd profile with `User=`, `EnvironmentFile=`, `Restart=always`, hardening directives, `systemd-analyze verify` and `enable --now`, so that runbook needs a cross-reference, not a new section. `docs/runbooks/quiet-window-auto-deploy.md` has no Linux content anywhere and declares itself a macOS profile in its first paragraph (`:1-13`, `:44-58`, `:117-155`). `docs/release/support-matrix.md:30` and `docs/install.md:10` both rate Linux **Unverified**; that rating is a statement about exercised installs and is not this chain's to flip.

4. Render the environment contract as `Environment=` lines, one per key, and prove key-set parity rather than restating it: a test asserts that for every label the set of keys rendered into the systemd unit is exactly the set rendered into the plist by `renderServiceLaunchdPlist` for the same `servicePlistValues`, including the runner-only `RUNNER_ID`/`RUNNER_PATH` pair, and the same for the auto-deploy definition across both `--pg-dump-mode host` and `--pg-dump-mode container` (covering `DEPLOY_DOCKER_BINARY`, `DEPLOY_PG_DUMP_CONTAINER` and `DEPLOY_CONTAINER_PG_DUMP_BINARY`). Values containing whitespace or `%` are escaped for systemd's parser. `EnvironmentFile=` must not be used for `shared/.env`: the wrapper is the only reader of that file and its non-override, no-expansion parse (`launchd-service-wrapper.mjs:188-259`) is the contract; a unit that preloaded it would both change those semantics and publish its contents through `systemctl show`.

5. Extend `installLaunchdServices` to a two-stage Linux install with the privilege rule stated explicitly. Stage one (rendering) runs unprivileged, refuses root exactly as today, writes the rendered units, the timer, the staged os-isolation drop-ins of item 12 and the same digest-and-backup manifest into an operator-owned staging directory under the existing `.agentos-deploy/` install root, and prints the exact root command for stage two. Stage two is a new `--install-units` mode that requires `geteuid() === 0`, refuses with `systemd-installer-requires-root` otherwise, copies staged files to `/etc/systemd/system` as `root:root` mode 0644, runs `systemctl daemon-reload`, and then `systemctl enable --now` for every long-running service unit and for the auto-deploy timer so the inventory starts at boot without an operator step. The auto-deploy `Type=oneshot` service is installed but is never enabled or started directly: its timer is what activates it, and `enable --now` on a oneshot would run a deployment at install time. The two installers keep their present split and each keeps its own manifest. The service installer's manifest is the stable wrapper plus one entry per service definition — the wrapper is `entries[0]` (`install-launchd.mjs:584-592`) and the length check is `SERVICE_LABELS.length + 1` (`:503`) — and Linux needs that wrapper entry exactly as macOS does, because every unit's `ExecStart` names the wrapper path: 14 entries at the default count, 20 at `AGENTOS_RUNNER_COUNT=16`, on both platforms. The auto-deploy installer (`install-launchd.mjs:658`) stays separate and owns its own definition and manifest: one plist on macOS, two files on Linux (the `Type=oneshot` service and its timer). So at count 16 a Linux host ends with 19 service units, the wrapper, and the auto-deploy pair; `enable --now` covers the 19 service units and the timer, and never the oneshot. `--revert --apply` reads the stage-one manifest, restores or removes each installed file by recorded digest with the same drift refusal as today, `systemctl disable --now` for each unit it removes, and a final `daemon-reload`. On macOS both new modes refuse with a named reason and the current single-stage behavior is untouched. `verifyServicePlistDefinitions` gains a systemd sibling enforcing the same four properties on unit text: no unresolved placeholder, the label appearing in `SyslogIdentifier` and `ExecStart`, the pointer environment present, and no empty assignment.

6. Stage two also installs `/etc/sudoers.d/anneal-service-control`, generated in stage one and validated with `visudo -c` before it is copied, granting the account named by `--service-user` NOPASSWD `systemctl` for exactly the generated unit names and exactly the verbs `restart`, `show` and `is-active`. It exists because the deploying account is not root and the units are system-level; `enable`, `disable` and `daemon-reload` are deliberately absent, since only the root install stage performs those. The Linux control adapter prefixes `sudo -n` when `geteuid() !== 0` and runs bare when it is 0, and a refused command fails loud with `service-control-denied:<unit>` — never a skipped restart reported as success.

Constraints: The macOS path is frozen behavior, not a reference implementation to refactor: with the platform resolved to `darwin` and the default runner count, every rendered plist, manifest entry, control command and installer stdout line must be identical to today's, and a test must witness that byte identity rather than assert it in prose. Tests must pass on both a macOS operator host and the Linux merge-gate worker: anything that needs a real `systemd-analyze`, `systemctl`, `useradd` or `dscl` either uses the existing tool-fallback pattern (`install-launchd.mjs:346-399`), a recorder stub, or skips with an explicit named reason — a silent skip is a defect.
