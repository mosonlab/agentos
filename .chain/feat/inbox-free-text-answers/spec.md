Every open Inbox card in the web UI offers the same answer surface: choice buttons where the card has choices, and a free-text box underneath, so an operator can type a full answer or attach a note to a gate decision instead of being limited to the listed options.

Background: This brief is based on `origin/main` at `8ac784ece6a3e8ff47ba56e4a8942fe37de30366`. The backend already accepts free text for a non-gate MULTIPLE_CHOICE question: `POST /inbox/messages/:id/reply` calls `applyInboxDecision` with `allowFreeText: true`, and `packages/db/src/inbox-decision.ts` only enforces choice-id matching when that flag is absent. The Feishu card footer already invites a text reply. The web page `apps/web/src/pages/Inbox.tsx` is the gap: when `message.choices` is non-empty it renders only the choice buttons, and when `gateTaskId` is set it renders only the approve and reject buttons; the `Textarea` branch is reached only for choice-less, non-gate cards. Approval-gate cards are a second gap: `applyInboxDecisionTx` refuses any decision other than the literal strings `approve` and `reject`, so a rejection carries no reason, and the requeued step (the `rejectionTarget` re-enqueued with `enqueueTaskRun`) runs blind. Stop questions (the cards bound by `parseStopQuestionKey` on `dedupeKey`) are machine-state prompts where free text has no consumer.

Changes:
1. The Inbox message read model (list and single-message routes in `packages/api/src/routes/inbox.ts`) exposes a server-computed boolean `acceptsFreeText`: true for an OPEN agent-authored TEXT or MULTIPLE_CHOICE question that a session is waiting on and for an OPEN approval-gate card; false for stop questions, closed or answered cards, human replies, and detached notifications. The web UI reads this field and does not re-derive the rule.
2. `POST /inbox/messages/:id/decision` accepts an optional `note` string (trimmed, 1 to 8000 characters) alongside `decision`. For a gate card, `decision` stays restricted to `approve` or `reject`; `note` is stored on the HUMAN reply message created for the decision and recorded in the task activity entry for the gate outcome. For a non-gate card, `note` is rejected with 400 (free text on those cards goes through `/reply`, unchanged).
3. When a gate is rejected with a `note`, the requeued step receives the note as human gate feedback: the run opened for the `rejectionTarget` carries the most recent rejection note for that task in its prompt context, labelled as operator feedback on the previous attempt, so the redo does not repeat the rejected output. A rejection without a note requeues exactly as today.
4. `apps/web/src/pages/Inbox.tsx`: an open card with `acceptsFreeText` renders its choice buttons (or approve/reject buttons for a gate card) and, below them, the existing `Textarea`. For a non-gate choice card the text box submits through `/reply` and the buttons submit through `/decision`; picking a choice and typing are alternatives, there is no combined submit. For a gate card the text box is the optional note: approve and reject both send `decision` plus the trimmed `note` when non-empty. A card with `acceptsFreeText: false` renders as today.
5. `docs/operator-api.md` documents `acceptsFreeText` on the Inbox message shape and the `note` field on the decision route, including the 400 for `note` on a non-gate card.

Out of scope: Feishu card layout and the Feishu event handler (`packages/inbox/`), including any pending-note state for Feishu gate decisions; combined choice-plus-text submission or any change to `selectedChoiceId` semantics; stop-question behaviour; which chain steps carry `approvalGate` and any project-level gate setting; the gate card body, its evidence worker, or `produceMergeAuthorization`; Inbox list filtering or performance.

Constraints: `note` never changes what decision was recorded; `approve` with a note approves, `reject` with a note rejects. Validation failures answer 400 with a named reason, never a silent drop of the note. The rule for `acceptsFreeText` lives in one server-side function used by both Inbox routes; the web bundle must not contain a copy of it. Existing decision idempotency (`requestId`, `externalEventId`) is preserved for decisions with and without a note.

Acceptance: `packages/api/src/inbox.test.ts` (or a sibling test in the same workspace) shows `acceptsFreeText` true for an open choice question with a waiting session and for an open gate card, and false for a stop question and for an answered card; the decision route with `note` on a gate card stores the note on the reply message and in the gate activity entry, and `note` on a non-gate card returns 400; a dbtest in `packages/api` (`npm run test:db -w @anneal/api -- src/<file>.dbtest.ts`) rejects a gate with a note and asserts the requeued task's next run prompt context contains that note verbatim, and asserts a rejection without a note leaves the prompt context unchanged from today; `apps/web` tests (`inbox-lanes.test.tsx` or a sibling) render an open choice card with both buttons and a text box, a gate card with approve, reject and a text box, and a card with `acceptsFreeText: false` without a text box; `npm run lint` and the touched workspaces' typecheck pass; `docs/operator-api.md` names `acceptsFreeText` and `note`.
