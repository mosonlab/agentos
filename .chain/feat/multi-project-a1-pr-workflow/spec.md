A Project created through `POST /projects` comes up workflow-ready: it owns a `local` Environment, the four canonical roles a pull-request workflow needs, and a new canonical four-step `pr-engineer-workflow` template that ends at an open pull request with no regression or merge step, so that after the operator adds an in-Project Repo and grants those four Agents `GIT_WRITE` access, the template instantiates and its review steps claim.

Route: implementation=senior-dev - project bootstrap moves source I/O across a Serializable transaction boundary, and the new template needs a cross-module specification-materialization/claim contract change that the acceptance suite can only partly witness.

Background: `POST /projects` (`packages/api/src/routes/admin.ts`) creates a bare Project row. Canonical Agents and TaskTemplates are installed only by `packages/db/prisma/seed.ts` and `packages/db/prisma/sync-canonical-prompts.ts`, which select the single project with slug `agentos-example`, and by `POST /onboarding` (`packages/api/src/onboarding.ts`), which is once-only and by contract creates one `default` Agent and zero templates. The template API (`packages/api/src/routes/templates.ts`) has no create route and `clone` refuses a source outside the addressed project, so an empty Project can never obtain a template and therefore can never instantiate a template chain. Both existing canonical templates end in a regression/merge tail that requires `scripts/merge-gate.sh` and `scripts/regression-verification.sh` inside the target repository and a merge-executor installation; a plain repository cannot run them. The direct template's first two steps are not reusable under another name: `packages/api/src/templates.ts` (revalidation omission, Route line), `packages/api/src/revalidation.ts`, `packages/db/src/run-open.ts` (`isDirectImplementationStep`, native child pinning) and `packages/api/src/specification-fidelity.ts` (`specificationMaterializationForDirectImplementation`) key on the canonical identity `direct-engineer-workflow`. The canonical review roles (`agents/roles/review-coordinator-sol.md`, `review-coordinator-opus.md`) and the review claim path (`prepareSpecificationVerification` in `specification-fidelity.ts`, called from `packages/api/src/run-claim.ts`) require the materialized specification `.chain/<branch>/spec.md` at the pinned implementation head for every canonical `sol-findings` and `blind-findings` step, so a canonical PR workflow whose implementation step is not materialized would park its first review claim. Canonical identity is the registry `LEGACY_TEMPLATE_GENERATIONS` in `packages/db/src/canonical-template-transition.ts`: `canonicalTemplateIdentity` recognizes a current name before it walks generations, but `canonicalStepOrdinals(name, null)` derives current ordinals from the latest registered generation and returns `null` when there is none, and a shape-only generation is classified as retired by `matchedLegacyGeneration`, so a template with no history cannot be represented there today. `planCanonicalInstallation` / `applyCanonicalInstallation` (`packages/db/src/canonical-template-installation.ts`) accept a caller transaction, a source map and `requiredProjectIds`, and `writeCanonicalTemplate` binds assignees to active Agents of the addressed Project and persists `variables: ["branchName"]`; the planner and applier are not exported from the `@anneal/db` barrel (`packages/db/src/index.ts`).

1. New canonical template source directory `agents/templates/pr-engineer-workflow/` with exactly four step documents in the existing frontmatter format. Step 1 `Implementation`: `stepIndex` 1, `layer` 1, `agent` `senior-dev-luna`, `outputKind` `implementation`, `priorOutputKinds` `[]`, `attachmentsFromPrevious` false, `opensPullRequest` true, `requiresCommit` true, `baseFromStepIndex` null. Step 2 `Code review (Sol)`: `stepIndex` 2, `layer` 2, `agent` `review-coordinator-sol`, `outputKind` `sol-findings`, `priorOutputKinds` `[implementation]`, `attachmentsFromPrevious` true, `opensPullRequest` false, `requiresCommit` false, `baseFromStepIndex` 1. Step 3 `Code review (Opus blind)`: `stepIndex` 3, `layer` 2, `agent` `review-coordinator-opus`, `outputKind` `blind-findings`, `priorOutputKinds` `[]`, `attachmentsFromPrevious` false, `opensPullRequest` false, `requiresCommit` false, `baseFromStepIndex` 1. Step 4 `Apply review fixes`: `stepIndex` 4, `layer` 3, `agent` `senior-dev`, `outputKind` `fixed-implementation`, `priorOutputKinds` `[sol-findings, blind-findings]`, `attachmentsFromPrevious` true, `opensPullRequest` false, `requiresCommit` false, `baseFromStepIndex` null. Steps 2-4 reuse the prompt bodies of the direct template's steps 3-5 verbatim. Step 1's prompt states: implement the task description on `{{branchName}}` as the specification of record; the platform materializes `.chain/{{branchName}}/spec.md` as the specification of record and the step leaves it untouched; commit; persist exactly one `implementation` JSON output object with the same fields the direct implementation step persists (`schemaVersion`, `headSha`, `baseSha`, `summary`, `testsRun`); leave publication and pull-request creation to the platform. The prompt does not mention native child threads, the Route line, or revalidation.

Review-side verification (`prepareSpecificationVerification` / `authorityFor`) already keys on the `sol-findings` / `blind-findings` output roles and is not changed; with the implementation step materialized, both PR review claims reach status `ready`. A new exported operation module in `packages/api/src` (same shape as `onboarding.ts`: injectable role and template source loaders, pure input validation, one Serializable transaction) implements Project bootstrap, and `POST /projects` calls it through `RouteDeps`, which carries the operation's loader dependencies with release defaults so a route test can inject substitutes. The operation loads role sources and template sources before the transaction opens and creates inside it: the Project from the existing `projectInput`; one Environment named `local` with `networking: OPEN` and `allowedHosts: []`; the four Agents `senior-dev-luna`, `review-coordinator-sol`, `review-coordinator-opus`, `senior-dev` bound to that Environment, each with `name`, `title`, `model`, `runnerPreference`, `inboxAccess`, `foundationalPrompt` and `rolePrompt` from the loaded sources and `disabledTools: []` (the same field mapping onboarding applies to its starter Agent); and the `pr-engineer-workflow` template through the exported installer with a one-entry source map and the new Project id as the sole required Project, so its steps bind to the four Agents just created and its persisted `variables` are exactly `["branchName"]`. The route still returns the Project row with `201`.

No partial Project is observable through the API.

Out of scope: `POST /onboarding`'s installation shape, code, and verifier; iterating every Project in `sync-canonical-prompts.ts`; installing `compound-engineer-workflow` or `direct-engineer-workflow` into new Projects; Repo creation, remote preflight, or automatic `AgentRepoAccess` creation in any route; Secret grants; native child-thread pinning for the new template; Inbox project scoping and every other web change; any change to the two existing templates' step documents, prompts, or registry generations; gate, merge-lease, or merge-executor scripts; database schema migrations.

Constraints: no Prisma schema change. Existing Projects keep every current Agent, Environment, Repo, grant, Task, Run and both existing canonical templates unchanged; the only new rows in the canonical project after seed or sync are the `pr-engineer-workflow` template and its steps. Fail loud: no fallback role set, no silent skip when a role or template source is missing, no swallowed transaction error. Existing Repo-grant enforcement at instantiation and claim is unchanged. The new template's rows are protected exactly like the other canonical templates: `PUT .../steps` refuses with `template_canonical`, `clone` succeeds. Open-pull-request delivery uses the existing runner behavior (push every step branch; `gh pr create` for a GitHub remote with an authenticated CLI) with no new runner code.
