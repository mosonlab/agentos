Board: Hold and Resume on chain aggregate cards, held aggregate state, Doing-column Hold all, and a hold that stops a chain before its first layer.

Background: This brief is based on `origin/main` at `031f5e36`. The chain hold primitive exists (`POST /tasks/:taskId/chain/hold`, `POST /tasks/:taskId/chain/resume`, `packages/db/src/chain-control.ts`, `packages/db/src/chain-hold.ts`) and is exposed only on the task detail page (`apps/web/src/components/chain-list.tsx` header button "Stop after current layer" / "Resume Chain"). The board does not surface it: `ChainAggregateState` in `packages/db/src/board-contract.ts` has no held value, `packages/api/src/board.ts` never reads `ChainControl`, so a held chain whose current layer has finished sits in Todo labelled "Idle" with no Resume action, and a running chain card offers no way to stop it after the current step. The Todo column head has "Activate all" (`parkedChains` in `apps/web/src/lib/board.ts`, `BoardColumn` in `apps/web/src/components/desktop-board.tsx`, `activateParkedChains` in `apps/web/src/pages/Tasks.tsx`); the Doing column head has nothing. Two mechanism defects make hold unable to keep a chain out of the queue: (a) `holdChain` computes `heldLayer` as the lowest layer with a non-DONE member, so a hold on a chain that has not started records `heldLayer: 1` and `heldPredicate` (refuses only `layer > heldLayer`) lets layer 1 run; (b) `dispatchBoundSuccessor` in `packages/db/src/chain-activation.ts` locks the successor chain but never reads the successor chain's `ChainControl`, so a held `waiting-on-predecessor` chain is queued the moment its predecessor completes. The operator model this chain implements: a card's state is derived; the operator has two verbs, Activate/Resume and Hold. A held chain finishes the layer it is on and starts nothing further; after that layer finishes the aggregate card moves to Todo (the existing column rule "active run means Doing, otherwise the frontier step's status" already produces this) and shows Resume.

Changes:
1. `holdChain` records `heldLayer` as the highest execution layer that has been admitted (any member whose status is not TODO, or that has at least one Run); when no layer has been admitted it records `0`. The `ChainControlEvent.layer` uses the same value. `heldPredicate`, `heldWhere`, and `heldSql` need no change: with `heldLayer: 0` they refuse every layer. The hold refusal message for `heldLayer: 0` reads "Chain is held before its first layer" instead of "held after layer 0"; the `chain/hold` and `chain/resume` handbook entries in `docs/operator-api.md` state the new rule and the value `0`.
2. `dispatchBoundSuccessor` reads the successor chain's `ChainControl` after taking the successor chain lock (the same order as the same-chain path at the `readChainControl` call in `activateChainSuccessor`). When the successor chain is HELD it does not queue the successor: it writes a control-plane `TaskActivity` on the successor task with metadata kind `chainControl.activationWithheld` (same shape as the same-chain withhold) and returns. A later `chain/resume` on that chain owns the activation (change 3).
3. `resumeChain` on a released control whose `heldLayer` was `0` activates layer 1 when layer 1 has no Run and the chain's first task either has no `dispatchAfterTaskId` or its predecessor is DONE; it goes through the same admission as `POST /tasks/:taskId/start` (repo access, agent, startability) and reports the activated task id in `nextTaskId`. When the predecessor is not DONE, resume releases the control and activates nothing; the predecessor's completion then queues the successor through change 2's unheld path. `resumeActivationAnchor` semantics for `heldLayer >= 1` are unchanged.
4. `packages/db/src/board-contract.ts`: `ChainAggregateState` gains `"held"`; `ChainAggregate.activation` gains `hold: { heldLayer: number; heldAt: string; holdReason: string | null } | null`, non-null whenever the chain's `ChainControl.state` is HELD. `packages/api/src/board.ts` loads `ChainControl` rows for the chains on the board in one query and derives: `activation.state` is `"running"` when any member is active (unchanged, even while held), otherwise `"held"` when `hold` is non-null, otherwise the existing derivation. A held chain in `"held"` state reports `activation.taskId` as the task `chain/resume` is addressed to (any member; use the first primary member). The board dbtest that fixes the aggregate projection covers: held before layer 1 (state `held`, `taskId` set), held after layer N with the layer finished (state `held`, card column TODO), held while running (state `running`, `hold` non-null).
5. `apps/web/src/components/chain-aggregate-card.tsx` renders by state: `parked-unactivated` keeps Activate; `waiting-on-predecessor` keeps the predecessor lock line and adds a Hold button; `running` adds a Hold button (label "Stop after current step") when `hold` is null, and when `hold` is non-null shows an amber pill "Stops after step" and a Resume button instead; `held` shows an amber pill (text "Held" when `heldLayer` is `0`, otherwise "Held after step N") plus the hold reason when present, and a primary Resume button. The card menu mirrors the same actions. Hold and Resume post `chain/hold` and `chain/resume` with a fresh `requestId` through `ChainAggregateActions` (`onHold`, `onResume`) wired in `apps/web/src/pages/Tasks.tsx`, with `reload()` after each; refusals land in the page's existing error surface.
6. Todo column head "Activate all" excludes chains whose `hold` is non-null (`parkedChains` in `apps/web/src/lib/board.ts`). Doing column head gains "Hold all" (`heldChains`-style helper listing every chain in that column whose `hold` is null), with a confirmation modal in the shape of the Activate-all modal that lists the chains and states that each finishes its current step before stopping and that no running Run is cancelled. Confirming posts `chain/hold` per chain (idempotent; a chain already held is skipped client-side) and reports "Held {n} of {total} chains" plus refusals. The button is absent when no chain in the column can be held.
7. `apps/web/src/locales/en.ts` and `zh.ts` gain every new string; `apps/web/src/lib/board.ts` state tone map and `STATE_TONE` in the card gain `held` (amber). No new `TaskStatus`; no new column.

Out of scope: cancelling Runs from the board (the Hold all and per-card Hold never call `POST /runs/:id/cancel`); a Hold all on the Todo column; a Backlog-side pause; changing what `chain-list.tsx` on the task detail page renders beyond consuming the new refusal message wording; the `Start now` / `Recover parked step` flow for parked (Backlog) steps; approval gates (`approvalGate`, the configurable-gates chain in flight on `chain-activation.ts` gated-step handling); `afterTaskId` binding rules, fan-in, or instantiate changes; run-claim SQL (`heldSql`, `heldWhere`); mobile board layout beyond rendering the same card component; archiving behaviour; the Todo/Doing column semantics text in `docs/governance/task-routing-v1.md`.

Constraints: fail loud, no silent fallback: a hold or resume refusal surfaces as the API's 409 message on the page, never as a silently skipped card. Hold is layer-granular by contract: nothing in this change interrupts an active Run. The board derives `held` only from the persisted `ChainControl` row; the web client never recomputes the barrier. Every new API-visible field is documented in `docs/operator-api.md` in the same change (board read shape under `GET /tasks`, hold/resume semantics). Existing dbtests for hold and resume (`chain-control.dbtest.ts`, `chain-resume.dbtest.ts`, `chain-activation-barrier.dbtest.ts`, `chain-enqueue-barrier.dbtest.ts`) keep passing with their held-layer expectations updated to the new rule where they hold an unstarted or partially started chain; a changed expectation is explained in the test.
