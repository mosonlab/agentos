Legacy seven-step Direct chains can resume a pre-merge stop through a fresh evidence-backed confirmation card without database intervention.

Background: requestConfirmationCard in packages/db/src/merge-integrator-db.ts currently selects only the nearest preceding chain task, then requires that task to have a Run with a Session. In direct-engineer-workflow, the nearest predecessor is the server-owned Merge readiness step, which intentionally has no Run or Session. Answering a merge-integrator base-drift stop with re-authorize therefore durably records refresh-requested but returns confirmationCardId=null, leaving the integrator in REVIEW with no fresh evidence card and no supported recovery path. Production PR #44 and PR #46 have demonstrated this exact state.

Changes:
1. Resolve the confirmation evidence source within the same project and chain by walking preceding steps newest-first and selecting the nearest legitimate task that has a persisted Run with a Session; never cross the chain, use an integrator Run, or bind to an unrelated target.
2. Add a durable idempotent control-plane recovery for an already-recorded refresh-requested stop whose confirmation request/card was not created, so normal reconciliation or a safe replay creates the missing request exactly once without manual database edits.
3. Preserve requestMergeEvidence phase ordering and dedupe: the recovered path opens one placeholder confirmation card and one evidence-request activity, and creates no merge authorization or mechanical Run until a human reads and approves filled fresh evidence.
4. Add regression coverage for a legacy seven-step Direct chain whose immediate Merge readiness predecessor has no Run/Session, including the already-recorded refresh-requested/null-card state and repeated/concurrent recovery attempts. Retain coverage for current twelve-step chains, terminal stop dispositions, target-unresolvable repair, and ordinary Inbox idempotency.

Out of scope: changing the stop-condition or choice matrix; auto-approving evidence; manually mutating PR #44 or PR #46 state; changing workflow templates, GitHub App permissions, executor provisioning, PostgreSQL or RUNNER_TOKEN credentials; schema migrations; unrelated Inbox or merge behavior.

Constraints: remain fail-closed; evidence must precede human judgment; the original stop and answer activities remain append-only authority; recovery must be race-safe and deduped; missing or ambiguous same-chain evidence sources must fail loudly without selecting a fallback outside the chain; no secret-bearing output or child-process credential changes.

Acceptance: automated database/API tests prove that re-authorize on the seven-step shape creates exactly one OPEN confirmation placeholder bound to the nearest preceding same-chain Run/Session; a pre-existing refresh-requested/null-card state is repaired through a supported idempotent path and repeated or concurrent attempts still produce one card/request; before approval there is no new merge authorization or Run; existing merge-stop, evidence-protocol, target-repair, Inbox-idempotency, and twelve-step cases remain green; scripts/merge-gate.sh --expect-head <exact candidate head> reports MERGE GATE: PASS for the final head.
