Run workspaces receive a verified dependency tree from a runner-owned content-addressed cache before the agent session begins.

Background: `packages/runner/src/workspace.ts` currently makes the isolated checkout in `provisionWorkspace` and returns it without materializing dependencies. Agent work therefore repeatedly creates about 540 MB of `node_modules` for the same lockfile. `scripts/merge-gate.sh` already proves the required safety model for this repository: a cache key bound to dependency inputs and the Node/npm/macOS toolchain, an exact manifest of root and workspace-package `node_modules` trees, APFS copy-on-write restoration, and atomic write-once publication. Run provisioning needs the same behavioral guarantees without coupling runner execution to the merge-gate script.

Changes:
1. Add a runner-owned dependency-cache boundary invoked by `provisionWorkspace` after either the normal branch checkout or pinned detached checkout is established and before the workspace is returned to `executeClaim`.
2. Derive the cache key from every repository input that can change `npm ci` output: `package-lock.json`, root and workspace package manifests, npm configuration, the Prisma schema consumed by install hooks, and the exact Node, npm, operating-system and architecture tuple. A missing required input is a named cache miss; an unreadable or ambiguous input fails loudly.
3. Enumerate only the root and declared first-level workspace-package `node_modules` targets. Clear those targets before every restore or install, reject symlinks and any path outside the run workspace or cache root, and preserve `RUNNER_RUN_AS_PREFIX` ownership by performing workspace mutations through the configured execution identity.
4. On a valid hit, verify the entry metadata and complete target manifest, clone each cached tree into the empty workspace using copy-on-write semantics, and never execute or mutate a cache entry in place. An incomplete or malformed entry is never trusted or repaired silently; report the named condition and use a clean `npm ci` path only when the lockfile inputs remain valid.
5. On a miss, run `npm ci --prefer-offline --no-audit --no-fund` once, verify the produced target set, stage a snapshot under a private temporary directory, and publish it atomically as a write-once entry. Concurrent daemons racing on the same key must converge on one valid entry without overwriting it or consuming a partial publication.
6. Cache only dependency trees and versioned metadata. Never cache repository source, build outputs, `.agentos` credentials, CLI configuration, environment values, logs, or other workspace state. Emit bounded runner progress for hit, miss, publication, integrity refusal, and elapsed provisioning time without exposing paths that contain credentials.

Out of scope: changing `scripts/merge-gate.sh` or its gate authority, caching build outputs or test verdicts, npm-to-pnpm migration, cross-host cache distribution, general workspace-reclaim redesign, session-config retention, and production deployment changes.

Constraints: Preserve the existing isolated-workspace, pinned-review, cleanup, process-group timeout, proxy, and run-as-principal invariants. Cache failure may never produce a partially populated workspace. Expected misses may take the clean install path; integrity violations and command failures must be visible and must not be converted into an unexplained slow-path fallback.

Acceptance: Runner tests using temporary workspace and cache roots prove (a) first provisioning installs and atomically publishes, (b) the second identical provisioning restores dependencies without invoking npm, (c) lockfile, manifest, Prisma, npm configuration, Node/npm, OS or architecture drift changes the key, (d) root and nested workspace trees are complete, (e) malformed, partial, symlinked and escaping entries are refused, (f) concurrent publishers leave one valid immutable entry, (g) branch and pinned-detached provisioning both receive dependencies, and (h) run-as-prefix ownership is preserved. Existing workspace, provisioning-failure, cleanup, proxy and runner suites remain green, and a scratch-repository integration test demonstrates that the restored tree is usable while the cached entry remains unchanged.
