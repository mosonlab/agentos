One malformed queued task is fail-stopped with durable operator evidence while the same runner claim request can still claim the next eligible task.

Background: `POST /runner/tasks/claim` loads up to twenty queued candidates and evaluates them inside `claimOnce`. Candidate-specific authority such as `pinnedImplementationRange` is currently resolved only after the Run has tentatively moved to `CLAIMED`, a Session and fencing token have been prepared, and the Task has moved to `DOING` within the transaction. A `PinnedBaseCommitError` caused by a legacy chain step whose referenced `TaskStepOutput.commitSha` is missing therefore aborts the whole transaction and returns HTTP 500. The poisoned candidate remains earliest and every daemon repeats the same failure, blocking otherwise valid queued work.

Changes:
1. Complete all deterministic candidate-specific activation validation before committing a claim transition, including pinned implementation range resolution and consistency between that range and the queued Run target. No Session, fencing token, lease, Task `DOING` transition, or decrypted secret set may be created for a candidate that cannot activate.
2. Define a narrow typed candidate-activation failure classification. It must cover `PinnedBaseCommitError` and equivalent deterministic missing or inconsistent task-owned activation authority, while repository/database transport errors, serialization exhaustion, programming defects, and unknown exceptions still fail the claim request loudly.
3. When a typed candidate-activation failure wins a compare-and-swap against an unclaimed `QUEUED` Run, terminalize that Run as non-retryable `FAILED` with `FailureClass.TASK_FAILED`, preserve the exact named reason, set `endedAt`, park its Task in `BACKLOG` with the same failure reason, and append one TaskActivity plus one deduplicated operator-facing Inbox notification. Preserve existing outputs and chain evidence; never fabricate the missing commit or authorization.
4. After isolating a typed bad candidate, continue scanning the remaining ordered candidates in the same claim request. Return the first valid claim normally; return 204 only when no valid candidate remains. A poison candidate may not force a 500 or hide later work.
5. Make concurrent runner polls idempotent: at most one transaction terminalizes and reports the bad Run, no duplicate Inbox noise is created, and at most one runner claims each valid Run. A poll that loses either compare-and-swap re-reads or continues without overwriting the winner.
6. Keep the existing handling for missing repository grants, mechanical-integrator binding, server-owned readiness, backend circuits, deploy barrier, and target-branch merge serialization behaviorally unchanged except where they share the new pre-claim validation boundary.

Out of scope: repairing or backfilling legacy `TaskStepOutput` rows, weakening pinned-base invariants, direct database repair, changing retry routing or budgets, adding queue priority, cancelling active Runs, implementing Chain Hold/Resume, or redesigning the scheduler.

Constraints: Isolation is only for errors proven to belong to one candidate. Unexpected control-plane failure must remain visible as a failed claim request. The fail-stop record must be auditable and must not auto-retry, activate a successor, or mutate another task. No error or Inbox body may expose credentials, decrypted secret values, or filesystem contents.

Acceptance: Database tests place a poisoned pinned candidate ahead of a valid queued candidate and prove one claim call parks and reports the poison while returning the valid claim. Additional tests prove all-poison returns 204 rather than 500, repeated and concurrent polls create one failure activity and one Inbox message, no Session/fence/lease is created for the poison, valid candidates retain exactly-once claim semantics, unknown and database errors still return failure without partial commits, and existing grant, mechanical claim, blind-review pinning, deploy-barrier and runner claim suites remain green.
