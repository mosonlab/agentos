Reject invalid compound implementation assignee configuration before it can turn Human approval into an internal server error.

Background: A compound-engineer-workflow chain reached its approved Revise plan gate with the successor Implementation task assigned to senior-dev-high. subprocessRunConfig in packages/db/src/workflow.ts requires a compound Implementation step to remain assigned to implementation-plan-executioner. Both PATCH /tasks/:taskId with status DONE and POST /inbox/messages/:messageId/decision attempted successor activation, threw that invariant error inside the transaction, rolled back the Human decision, and returned HTTP 500. The task mutation surface currently permits this latent invalid assignment.

Changes:
1. Validate Task assignee changes on PATCH /tasks/:taskId so an unarchived compound-engineer-workflow Implementation task can only be assigned to the active in-project Agent named implementation-plan-executioner; return a stable named 4xx response and leave the task unchanged for any other assignee.
2. Preserve defense in depth in activation: if legacy or concurrently corrupted persisted state violates the same compound Implementation assignee invariant, map both task-completion approval and Inbox approval to a stable named 4xx response instead of an unhandled 500, with the full transaction rolled back.
3. Keep successful Human approval atomic and idempotent: a valid gate decision records exactly one decision, closes the gate, marks the predecessor DONE, creates exactly one successor Run, and replay does not duplicate any of them.
4. Add focused API and throwaway PostgreSQL regression coverage for direct task PATCH rejection, invalid legacy state through both approval routes, successful repaired-state approval, and replay/concurrency behavior.

Out of scope: changing canonical Agent or TaskTemplate definitions; allowing senior-dev-high to own compound orchestration; weakening subprocessRunConfig; modifying structural migrations, release authority, merge automation, Chain DAG Phase 2, runner health, historical Run/output rows, or existing completed decisions; direct SQL or production data repair.

Constraints: Fail loudly with a named client-visible error; never silently substitute an assignee, auto-approve, partially commit a decision, create an orphan Run, or convert autoStart into dependency semantics. Existing valid direct-engineer-workflow senior-dev-high assignments remain supported. Preserve append-only branch history and current Human approval authority.

Acceptance: Focused unit/API tests prove the PATCH assignee violation returns the documented 4xx and leaves the row byte-equivalent on relevant fields; throwaway PostgreSQL tests prove both approval routes return the same named 4xx for a deliberately seeded legacy-invalid compound successor with no decision/status/Run side effects; tests prove a repaired valid successor approves atomically and exactly once under replay/concurrency; existing workflow, chain, inbox, and app tests pass; exact-head scripts/merge-gate.sh reports MERGE GATE: PASS for the merged candidate; after quiet-window deployment, a fresh disposable chain fixture or equivalent supported live probe demonstrates invalid assignment is rejected without 500 and valid approval activates exactly one successor.
