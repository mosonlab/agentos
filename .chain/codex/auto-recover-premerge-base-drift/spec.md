Ordinary pre-merge base drift recovers automatically through a fresh exact-head and current-base verification cycle without human re-authorization.

Background: The merge executor deliberately returns the pre-merge stop condition base-drift when the target branch advances after a Mechanical merge authorization was issued. Earlier drift can already send Merge readiness back to Regression verification through requeueRegression, but a late executor stop is persisted by recordIntegratorStop and currently opens a re-authorize Inbox question through STOP_CHOICES. That treats normal serialization between otherwise valid pull requests as a human decision and can repeat indefinitely. The existing evidence-backed requestConfirmationCard path remains necessary for genuine exceptional stops; ordinary base-SHA advancement on the same pull request and target needs a separate server-owned recovery path that never weakens the exact head/base authorization invariant.

Changes:
1. Classify only an executor's pre-merge base-drift as automatically recoverable when the stop evidence is well formed and a fresh server-side repository read proves the same repository, pull-request number, target branch, and authorized/current PR head, with only the target base SHA advanced. A target-ref change, unresolved or ambiguous identity, head drift, malformed or mismatched payload, foreign state, or any incident condition is ineligible and remains fail-closed.
2. For an eligible stop, atomically and idempotently park the obsolete Merge execution/readiness state, preserve all prior stop outputs and authorizations as append-only evidence, return the chain to Regression verification, and enqueue exactly one fresh regression run against the latest target base. Duplicate executor completion, task-output replay, reconciliation, or worker ticks for the same stop must not create another run or notification.
3. Persist a durable recovery marker and attempt count in existing metadata/activity storage, with a maximum of two automatic pre-merge base-drift recoveries per chain and pull-request identity. The third eligible drift stops without another regression run and emits one precise operator notification. Recovery activities identify the attempt, source stop, repository/PR/target, authorized head/base, and observed/current base without secrets.
4. Remove the ordinary base-drift human re-authorize confirmation entrance: an eligible ordinary drift must create no confirmation card, and an ineligible or exhausted base-drift must not offer re-authorization as a parallel fallback. Keep the PR #54 evidence-backed confirmation-card and historical refresh-requested/null-card recovery behavior unchanged for other stop conditions that still support manual recovery.
5. Require every automatic recovery to complete the existing fresh Regression verification and exact-head/current-base gate, then the existing Merge readiness checks and any required independent review, before the server issues a new Mechanical merge authorization and the GitHub App executor may run. Never reuse or rewrite the obsolete authorization.
6. Carry the automatic-recovery context through the fresh tail. If that regression returns refresh-conflict or a real gate-fail, or if its independent review rejects, stop once with a precise operator notification and do not create the normal automatic refresh-conflict, gate-fix, or review-fix auxiliary task. ambiguity, payload-mismatch, changed-underneath-me, base-drift-post-merge, and all other foreign or post-merge incidents retain their existing fail-closed behavior and never enter this retry loop.
7. Apply the same recovery contract to current direct and compound merge tails without changing their normal first-pass behavior, wire formats, or GitHub App isolation.

Out of scope: PR #44 or PR #46 task/branch/PR state changes; credential rotation; GitHub App provisioning; executor installation or deployment changes; Prisma schema or migrations; automatic conflict resolution; automatic repair after gate failure or review rejection in a drift-recovery cycle; post-merge acceptance, revert, or incident automation; widening automatic recovery to stop conditions other than pre-merge base-SHA drift; changes to archived records.

Constraints: Preserve exact head plus exact current base as the authorization boundary; all identity and evidence checks fail loudly; no degraded fallback, old-authorization reuse, silent retry, duplicate run, or duplicate notification is allowed. Use existing transactional locks and durable metadata/activity records so restart and replay are safe. The source/serving checkout remains read-only; implementation occurs only in the chain's isolated workspace.

Acceptance: Database and focused API tests prove (a) an eligible direct-tail and compound-tail pre-merge base-SHA drift creates no Inbox confirmation card and exactly one fresh Regression verification run under duplicate completion/reconciliation, (b) fresh PASS/readiness produces a new authorization bound to the refreshed head/base before a new executor run, (c) two distinct eligible drifts recover and the third creates no run and one notification, (d) target-ref/head/identity/evidence mismatch and every named incident condition create no auto-recovery run, (e) a drift-recovery refresh-conflict, gate-fail, or independent-review rejection creates no auxiliary repair task and stops once, (f) STOP_CHOICES no longer exposes re-authorize for ordinary base-drift, and (g) the PR #54 manual evidence-source and historical null-card recovery regressions for other supported stops remain green. The repository merge gate passes for the exact final head.
