# BRIEF: Move the template, trigger and hook routes out of app.ts into routes/templates.ts

Date: 2026-08-31. Status: instantiated as a direct chain bound after the terminal task of chain 9f5b5fab (template authoring); not started. Routing: direct-engineer-workflow.
Route: implementation=senior-dev-luna - a verbatim relocation whose specification is the ordered route table already asserted by a test; the review and regression tail witnesses every acceptance item.

After this chain, `packages/api/src/app.ts` registers no route inline: the `/task-templates`, `/triggers`, `/hooks/templates` and fire routes live in `packages/api/src/routes/templates.ts` and are registered from `createApp` at the position they occupy today.

Background: chain 0a4b543e (brief `BRIEF-app-route-modules-20260831.md`) moved every other route group out of `app.ts` into `packages/api/src/routes/<group>.ts`, each exporting one `register<Group>Routes` function that receives its shared dependencies through the `RouteDeps` type in `routes/support.ts` (with the existing continuation return values for system, runner and session, and runner-specific dependencies for runner), and added `app-routes.test.ts`, whose literal ordered list of `${method} ${path}` pairs is the specification of route registration. That chain left the template, trigger and hook routes inline in `app.ts` because chain 9f5b5fab (template authoring: clone and structure-replace endpoints, validator, removal of the `Route:` allowlist) was rewriting them at the same time. Both chains have merged when this chain starts; this chain finishes the move for the routes they left behind, whatever their final set is on this chain's base (on main `79f46fd6` before either chain they were: `POST /hooks/templates/:templateId`, `GET /projects/:projectId/task-templates`, `GET /task-templates/:templateId`, `PATCH /task-templates/:templateId`, `POST /projects/:projectId/task-templates/:templateId/instantiate`, `GET /projects/:projectId/triggers`, `GET /triggers/:templateId`, `GET /triggers/:templateId/fires`, `POST /triggers/:templateId/pause`, `POST /triggers/:templateId/enable`, `POST /task-templates/:templateId/fire`; 9f5b5fab adds clone and steps routes under `/projects/:projectId/task-templates/:templateId/`). The revalidation step at the head of this chain confirms that `routes/`, `routes/support.ts` and `app-routes.test.ts` exist on the base before implementation starts; if they do not, the premise has collapsed and the chain stops there.

Changes:
1. Create `packages/api/src/routes/templates.ts` exporting `registerTemplateRoutes(app, deps)`, and move into it, verbatim, every route still registered inline in `app.ts` on the chain's base together with the zod schemas and helpers that only those routes use. Handler bodies, status codes, refusal reasons, response shapes and the relative registration order of the moved routes do not change.
2. Helpers those routes share with an already-moved group are imported from `routes/support.ts`; a helper used only by the moved routes goes into `routes/templates.ts`. No helper is duplicated, and `RouteDeps` is widened only by a value that more than one group reads after this move.
3. `createApp(db, options)` keeps its exported name and signature and calls `registerTemplateRoutes` at the position the inline routes occupy today relative to the other register calls, so the ordered route table is unchanged.
4. `app-routes.test.ts`: the literal expected list is not edited by this chain. The test passes before and after the move with the same list; that equality is the proof that only the registration site changed.
5. Move the tests in `app.test.ts` that exercise the moved routes, verbatim, into `packages/api/src/routes/templates.test.ts`. Tests that exercise the app boundary stay in `app.test.ts`. The total test count across `app.test.ts` and `routes/*.test.ts` equals the count on the chain's base.
6. Update importers only where the import path of a moved symbol changed; `createApp` continues to be imported from `./app.js`.

Out of scope: any change to handler behavior, validation rules, status codes, refusal reasons, response shapes, or middleware order; moving logic out of handlers into domain modules (`templates.ts`, `triggers.ts` and siblings are untouched); renaming or reordering routes; changes to the `Route:` line parsing or template instantiation semantics delivered by 9f5b5fab; changes to `test-app.ts` beyond what an import path requires; changes to any file outside `packages/api`; changes to the `dbtest` suites; operator API documentation (no route changes, so none is needed).

Constraints: `routes/templates.ts` imports nothing from `app.ts` (no circular import). A handler that fails to type-check after the move is fixed by importing the same symbol it used before, not by loosening a type. If the base has a route under these prefixes that `app-routes.test.ts` does not list, the chain stops and reports it rather than editing the list: the list is owned by whoever registered the route.

Acceptance: `app-routes.test.ts` passes with its literal list unchanged (the file's diff in this chain is empty). `grep -c "app\.\(get\|post\|patch\|put\|delete\)(" packages/api/src/app.ts` is 0. `grep -c "app\.\(get\|post\|patch\|put\|delete\)(" packages/api/src/routes/templates.ts` equals the number of inline registrations `app.ts` had on the chain's base. No file under `packages/api/src/routes/` imports `../app.js`. The sum of tests in `app.test.ts` plus `routes/*.test.ts` equals the count on the chain's base. `npm run lint`, `npm run typecheck -w @anneal/api`, and the `@anneal/api` unit and dbtest suites are green.
