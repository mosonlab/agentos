The Costs page work already delivered on branch agentos/chain/costs-efficiency-view merges to main with the backfill and live ingestion classifying every retained usage payload identically.

Background: the previous chain implemented the whole feature (per-chain cost and lead time, waste by cause, cache reads-only definition, `Session.cacheCreationInputTokens`, backfill script, pricing entries, web tables) and passed two regression rounds' repairs (NaN `costUsd` from a fixture missing `cacheCreationInputTokens`; `readProjectCosts` comparing the raw lowercase `done` status to `TaskStatus.DONE`). The third regression verdict at head 77d4861b is the unresolved reviewer finding SOL-006 / BF-004: `session-cache-backfill.ts` (`parsePayload`, `finalPair`) decides cache-split completeness with its own rule (any entry with `input !== null || output !== null` and no cache component is incomplete; a provider-bearing output-only or cost-only FINAL_OUTPUT marks the split unknown; `token()` treats JSON null as absent), while live ingestion `extractUsage` in packages/db/src/usage.ts derives `modelHasInput` from `inputTokens` / `cacheReadInputTokens` / `cacheCreationInputTokens` only, with `!== undefined`, and deliberately ignores output- or cost-only entries. For `{ modelUsage: { a: { inputTokens: 10, cacheReadInputTokens: 100, cacheCreationInputTokens: 50 }, b: { outputTokens: 7 } } }` ingestion stores 100 / 50 while the backfill returns `unknown` and leaves the row NULL; a complete split event followed by an output-only terminal event is likewise left NULL by the backfill although ingestion stored the known split. Combined with the migration's explicit-NULL rule those rows stay unpriced forever.

Changes:
1. The implementation starts by merging `origin/agentos/chain/costs-efficiency-view` at 77d4861b3a1a802f0f276b24456d31823a46b2a2 into the chain branch; every item of the previous brief (appended below as reference) stays as delivered, and this chain adds only the items below.

One shared helper in packages/db/src/usage.ts (or a sibling module both import) owns the provider-shape decoding and the completeness rule for the cache split: input-bearing fields only decide completeness; JSON null and absent are treated the same way ingestion treats them today; output-only and cost-only entries never make a split unknown. `extractUsage` and the backfill both call it, differing only in error policy (ingestion stays tolerant with diagnostics, backfill stays strict and stops on a payload it cannot parse).
3. `finalPair` in the backfill applies that rule across the session's event sequence exactly as ingestion does: a complete split followed by an output-only or cost-only FINAL_OUTPUT yields the known split; the backfill result for every retained payload equals what ingestion would store for the same payload.

## Reference: previous brief (delivered on the merged branch, unchanged)

The Costs page shows, for the selected window, a table of completed chains with lead time, busy share, repair count and cost broken down by step role; a wasted-spend figure split into operator cancellations and failures by failure class; and per-agent cache figures that count cache reads only, with the uncached input spend next to them.

Background: the Costs page (`GET /projects/:projectId/costs`, `aggregateCosts`) aggregates by run, agent, model and day. The unit the operator dispatches and pays for is a chain (`Task.chainId`), and nothing on the page answers what one chain cost, how long it took, or where its time went. Recomputing this by hand from the board on 2026-08-31 (30 days, 112 chains) showed median lead 131 min against median cost $4.8 and a correlation of 0.14 between the two: lead time is lost in waiting, not in model work, and the page cannot show that. The same recomputation showed that "Wasted spend" ($413) mixes two populations: environment failures concentrated on 2026-08-16..17, and operator cancellations after 2026-08-21 that are decisions, not defects; the single figure cannot be acted on. Third, `Session.cachedInputTokens` holds cache reads plus cache creations for Claude and PI (the usage extractor adds `cacheReadInputTokens` and `cacheCreationInputTokens` into one column) but reads only for Codex (`cached_input_tokens`), so the by-agent `cachePct` compares different quantities across providers (Opus reviewers show 99.9%, Sol reviewers 94.6%, and the gap is mostly the definition). Cache creation for Claude is billed above the uncached rate, so the column also hides cost rather than showing it. Provider-reported `costUsd` is authoritative where present and the split does not change any priced total. Repair tasks (`Autonomous merge tail: gate-fix | refresh-conflict | review-fix`) carry no `Task.chainId`; the board resolves them through the repair marker's regression task using `readRepairChainByTask` (with `repairBinding` as the pure projection helper). Step identity comes from `stepRole({ outputKind })`, not from task names.

Changes:
1. Session usage contract: add `Session.cacheCreationInputTokens` (nullable Int). After this change `cachedInputTokens` means cache reads only; `cacheCreationInputTokens` means cache writes; `inputTokens` stays the canonical total (uncached + reads + creations) and `totalTokens` is unchanged. The usage extractor sets the new column from Claude `modelUsage.cacheCreationInputTokens`, Claude top-level `cache_creation_input_tokens`, and PI `cacheWrite`; for Codex it sets 0 (Codex reports no write component). Null means the split is unknown, never zero.
2. Backfill: a one-shot, idempotent script that, for every existing Session with a null `cacheCreationInputTokens`, re-derives the read/creation pair from the retained SessionEvent payload the extractor already reads for terminal usage, and rewrites `cachedInputTokens` and `cacheCreationInputTokens` accordingly. Sessions whose retained events carry no such pair are left with a null creation column and counted in the script's summary line; the script stops on a payload it cannot parse rather than skipping it silently. Document how to run it next to the other operator db commands.
3. Costs response, by agent: `cachePct` = reads / `inputTokens` over runs whose creation column is non-null; add `cacheUnknownRuns` (runs excluded because the split is unknown); add `uncachedInputTokens` (sum of `inputTokens - cachedInputTokens - cacheCreationInputTokens` over runs with a known split) and `uncachedInputUsd` (that count priced at the model's table input rate; null when the pricing table has no entry for the model). The web by-agent table shows Cache % and Uncached input $ side by side; unknown-split runs are shown as a count, not folded into the percentage.
3a. Token pricing table: add `claude-opus-5` (input 5, cached input 0.5, output 25 USD per million) and `claude-fable-5` (10, 1, 50) next to the existing gpt-5.6 entries, with the official pricing page cited in the same comment block. `modelNameForPricing` already strips the effort suffix and provider prefix, so `claude-opus-5:high` resolves to the new entry. Provider-reported `costUsd` remains authoritative for a run's total; the entries feed `uncachedInputUsd` and the estimate for a Claude session that reported tokens without a cost. Cache creation has no column in the table and is not priced by it.
4. Costs response, waste: add `waste: { totalUsd, operatorCancelledUsd, failedUsd, byFailureClass: [{ failureClass, usd, runs }] }` over the same terminal non-SUCCEEDED set that produces `wastedUsd`. A run is operator-cancelled when `Run.cancelRequestId` is set; every other member is failed and grouped by `Run.failureClass` (null class grouped as `unclassified`). `operatorCancelledUsd + failedUsd` equals `wastedUsd` exactly. The web tile shows the two figures and expands the failed side by class.
5. Costs response, chains: add `chains: [...]` for chains whose last run ended inside the window and whose chain tasks are all terminal. Each row: `chainId`, `chainName`, `taskCount`, `leadMinutes` (first run `startedAt` to last run `endedAt` over every run of every task in the chain, including bound repair tasks and retried runs), `busyMinutes` (sum of run durations over the same set), `busyPct`, `repairs: { gateFix, refreshConflict, reviewFix }`, `costUsd`, `costByRole` (one amount per `StepRole` present, plus `repair` for bound repair tasks and `unpriced` runs counted separately as `costUnavailableRuns`), and `longestGap: { minutes, beforeTaskName }` (largest interval between one run's `endedAt` and the next run's `startedAt` in chain time order). Repair tasks are attached through the same binding the board uses; the helper may be moved to a shared module but board output must not change. In-flight chains are excluded, not shown partially.
6. Web: a "Chains" table on the Costs page below Daily spend, sorted by lead time descending by default, sortable by cost, with `costByRole` visible per row (expand or inline bars) and the chain name linking to the existing chain view where one exists. It follows the page's window and refresh controls.
7. Model and agent totals, `totalUsd`, `estimatedUsd`, `runCount`, `topRuns`, and the daily chart keep their current values and shapes; the new fields are additive.

Out of scope: the spend threshold notification (its own Parked card); PI-priced models in the token pricing table (PI reports its own cost per message); a cache-creation price column; any task-type or work-category label; routing or tier changes for any agent; changes to Top runs; changes to the chain detail page or the board's chain aggregate card; per-turn cache-loss analysis from SessionEvent (a separate investigation); retention or pruning of SessionEvent; the `tz` and `days` validation rules; the `cachePct` behaviour of the board's per-task cost line beyond what the shared serializer already does.

Constraints: no silent fallback anywhere in this chain: an unknown cache split is null and counted, never treated as zero; a chain whose runs cannot be priced shows the priced part and the unpriced count, never a fabricated total; a malformed retained payload stops the backfill with the session id. The waste split and the chain cost roles must reconcile exactly with the existing totals they partition.
