# BRIEF: Document the operator exit for a merge tail stopped after its automatic repair budget

Date: 2026-09-01. Ruling: Moson chose option A (documentation only, no new operator action) for card cmthxp5zs835kmpxn7w1dwt08. Routing: direct-engineer-workflow.

An operator who finds a Regression verification step parked in REVIEW after the automatic repair budget is exhausted can read, in the operator handbook, exactly what is refused and the one supported way to carry the delivered branch forward.

Background: when a regression verdict fails and `MAX_MERGE_TAIL_REPAIR_ATTEMPTS` (packages/db/src/merge-tail.ts) review-fix or gate-fix attempts have already been opened for the chain, `settleMergeTailCompletion` stops the tail: the regression task parks in REVIEW with failureReason "semantic regression FAIL on chain head <sha> after N automatic repair attempts" (or the merge-gate variant), and a stop notice is written to the Inbox. From that state `POST /tasks/:taskId/retry` on the regression task opens a Run that `regression-repair-handoff` fails at claim time as `handoff-invalid` ("no successful review-fix result binds <head> to <base>"), and `PATCH /tasks/:taskId` with a status is refused with "Chain task statuses are controlled by chain execution". Neither refusal is a defect: the ceiling is the rule. The supported exit, exercised on 2026-09-01 for chain 3ef787b5, is a new direct chain whose brief merges the delivered branch as its first change and states the remaining defect as its scope; the old chain is held and its tasks archived. docs/operator-api.md documents hold, resume, delete, retry and archive individually but never says which of them apply here or in what order. docs/BRIEF-TEMPLATE.md has no pattern for a brief that starts from a delivered branch.

Changes:
1. docs/operator-api.md gains one subsection, placed directly after the `POST /tasks/:taskId/chain/resume` section and before `PATCH /tasks/:taskId`, titled "Recovering a merge tail stopped after its repair budget". It states the parked state and its exact failureReason shapes, names the two refusals above verbatim as expected behaviour, and gives the ordered recipe: (a) read the regression task output and the stop notice to confirm the last verdict is a real defect; (b) `POST /tasks/:taskId/chain/hold` on any task of the chain with a `reason` naming the successor chain; (c) instantiate a new direct chain on the same repo with a fresh `branchName`, whose brief follows the pattern in change 2; (d) `POST /tasks/:taskId/archive` on every task of the old chain; (e) never edit rows in the database to reopen the loop. Each step carries a curl example in the file's existing style.
2. docs/BRIEF-TEMPLATE.md gains one subsection under "Skeleton" (or a sibling section after it) titled "Continuing from a delivered branch", stating that Change 1 of such a brief is a plain merge of `origin/<old branch>` at a pinned commit sha, that the remaining Changes cover only the defect that stopped the previous chain, that the previous brief is appended verbatim under a "Reference" heading so reviewers can judge the merged diff against it, and that Acceptance must include "the chain branch contains <sha> as an ancestor" plus the previous brief's acceptance criteria unchanged.
3. Both files cross-reference each other at the new subsections.

Out of scope: any new API route, UI control, or change to `MAX_MERGE_TAIL_REPAIR_ATTEMPTS`; changes to `regression-repair-handoff` or task-move authority; documenting DB-level recovery; touching any other section of either file; README or zh-CN pages.

Constraints: prose states what the platform does today, verified against the code paths named above; no emoji or decorative symbols; keep the file's existing heading levels, curl style and English-only convention.
