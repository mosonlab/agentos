Adding a Prisma migration no longer edits `packages/db/src/release-migrate.ts`; the recorded release-candidate tail is bumped only when a release is cut, and `db:migrate:release` still stops on any checkout whose migration tail is not the recorded candidate.

Background: `RELEASE_CANDIDATE_MIGRATIONS = { count, terminal }` in `packages/db/src/release-migrate.ts` records the migration tail of the release candidate. `releaseMigrate` (both `--fresh` and `--existing`) reads the tail on disk with `readMigrationTail` and stops with `migration-tail` unless count and terminal are exactly equal to the pin; that runtime rule is the guarantee documented in `docs/release/migration-and-recovery.md` ("shorter or longer" is a stop). The pin's own comment states that updating the two values "is part of adding a migration", and `release-migrate.test.ts` (around line 512) asserts that the pin equals the tail on disk, so every PR that adds a migration must also edit these two lines to keep the unit gate green. Replaying the refresh conflicts of 2026-08-24..31 with `git merge-tree` shows this file as the single largest conflict source: 7 of 19 refresh-conflict repairs conflicted on exactly these lines, because any two concurrent chains that each add a migration both rewrite them. The consumers of the pin are the release install path (`npm run db:migrate:release -- --fresh` in `docs/release/developer-preview.md`) and the upgrade path (`--existing`); the quiet-window auto-deploy pipeline does not run `db:migrate:release` (no reference under `scripts/deploy/`). The `chore(release): prepare Anneal v0.6.0` commit (d422f513) did not touch the pin; pins were bumped in the migration PRs themselves (`fix(db): record ... migration tail` commits).
