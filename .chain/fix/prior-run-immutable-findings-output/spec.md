# BRIEF: Run completion accepts an immutable findings output authored by a prior Run

Date: 2026-09-01. Origin: chain 2a97bb93 step "Code review (Sol)" (task cmthbwr0y0tfqmpxn074fxl9h) parked in REVIEW with no operator exit after its first Run was LOST. Routing: direct-engineer-workflow.

A canonical review step whose findings artifact was persisted by an earlier Run of the same task completes and advances the chain on a later Run instead of parking in REVIEW.

Background: `sol-findings` and `blind-findings` outputs are immutable once persisted (`outputIsImmutableOncePersisted` in packages/api/src/canonical-task-output.ts): `persistSessionTaskOutput` answers a second write with 409 "task output is immutable once persisted", the session status route reports `outputSatisfiedByPriorRun: true`, and the runner skips remediation and reports success (`TASK_OUTPUT_REMEDIATION_SKIPPED`). `run-completion.ts` agrees: `missingOutputReason` excludes an immutable prior-Run output, so the completion is `succeeded`. But `canonicalOutputRefusal` (canonical-task-output.ts, the `output.runId !== runId` check) still refuses with "<kind> task output belongs to prior Run <id>, not current Run <id>", and completion parks the task in REVIEW with that failureReason. On 2026-08-31 Run 1 of the Sol review persisted its findings at head c98b3b06 and was then LOST because the API stopped answering for twenty minutes (lease expired); Runs 2, 3 and 4 each redid the review, hit the 409, and were parked by that refusal. Operator `retry` repeats the loop; `PATCH status` is refused for chain tasks. The three authorities (session status, completion missing-output rule, canonical refusal) disagree, and the disagreement has no exit.

Changes:
1. In `canonicalOutputRefusal`, a persisted output that belongs to another Run is accepted when `outputIsImmutableOncePersisted(step)` holds, `output.kind === step.outputKind`, `output.commitSha === completionHeadSha`, and the body passes `canonicalBodyRefusal` for that step; the existing kind, head-binding and body refusals still apply to it in that order. For every canonical step that is not immutable the "belongs to prior Run" refusal is unchanged.
2. A completion accepted through item 1 settles exactly like one whose own Run authored the output: task DONE, `activateChainSuccessor` runs, the persisted output row keeps its original `runId`, and one control-plane activity on the task records that the canonical output was satisfied by the prior Run (name that Run id in the body).
3. A persisted immutable prior-Run output whose `commitSha` differs from the completion head is still refused with the existing "is bound to <sha>, not completion head <sha>" message and the task still parks in REVIEW.
4. dbtest coverage in packages/api/src/run-output.dbtest.ts: extend the existing test "an immutable prior Run output disables remediation and explicitly satisfies the task" so the second Run completes with `succeededCompletion` at the same head and the test asserts task DONE, output `runId` equal to the first Run, the activity from item 2, and no "belongs to prior Run" activity; add the item 3 negative case; keep the existing `implementation`-kind retry test (the one asserting `/belongs to prior Run/`) passing unchanged.

Out of scope: why the API stopped answering (lease starvation, request timeouts); runner lease or heartbeat timing; skipping the agent session entirely when `outputSatisfiedByPriorRun` is already true at claim time (report it as a follow-up if the diff makes it obvious, do not implement); regression-verification outputs and `regression-repair-handoff`; merge-tail repair budgets; operator PATCH authority over chain task statuses; any change to `persistSessionTaskOutput` or the 409 immutability rule.

Constraints: no silent fallback: an immutable prior-Run output is accepted only under the exact conditions in item 1, and every other mismatch keeps its current named refusal. Completion never restamps, copies or synthesizes an output row. Behaviour for non-immutable canonical steps is byte-for-byte unchanged.

Acceptance: the extended dbtest and the new negative dbtest pass; the existing implementation-kind retry dbtest still asserts `/belongs to prior Run/`; `npm run lint` is green; the api package unit and dbtest suites are green; a chain fixture where the Sol review step's first Run persisted findings and failed, and the second Run completes SUCCEEDED at the same head, ends with the review task DONE and the next layer's task activated.
