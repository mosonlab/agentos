Workflows: a control-plane step cannot be staffed, and a repair card never falls back to a hidden role

Goal: the staffing editor and the API tell the truth about who executes a step: the merge-readiness step shows no agent picker and refuses profile entries, and a merge-tail repair card is assigned only to an agent the chain actually staffed.

Background: the merge-readiness step (`outputKind: merge-authorization`, recognised by `isMergeReadinessStep` in `packages/db/src/merge-tail.ts`) is executed by the control plane; its template prompt says "No model run executes it" and `chainExecutionOwner` in `packages/api/src/chain-execution-owner.ts` already reports it as `control-plane`. Its template frontmatter still binds `review-coordinator-astra-medium` because a task row needs an assignee, so `WorkflowsPage`'s profile editor in `apps/web/src/pages/Workflows.tsx` renders an Agent picker for it exactly like an agent step, and `staffingAssigneeRefusal` in `packages/api/src/staffing-profiles.ts` accepts a profile entry for it. An operator reads that as "Astra runs merge authorization" and may change it expecting an effect; it has none. Separately, `mergeTailRepairAssignee` in `packages/api/src/merge-tail-actions.ts` assigns `review-fix` and `gate-fix` repair cards to the chain's fixed-implementation step agent, but when the chain has no such step it silently falls back to the hard-coded role `FIX_IMPLEMENTATION_ROLE` (`senior-dev-astra-medium`). Every current template has the step, so the fallback only fires for a chain from a retired generation or a cloned template without it, and then it staffs work with an agent nobody configured.

Changes:
1. `GET /projects/:projectId/task-templates` and `GET /task-templates/:templateId` add to every step a string `executionOwner` with the values `chainExecutionOwner` already defines (`agent`, `human`, `control-plane`, `merge-executor`), computed on the server from the step; `docs/operator-api.md` documents the field on both routes in the same change.
2. The profile editor renders a step whose `executionOwner` is `control-plane` without an Agent picker, showing one hint sentence (i18n key in `apps/web/src/locales/en.ts` and `zh.ts`) that the control plane runs this step and no agent is staffed; the `merge-executor` step keeps its existing sentinel treatment; `human` steps keep the existing hint. The console does not decide ownership by matching output kinds or names.
3. `staffingAssigneeRefusal` refuses a profile entry that names an agent for a control-plane step with a new code `staffing_profile_step_control_plane`, reported through the same 400 shape as `staffing_profile_step_not_agent`; an entry with `assigneeAgentId: null` for that step stays allowed as today.
4. `mergeTailRepairAssignee` no longer falls back to `FIX_IMPLEMENTATION_ROLE`: when `review-fix` or `gate-fix` repair finds no fixed-implementation task on the chain, the repair is not created and the merge tail stops with the existing stop path, posting an inbox notice that names the chain and the missing step. The `refresh-conflict` route to `merge-resolver-opus-medium` is unchanged. The `FIX_IMPLEMENTATION_ROLE` constant is deleted.
5. `docs/operator-api.md` "Staffing profiles" lists the new refusal code, and the merge-tail documentation names the new stop reason.

Out of scope: the template frontmatter `agent` of the readiness step (a task row still needs an assignee; the binding stays but is no longer presented as staffable); any change to how readiness is executed; the Workflows list page delivered by chain 7f0c65cc; renaming steps (chain 5034a0f6); repair budget or repair-round rules.

Constraints: fail loud, no silent substitution of an agent; existing profiles that already carry an entry for the readiness step are not migrated silently, the PUT that next saves them is refused with the new code and the message names the step to remove; API and console agree through the `executionOwner` field only.

Acceptance: `packages/api/src/routes/templates.test.ts` asserts `executionOwner` values for an agent step, the readiness step, the merge-execution step and a human step on both routes; a staffing-profiles test asserts the new refusal for an agent entry on the readiness step and acceptance of a null entry; `apps/web/src/tests/workflows.test.tsx` asserts the readiness step renders the hint and no picker while an agent step still renders a picker; a merge-tail test asserts that a chain without a fixed-implementation step stops with the named notice instead of creating a repair card assigned to `senior-dev-astra-medium`; `git grep FIX_IMPLEMENTATION_ROLE` returns nothing; `npm run test -w @anneal/api`, `npm run test -w @anneal/web`, `npm run lint`, `npm run typecheck` and `npm run test:snapshot-scan` pass.

Route: implementation=frontend-dev-opus-medium - a console surface change carried by one read-only API field and two small API refusals; frontend work by the routing contract
