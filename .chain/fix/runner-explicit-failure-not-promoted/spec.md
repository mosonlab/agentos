The runner's post-delivery disconnect recovery accepts only a genuine stream loss after a server-verified delivery; an explicit provider failure with exit code 0 and persisted output stays FAILED.

Route: implementation=senior-dev - cross-package contract change (API output-status response plus runner success authority) and a success-decision boundary that the acceptance suite cannot witness without deliberate adversarial fixtures.

Background: PR #345 (fix/runner-post-delivery-disconnect, merged 2026-08-31) added post-delivery disconnect tolerance in packages/runner/src/runner.ts. The candidate condition is `exitCode === 0 && signal === null && terminationReason === null && (!terminalEventSeen || !terminalSuccess) && ...`. The second disjunct means an adapter that observed an explicit unsuccessful terminal event (Claude `result` with `is_error: true` or `terminal_reason !== "completed"` in adapters/claude.ts, Codex `sawError` in adapters/codex.ts, PI `agent_settled` with `finalAttemptFailed` in adapters/pi.ts) is still a disconnect candidate. When `readSessionTaskOutputStatus` reports `outputPersisted` and the workspace file `.agentos/task-output-receipt.json` (written by the runner MCP server on delivery, Agent-writable) matches runId/kind/HEAD, `postDeliveryDisconnectTolerated` becomes true and `executionSucceeded` is granted, so a Run the provider explicitly failed is completed as SUCCEEDED and the chain advances on its output. The control-plane response (`packages/api/src/routes/session.ts`, task output status) exposes only the boolean `outputPersisted` and `outputKind`; the persisted `TaskStepOutput` row already stores `runId`, `kind`, and `commitSha` but never returns them, so the local receipt is the only evidence binding the delivery to a commit, and it lives in a directory the Agent can rewrite. `classifyRuntimeError` in adapters/runtime.ts maps `exitCode === 0 && (!terminalEventSeen || !terminalSuccess)` to PROTOCOL_ERROR, which is the class a real post-delivery stream loss currently lands in.

Changes:
1. Split the two cases the runner currently conflates. Recovery is a candidate only when `terminalEventSeen === false` (no terminal event at all). When `terminalEventSeen === true && terminalSuccess === false`, the Run is FAILED through the existing failure path regardless of exit code, persisted output, or receipt; `providerError` from the adapter is preserved as the failure reason.
2. Extend the session task-output-status response with the server-side receipt identity of the persisted output: `output: { runId, kind, commitSha }` read from `TaskStepOutput` (null when nothing is persisted for this Run). `outputPersisted` keeps its current meaning (`stepOutput.runId === run.id`).
3. Make the server-side identity the authority for recovery: recovery is accepted only when the response reports `outputPersisted === true`, `output.runId === claim.run.id`, `output.kind === "result"`, and `output.commitSha` is a 40-hex sha equal to the captured workspace HEAD. The local receipt file is read only to be included in the audit payload (Change 5); its absence, mismatch, or malformation no longer changes the success decision and no longer throws.
4. Emit one dedicated runner event `POST_DELIVERY_DISCONNECT_ACCEPTED` on every accepted recovery, carrying `runId`, `commitSha`, `providerError`, `terminalEventSeen`, and the local receipt (or the reason it could not be read). The existing `POST_DELIVERY_DISCONNECT_CHECK_FAILED` event and the tolerated-disconnect activity line remain for the rejected and accepted paths respectively.
5. Add a maintenance command (packages/api or packages/db script, wired like the existing session-cache-backfill command) that lists Runs completed as SUCCEEDED since the #345 merge commit whose session events contain a terminal event with an explicit failure followed by the tolerated-disconnect activity line. Output is a table of runId, taskId, chainId, providerError; the command changes nothing. Run it once against the production database during Regression verification and record the result in the step output.

Out of scope: the shape or wording of adapter terminal parsing beyond reading the existing `terminalEventSeen`/`terminalSuccess`/`providerError` fields; retry policy and failure classification for FAILED Runs (classifyRuntimeError stays as is); merge-tail repair kinds; the receipt writer in mcp-server.ts and the receipt file format; any change to cancellation, lease-loss, budget, or remediation failure paths; repairing or re-running any Run the audit command lists.

Constraints: fail closed - every ambiguity in the recovery check resolves to FAILED, never to SUCCEEDED; the runner must not need the workspace receipt to complete a successful recovery, and must not be able to be talked into success by anything written under the workspace; the API response extension is additive (existing fields unchanged) so an older runner keeps working against the new API; no new database columns or migrations.

Acceptance:
- Runner unit tests: for each adapter fixture (Claude `result` with `is_error: true`; Codex turn failure; PI `agent_settled` with a failed final attempt) with `exitCode: 0`, `outputPersisted: true`, matching server-side `output.{runId,kind,commitSha}`, and a valid local receipt, the Run ends FAILED with the adapter `providerError` as the failure reason and no `POST_DELIVERY_DISCONNECT_ACCEPTED` event.
- Runner unit test: `terminalEventSeen: false`, `exitCode: 0`, matching server-side identity, receipt absent -> SUCCEEDED, exactly one `POST_DELIVERY_DISCONNECT_ACCEPTED` event whose payload records the missing receipt.
- Runner unit tests: `terminalEventSeen: false`, `exitCode: 0`, and server-side identity with (a) `output` null, (b) `runId` of a different Run, (c) `kind !== "result"`, (d) `commitSha` differing from the captured HEAD, (e) a non-40-hex `commitSha` -> FAILED in every case even with a local receipt that matches everything.
- Runner unit test: a local receipt rewritten to match a mismatched server-side identity does not change the FAILED verdict.
- API test: task-output-status returns `output: { runId, kind, commitSha }` when a `TaskStepOutput` row exists for the Run and `output: null` otherwise; all previously returned fields are unchanged.
- Existing runner suites for cancellation, lease loss, budget exhaustion, and remediation failure are green and unchanged.
- The audit command runs against the test database with one seeded promoted-failure Run and one seeded genuine-recovery Run and lists only the former; a production run during Regression verification is recorded in the step output with its row count.
- Lint (`npm run lint`), typecheck, and the exact merge gate pass.
