A run whose agent has already delivered its result survives a provider stream death at exit: the runner promotes it to SUCCEEDED instead of discarding finished work as PROTOCOL_ERROR.

Background: when the provider CLI exits with code 0 but the stream died before the terminal event (codex: no turn.completed after "stream disconnected before completion"), classifyRuntimeError in packages/runner/src/adapters/runtime.ts returns PROTOCOL_ERROR and the runner treats the run as failed: work is salvaged to the per-run salvage branch instead of the configured branch, and downstream consumers (merge-tail settle, regression-repair-handoff) see a failed run even though the agent had already committed its head and persisted its result task output. Incident 2026-08-31, gate-fix repair cmtha0req0j6smpxnpoec86we (chain 747a727b): 70 minutes of finished, pushed, output-persisted repair work was discarded; the platform requeue then re-ran the whole session and operator retries of the regression task were rejected as handoff-invalid until it finished.

Route: implementation=senior-dev - the change rewrites the runner's success/failure contract consumed by merge-tail settle and salvage; wrongly promoting a cut-off agent is a cross-module hazard the green suite does not witness directly.

Changes:
1. In the runner's run-completion path, promote a run to SUCCEEDED when ALL of: (a) the CLI exited with code 0, no terminationReason, not timed out, and the terminal event is missing or unsuccessful (the shape that today classifies as PROTOCOL_ERROR); (b) this run has a persisted result-kind task output; (c) that output's commitSha is an exact 40-hex sha equal to the workspace HEAD at exit. On promotion the run takes the normal success path end-to-end: delivery pushes to the configured branch (not the salvage ref), session settles as succeeded, and no failure envelope is recorded.
2. On promotion, append a runner-stream activity line to the task recording that a provider disconnect after delivery was tolerated, including the providerError text, so operators can see it happened.
3. Any run failing (a), (b), or (c) keeps today's behavior exactly: classification, failure envelope, and salvage unchanged.
4. Unit tests in packages/runner cover: the promoted combination; exitCode 0 with no persisted output stays FAILED; persisted output whose commitSha differs from HEAD stays FAILED; nonzero exit with persisted output stays FAILED; terminationReason or timeout with persisted output stays FAILED.

Out of scope: adapters/codex.ts reconnect latching (isReconnectStatus) and every other adapter's event parsing; settleMergeTailCompletion, stopMergeTail, and regression-repair-handoff in packages/api (a promoted run is an ordinary success to them); the platform requeue mechanism (recordMergeTailRequeue); retry/resume semantics; salvage ref naming; spend accounting.

Constraints: the predicate must be conjunctive and narrow - no promotion on partial evidence, budget-exceeded runs, cancelled runs, or nonzero exit codes; when in doubt the run stays failed. Fail loudly: if the promotion path itself errors (output lookup, HEAD resolution), the run fails with the original classification and the error is reported, never swallowed.
