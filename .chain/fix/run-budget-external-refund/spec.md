A Run that fails because of a provider transport fault or a git transport or credential fault no longer spends the Task's session budget, its failure reason names the fault, and four misclassified failure texts land in the right FailureClass.

Background: A Task's Run budget is `maxSessionsPerTask + budgetGrants` (`packages/db/src/run-open.ts`, `runBudgetCeiling`). `packages/api/src/run-completion.ts` refunds one attempt (`refunded = external && !mechanical`) only when the envelope's `externalFailure` is true, and `packages/api/src/execution.ts` (`envelopeExternalFailure`) sets that only when the agent never exited or the phase is not `EXECUTE`. A missing-output refusal forces `external = false`. Consequences observed 2026-09-01 to 2026-09-02 on production (56 failed Runs audited):

- A mid-session provider transport drop (`fetch failed`, classified `TRANSIENT_PROVIDER` through `TRANSIENT_NETWORK_PATTERNS`) exits the agent cleanly with exit code 0 in phase `EXECUTE`, so it spends an attempt. Six such Runs in two days; the failure rate through the host's proxy is a steady background rate, not an incident.
- A Regression verification step whose `regression-verification.sh` `prepare` or `finalize` dies on `target fetch failed` (the `fetch_base` loop, then `die "cannot refresh target head"`) exits cleanly with no handoff; `packages/runner/src/runner.ts` reports `A step declaring output kind '<kind>' finished without a current-Run mechanical output handoff for Run <id>` with event `TASK_OUTPUT_REMEDIATION_UNAVAILABLE` reason `mechanical-handoff-absent`, classified `PROTOCOL_ERROR`, and the missing-output rule spends an attempt. Sixteen such Runs across ten tasks from one credential defect (since fixed by PR #395 and #415); task `cmtjklnnc0gnfmpfittxaxcyl` reached 14 Runs only because the operator raised `maxRunsPerTask` from 5 to 16 by hand. The real git error (`could not read Username`, `git-credential-runner.sh: No such file or directory`) appears only in tool output, never in `failureReason`.
- `not-authenticated: the CLI's own login check did not pass (exit 2)` (pi adapter, `PROVISION` phase) does not match `CLI_AUTH_PATTERN` and lands as `TASK_FAILED`, non-retryable.
- `gh failed (1): Post "https://api.github.com/graphql": EOF` in `DELIVER` lands as `TASK_FAILED`, non-retryable, although it is the proxy closing the socket.
- `PROVIDER_OUTAGE_PATTERN` is `/provider outage|\b5\d\d\b/`; on Run `cmtjqnoj711hqmpfirejubfdi` it matched the stack-trace line number in `node:events:526:24`, so the class was right by accident.
- `isCodexReconnectStatus` (`@anneal/db`, consumed by `packages/runner/src/adapters/codex.ts`) accepts `Reconnecting... N/M (cause)` since PR #403 but still rejects `Reconnecting... waiting for network (...)`, which carries no counter; two hits on 2026-08-28.

Changes:
1. Refund rule. A failure whose FailureClass is `TRANSIENT_PROVIDER` because the verdict text matched `TRANSIENT_NETWORK_PATTERNS` or `PROVIDER_OUTAGE_PATTERN` is external in every phase, including `EXECUTE` with a clean agent exit. A missing-output refusal for a `regression-verification-v2` step whose block reason (change 3) is `target-fetch-failed` is also external. Every other missing-output refusal keeps `external = false`.
2. Refund cap. Refunds granted under change 1 are capped per Task at 3 (a named constant in `packages/db/src/run-open.ts` beside `runBudgetCeiling`); a fourth such failure spends normally and the completion writes a TaskActivity line stating that the external-failure refund cap was reached. Refunds already granted for non-`EXECUTE` phases keep their existing behaviour and do not count toward this cap.
3. Machine-readable block reason. When `regression-verification.sh` dies on `cannot refresh target head` (any of its three `fetch_base` call sites), it writes a block record under the same per-Run handoff location that `readRegressionOutputHandoff` already reads, with `reason: "target-fetch-failed"` and the last git stderr line. `packages/runner/src/runner.ts` includes that reason and stderr line in `terminalFailureReason` and in the `TASK_OUTPUT_REMEDIATION_UNAVAILABLE` event payload when the handoff is absent; when no block record exists, the message is unchanged.
4. `CLI_AUTH_PATTERN` also matches `not-authenticated: the CLI's own login check did not pass`, so that text classifies as `AUTH_REQUIRED`.
5. `TRANSIENT_NETWORK_PATTERNS` also matches `Our servers are currently overloaded`, `try again later`, and a transport `EOF` reported by `gh` or `git` (`Post "<url>": EOF`, `unexpected EOF`); the `gh` graphql EOF in `DELIVER` classifies as `TRANSIENT_PROVIDER` and is retryable.
6. `PROVIDER_OUTAGE_PATTERN` matches a 5xx only in an HTTP context (status word or `HTTP`/`status` prefix); `node:events:526:24` alone no longer matches.
7. `isCodexReconnectStatus` also accepts `Reconnecting... waiting for network (<cause>)`; the codex adapter does not set `sawError` for it.

Out of scope: retry backoff and `retryAt` scheduling; stall and tool deadlines; the default `maxSessionsPerTask`; merge-tail repair card budgets (PR #404); workspace salvage and replacement Runs; the runner-side `network-retry.ts` attempt counts; `FETCH_ATTEMPTS` in `regression-verification.sh`; any change to the completion wire contract shape; the merge executor.

Constraints: refunds are never granted for `NO_CHANGES_PRODUCED`, `BUDGET_EXCEEDED`, `TASK_FAILED`, or any failure the runner marked mechanical. A refund decision and the cap are both visible in the Run's completion record and in TaskActivity; nothing falls back silently. Existing `*.dbtest.ts` coverage is merge gate evidence and is not run inside a Run.
