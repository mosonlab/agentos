A merge executor whose completion contract differs from the API it claims from is refused at claim time with a recorded reason, and a rejected completion is a visible TaskActivity fact instead of a Run that sits in `running` until the stall timeout declares it lost.

Background: The merge executor (`packages/merge-executor`) is a separately built process; it is not carried by auto-deploy. PR #417 (commit `636d33fb`, merged 2026-09-02 16:05Z) changed the Run completion wire contract (`terminalEventSeen`/`terminalSuccess` removed, `outcome: {case}` added, required at `packages/api/src/run-completion.ts`). The API deployed with it while the executor kept the old build. On 2026-09-02 23:09Z, 23:19Z, and 23:29Z the same Merge execution task (`cmtjj2laz0cvimpfi11gylgtr`) produced three Runs: each merged within ten seconds (TaskActivity `Mechanical merge completed as 5ca5aa3a...`), then `agentos.complete` got a 400, the catch path in `packages/merge-executor/src/index.ts` called `complete` again with the same shape, got the same 400, logged `completion after crash failed`, and cleared its heartbeat interval. Each Run stayed `running` with `heartbeatAt` frozen at claim time and zero SessionEvents until the platform judged it `lost` after the 10-minute stall window. The chain finished only after an operator answered the resulting stop. The existing guard `MechanicalApiIncompatible` (`index.ts`, checked on the first heartbeat's `mechanicalCancellationPolicy`) protects only the direction new executor plus old API; the direction old executor plus new API has no guard. PR #429 made the 400 body visible in logs and is diagnostic only.

Changes:
1. A completion contract version is declared once in `@anneal/db` beside the claim contract (`packages/db/src/claim-contract.ts`) and the run completion input type, as a named constant that every change to the completion input shape must bump; the executor and the API both read it from the package.
2. The mechanical claim request from the executor carries its contract version. The API refuses a mechanical claim whose version does not match its own with `409 Conflict`, code `mechanical_contract_mismatch`, a message naming both versions, and no Run is claimed or created for it. The refusal writes a TaskActivity on the task that would have been claimed, naming both versions, so the board shows why the step is not moving.
3. On that 409 the executor logs at error level with both versions and stops claiming (the polling entry returns a named result distinct from `idle`); it does not retry the claim in a loop.
4. When `agentos.complete` returns a non-2xx status, the executor writes a TaskActivity on the Run's task carrying the status and response body before it gives up, and the log line carries the same. The completion is attempted once more only if the first attempt failed with a network error, not for a 4xx.
5. `docs/operator-api.md` documents the claim request field, the `409 mechanical_contract_mismatch` refusal, and the TaskActivity it writes, in the same change.

Out of scope: adding the executor to auto-deploy or any deploy script; changing the completion payload shape or the `outcome` vocabulary; the agent (non-mechanical) runner claim path; the stall timeout and the lost-Run judgement; the existing `MechanicalApiIncompatible` heartbeat check, which stays as is; GitHub App installation or token minting.

Constraints: the version check is fail-closed; a claim without a version from a mechanical executor is refused the same way as a mismatched one. No silent fallback to the old completion shape. Existing `*.dbtest.ts` coverage is merge gate evidence and is not run inside a Run.

Acceptance:
- `packages/api` unit test: a mechanical claim carrying a mismatched or absent contract version returns `409` with code `mechanical_contract_mismatch` and a message naming both versions, creates no Run, and writes one TaskActivity naming both versions; a matching version claims as before.
- `packages/merge-executor` unit test: `claimOnce` on that 409 returns the named non-idle result, logs at error level once, and issues no second claim in the same call; `agentos.complete` returning 400 causes exactly one TaskActivity write carrying the status and body and no second completion attempt; a network error on the first completion attempt causes exactly one retry.
- `@anneal/db` test: the contract version constant is exported and the completion input schema module references it.
- `docs/operator-api.md` contains the claim field and the refusal code.
- `npm run test -w packages/api`, `-w packages/merge-executor`, `-w packages/db` are green; `lint` and `typecheck` for those workspaces are green.

Route: implementation=senior-dev - cross-module contract migration between @anneal/db, the API claim route, and a separately deployed process; the hazard is a version skew the suite cannot reproduce because both sides are built from one tree.
