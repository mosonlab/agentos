Runs: An automatic retry publishes to the branch its task declares

After this chain, a Run opened by the automatic retry inside a completion transaction keeps the head branch of the Run it replaces, so a succeeded merge-tail repair retry publishes its commit to the task's shared branch instead of to a per-Run ref nothing consumes.

Route: implementation=senior-dev-luna - the rule is one branch-resolution arm in Run birth and is fully witnessed by an intent-matrix unit test plus a two-Run repair dbtest.

Background:

A merge-tail repair task is deliberately chain-detached: `packages/api/src/merge-tail-actions.ts:660-682` creates it with `chainId` null, `targetBranch` set to the source Run's branch, and then writes `branch` and `targetBranch` of its first Run to that same shared chain branch. Every repair kind — `refresh-conflict`, `gate-fix`, `review-fix` — is created by that one function.

When such a Run fails retryably, `packages/api/src/run-completion.ts:929-939` opens the replacement with the `retry-after-completion` intent. `packages/db/src/run-open.ts:834-851` resolves the new Run's branches, and for a task that is not a template chain step it takes the arm that hard-codes `branch: null` and computes only a base through `resolveRequeueBase` (`packages/db/src/run-open.ts:404-419`). That base correctly prefers publication evidence, which for a failed Run that salvaged its workspace is the per-Run ref `agentos/<taskId>/run-1` (`packages/runner/src/delivery.ts:900`). The head, however, is now null, and the runner substitutes its own fallback name at `packages/runner/src/workspace.ts:433`: `claim.run.branch ?? agentos/<taskId>/run-<n>`. The retry therefore checks out the salvage ref and, on success, pushes `agentos/<taskId>/run-2`. `/start` writes that fallback back onto the Run row (`packages/api/src/run-lifecycle.ts:142`) and completion records it as `pushedBranch` (`packages/api/src/run-completion.ts:894`), so the row looks deliberate.

The pre-refactor code named this exact hazard: the comment removed by commit `48068b0a` said a retry created with `branch: null` lets `workspace.ts` silently move it to a per-run branch, and it fixed only template chains, leaving "non-template retries retain the historical `branch: null` behavior". Chain-detached repair tasks are non-template retries that do carry a required publish head.

The consequence is a dead-ended merge tail. `packages/api/src/regression-repair-handoff.ts:153-157` requires `output.run.pushedBranch === input.branch`, and its comment at lines 158-160 states the intended contract: a failed Run may publish to a per-Run salvage ref, and the retry checks that ref out as `targetBranch` while still publishing successful repair evidence to the task's shared branch. Production run cmtmn1sre0c33mpbks5ntpxi5 (repair task cmtmmo06z0ayxmpbkt3vk0wso, kind `refresh-conflict`, chain "Runner: A runner serves only the runner kinds it declares") succeeded with head `01cea9e7` but recorded `pushedBranch=agentos/cmtmmo06z0ayxmpbkt3vk0wso/run-2` and `targetBranch=agentos/cmtmmo06z0ayxmpbkt3vk0wso/run-1`; `feat/runner-served-kinds` stayed at its pre-repair head, every regression retry failed with `repair task ... did not publish ... to feat/runner-served-kinds`, and an operator had to fast-forward the branch and edit the Run row by hand.

The asymmetry inside the same function is the proof that the null head is not a rule anyone relies on: the operator retry intent (`retry`) resolves through `resolveRunBranches`, whose non-chain arm keeps `prior?.branch ?? null` and documents why (`packages/db/src/run-open.ts:470-478`); the `retry-after-lease-loss` arm keeps `prior?.branch ?? null` as well (`packages/db/src/run-open.ts:857-861`). Only the automatic post-completion retry drops the head.

Changes:

1. In `packages/db/src/run-open.ts`, the `retry-after-completion` arm for a task that is not resolved through `resolveRunBranches` keeps the prior Run's head: `branch: prior?.branch ?? null`, replacing the hard-coded `branch: null`. The base stays exactly as it is today — `resolveRequeueBase` when a prior Run exists, otherwise `task.targetBranch ?? task.repo.defaultBranch` — so a retry still checks out the salvage ref its predecessor published while publishing to the head its predecessor declared.
2. Replace the now-obsolete rationale at that arm with the rule it enforces: publication evidence answers the base, the prior Run's head answers the head, and a null head is delegation to the runner's per-Run fallback and therefore reserved for tasks that never declared one.
3. Leave the template-chain and chain-indexed branches of the same expression untouched: they already resolve their head through `resolveRunBranches` and must keep resolving it there.

Out of scope:

- The runner's per-Run fallback at `packages/runner/src/workspace.ts:433` and the salvage ref name at `packages/runner/src/delivery.ts:900`. A failed Run must keep publishing `agentos/<taskId>/run-<n>`; do not make salvage conditional on task kind.
- `packages/api/src/regression-repair-handoff.ts`. Its `pushedBranch === input.branch` requirement is the contract this change restores, not a check to relax; do not add a per-Run-ref tolerance to it.
- `resolveRequeueBase` and `inheritedBase` base selection, including the poisoned-head fallback documented at `packages/db/src/run-open.ts:404-419`.
- Repair-card creation in `packages/api/src/merge-tail-actions.ts`, the repair budget (`maxSessionsPerTask: 2`), `MAX_MERGE_TAIL_REPAIR_ATTEMPTS`, and operator reentry in `packages/api/src/merge-tail-repair-reentry.ts`.
- Chain-detachment of repair tasks. Do not give repair tasks a `chainId` or `chainIndex` to route them through the chain branch rule.
- The workspace-reclaim and late-salvage replacement path in `packages/api/src/workspace-reclaim.ts`, including `repairReplacementAfterSalvage`.
- Operator recovery tooling and any backfill of the Run rows already written by the defect.

Constraints:

- Publication evidence keeps its current authority: only `Run.pushedBranch` may answer "what ref exists on the remote", and no code added by this change may read `branch`, `pushStatus`, or `status` as a substitute.
- The change alters head resolution only for the `retry-after-completion` intent on tasks not routed through `resolveRunBranches`. Every other intent's branch pair is byte-identical before and after.
- Fail loud: no code path may silently swap a Run's publish head for a per-Run ref. When a task declares no head, the null stays null and the runner's documented fallback owns the name.
- Run birth stays inside the caller's transaction and keeps its existing mutex and refusal behavior; no new query may be added outside the transaction.
- Two chains are in flight and own files this brief reads. `feat/runner-served-kinds` (remote head 01cea9e7) modifies `packages/api/src/run-claim.ts`, `packages/api/src/chain-branch.dbtest.ts`, `packages/api/src/workspace-reclaim.dbtest.ts`, `packages/api/src/runner-served-kinds.dbtest.ts`, `packages/api/src/runner-backend-health.dbtest.ts`, `packages/runner/src/runner.ts`, `packages/runner/src/api.ts`, `packages/runner/src/availability.ts`, `packages/runner/src/config.ts`, `packages/runner/src/index.ts`, and `packages/runner/src/runner.test.ts`. `feat/optional-template-steps` modifies `packages/api/src/run-claim.ts` and the template surface (`packages/api/src/templates.ts` and its tests). Of those, `packages/runner/src/runner.test.ts` and `packages/api/src/chain-branch.dbtest.ts` appear in this brief's Acceptance as suites that must pass unmodified: do not edit them, and do not edit `packages/api/src/run-claim.ts`, `packages/api/src/templates.ts`, `packages/api/src/workspace-reclaim.dbtest.ts`, or any file under `packages/runner/src`.
