PI runs stop persisting their streaming chunk events, so a PI run stores the same order of SessionEvent rows as a Codex run instead of 30x more.

Background: every provider line a runner reads is stored twice: once verbatim as PROVIDER_RAW (packages/runner/src/adapters/runtime.ts processProviderEvent) and once as the parsed adapter event. pi --mode json streams two kinds of incremental chunks: message_update (one per text/thinking fragment of an assistant message) and tool_execution_update (one per output fragment of a running tool, each carrying the accumulated output so far). parsePiEvent (packages/runner/src/adapters/pi.ts) forwards message_update as MODEL_DELTA and tool_execution_update as TOOL_PROGRESS. Production, 30 days: PI is 14 percent of runs but 52 percent of SessionEvent bytes (1.7 GB of 3.25 GB); a PI run averages 7,167 rows versus 236 for Codex. Of the PI rows, message_update is 716,265 x 2 rows / 578 MB and tool_execution_update is 33,547 x 2 rows / 522 MB. Neither chunk kind carries information that survives: message_end (persisted as MODEL_COMPLETED) holds the complete assistant message plus usage, and tool_execution_end (TOOL_COMPLETED) holds the complete tool output. No reader depends on them: apps/web/src/lib/session-stream.ts only consumes MODEL_DELTA for CLAUDE and CODEX and produces no item for PROVIDER_RAW or TOOL_PROGRESS; packages/db/src/post-delivery-disconnect-audit.ts reads PI failure evidence from agent_end (PROVIDER_STATUS), not from chunks. The only live use of the chunks inside the runner is liveness: emitAdapterEvent stamps state.lastProgressEventAt and the tool_execution_update branch stamps state.inFlightTool.lastProgressAt, both feeding stall detection.

Changes:
1. For PI, a message_update provider event produces no SessionEvent of any type: no MODEL_DELTA and no PROVIDER_RAW. The adapter still records progress for stall detection (state.lastProgressEventAt advances on every message_update exactly as it does today).
2. For PI, a tool_execution_update provider event produces no SessionEvent of any type: no TOOL_PROGRESS and no PROVIDER_RAW. state.inFlightTool.lastProgressAt and state.lastProgressEventAt still advance on every tool_execution_update.
3. All other PI provider events (session, message_start, message_end, turn_end, tool_execution_start, tool_execution_end, agent_end, agent_settled, error and unknown types) keep their current PROVIDER_RAW plus parsed-event pair unchanged; the usage harvest on message_end and the terminal-state logic on agent_settled are untouched.
4. The suppression is expressed at the point where the PI adapter hands an event to the runtime (a per-adapter predicate or equivalent), not by a type string filter inside the API ingest path or a database trigger. CLAUDE and CODEX adapters emit exactly what they emit today.
5. Unit tests in packages/runner/src/adapters/pi.test.ts (or the adapters test file that already exercises parsePiEvent with a captured transcript) assert: a transcript containing message_update and tool_execution_update lines yields zero events of type MODEL_DELTA, TOOL_PROGRESS, or PROVIDER_RAW with payload.type in {message_update, tool_execution_update}; the same transcript still yields MODEL_COMPLETED with the harvested usage and TOOL_STARTED/TOOL_COMPLETED pairs; and state.lastProgressEventAt is later after a message_update than before it.

Out of scope: deleting or pruning the existing PI chunk rows already in production (a separate operator SQL step, decided and run by the operator after deploy); any change to CLAUDE or CODEX event emission or to PROVIDER_RAW for non-chunk events; a general SessionEvent retention or age-based pruning mechanism; changes to the web session stream, the disconnect audit, or usage.ts; changing PI CLI flags (--mode json stays); compaction, context-window, or cache settings of either harness.

Constraints: fail loud, no silent fallback: if the runtime needs a new adapter hook to express the suppression, its absence on an adapter must be a type error, not a runtime default. The PI stall detector must observe the same progress signal it observes today; a PI run that streams a long assistant message with no other events must not be flagged stalled where it is not flagged today. No database migration.

Acceptance: `npm run lint` passes; packages/runner test suite is green; the new pi adapter tests in Change 5 exist and pass; grep of the diff shows no edits under packages/api/src, packages/db, or apps/web; a captured PI --mode json transcript fixture replayed through the adapter produces no SessionEvent whose payload.type is message_update or tool_execution_update, while the count of MODEL_COMPLETED, TOOL_STARTED, TOOL_COMPLETED, PROVIDER_STATUS and FINAL_OUTPUT events equals the count produced before the change on the same fixture.
