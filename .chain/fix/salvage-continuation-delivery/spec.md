A Run that starts from its own Task's salvaged base and correctly produces no new commit must deliver as a success instead of dead-ending the Task in REVIEW.

Background: When a Run is declared LOST while its work is already committed, `acknowledgeReclaimSalvage` publishes that work to `agentos/<taskId>/run-<n>` and records it as the lost Run's `pushedBranch` (packages/api/src/workspace-reclaim.ts). Every later Run of that Task, whether enqueued by `repairReplacementAfterSalvage` or opened by `POST /tasks/:id/retry`, resolves its clone base through the same `inheritedBase` in packages/db/src/run-open.ts, so its `baseSha` is the salvaged head. The Run snapshot's `requiresCommit` (run-open.ts, `task.templateStep?.requiresCommit ?? task.opensPullRequest`) is computed without knowing that, and `packages/runner/src/delivery.ts` fails any Run with `head === workspace.baseSha && requiresCommit` as `NO_CHANGES_PRODUCED`, which `execution.ts` treats as non-retryable. When the salvaged base already satisfies the brief in full, the correct outcome is "nothing to add", and the Task lands in REVIEW with no PR and no supported exit. Observed on task `cmti0il0s0k9gmpcheycunjm3` (chain `24573801`): Run 1 LOST after committing, salvage published `5d29993b`, Run 3 verified that base, recorded a canonical `implementation` output with `commitSha = 5d29993b`, and was failed anyway, stalling six downstream steps and the chain bound behind it. A Run whose snapshot carries `requiresCommit: false` already pushes and delivers normally with `head === baseSha` (delivery.ts honours the snapshot; production Run `cmtgiy6wn0001mp5iif5gmaae` delivered that way), so the control plane only has to set that snapshot field correctly.

Changes:
1. In `openRun` (packages/db/src/run-open.ts), the new Run's `requiresCommit` is `false` when its resolved base is the `pushedBranch` of a prior Run of the same Task (`prior.taskId === task.id` and the resolved base ref equals `prior.pushedBranch`). The decision is made once, from those two persisted facts, when the Run snapshot is created; it is never patched afterwards. It applies to every path that reaches `openRun` with an inherited base: the salvage replacement and the operator retry alike.
2. Completion of such a Run is accepted only against evidence: the Run recorded a canonical `implementation` output whose `commitSha` equals its `baseSha`. Without that output the Run fails with its existing class and reason; a clean provider exit alone is never sufficient. Reuse the existing canonical-output checks in packages/api/src/run-completion.ts and canonical-task-output.ts; do not add a parallel validator.

Out of scope: the runner (`packages/runner` is not touched; it already honours `requiresCommit` from the claim); any new column on Run or field on the claim; the lease starvation that loses a finished Run in the first place (Parked card `cmthxp5zj835g`); any operator exit from the REVIEW column; the `orphanedNoChangesOutput` path in `regression-repair-handoff.ts`; the post-delivery terminal-failure promotion under repair by chain `41706b4a`; relaxing `requiresCommit` for any Run whose base is not its own Task's prior `pushedBranch`; the `NO_CHANGES_PRODUCED` class itself, which must keep failing a Run that idled on an ordinary base.

Constraints: The relaxation is evidence-gated, never name-gated: no step name, output kind, branch-name pattern or call path may participate in the decision, only the persisted relation between the prior Run's `taskId`/`pushedBranch` and the new Run's resolved base. A Run that produced nothing on an ordinary base must still fail exactly as it does today. A salvage continuation that produces no canonical output must fail loudly rather than be waved through. Do not add a migration unless one is strictly required; the expected shape needs none.

Acceptance: `packages/db/src/run-open.test.ts` (or the nearest existing openRun test file) asserts that a Run opened with an inherited base from its own Task's prior `pushedBranch` carries `requiresCommit: false`, and that a Run opened from the target branch or from another Task's branch keeps today's value. `packages/api/src/execution.test.ts` or `run-completion.test.ts` asserts that a Run with `requiresCommit: false` and a canonical `implementation` output with `commitSha === baseSha` completes SUCCEEDED, and that the same Run without that output stays FAILED. A dbtest drives the full path: Run lost with committed work, `acknowledgeReclaimSalvage` publishes, `repairReplacementAfterSalvage` enqueues, the replacement delivers with `head === baseSha`, and the Task reaches DONE and the next chain layer activates. `packages/runner/src/delivery.test.ts` is unchanged and still asserts that `head === baseSha` with `requiresCommit` true yields `NO_CHANGES_PRODUCED`. `npm run lint`, `npm run test --workspace packages/db` and `npm run test --workspace packages/api` are green.
