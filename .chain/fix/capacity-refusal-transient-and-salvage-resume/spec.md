Runs: a provider capacity refusal is a transient external fault, and a fix step resumes from its own salvaged attempt

Goal: a Codex or Claude session that dies with "Selected model is at capacity" is retried as an external fault without consuming the task's budget, and an Apply-review-fixes Run that starts on the salvaged WIP commit of its own failed prior attempt continues without asking a human.

Background: on 2026-09-05 14:31Z two Apply-review-fixes Runs (senior-dev-astra-low, chains f4ef67a7 and 252293b5) ended with providerError "Selected model is at capacity. Please try a different model." The runner classified both `TASK_FAILED`, `transient: false`, `retryable: false`; the platform requeued a second Run but charged the attempt to `maxSessionsPerTask`. `TRANSIENT_NETWORK_PATTERNS` in `packages/api/src/execution.ts` lists "our servers are currently overloaded" and HTTP 5xx shapes but not this text, so the EXECUTE-phase refund never applied. The failed attempts had already edited files, and `salvageWorkspace` in `packages/runner/src/delivery.ts` committed them as "WIP salvage" on the Run-owned head. The second Runs therefore started on a HEAD whose parent is the reviewed head, and the step contract ("verify that every present report's reviewed head is the HEAD you are about to fix") gave the agent no way forward except an inbox question; both chains waited on a human for the answer "continue from the salvage". Observed three times on 2026-09-05 (14:31Z twice on Astra low, 14:44Z on Astra medium, chain 5034a0f6), so the recurrence condition is already met.

Changes:
1. The transient-provider classification recognises a model capacity refusal (the Codex text above and the Claude equivalent, matched on the verdict channels only, as the existing patterns are) so such a Run is `TRANSIENT_PROVIDER`, refunded under the existing EXECUTE-phase refund rules, and retried after the existing backoff.
2. The Apply-review-fixes step contract (its template Markdown, all three templates) states: when the starting HEAD is a WIP salvage commit of a prior Run of this same task and its parent is the reviewed head, treat the salvaged changes as in-progress fixes, validate them against the reports, continue on top of them, and record the reviewed head as `sourceHead`; every other reviewed-head mismatch remains a stop. This is a prompt-only change and follows the README procedure for changing a canonical prompt (re-pin the source generation, publish, register the outgoing generation).
3. The runner's completion evidence for a salvaged Run names the salvage commit and its parent in the next Run's claim metadata, so the agent does not have to reconstruct that fact from git history.

Out of scope: retrying inside the CLI session; changing budgets or `maxSessionsPerTask`; any change to how salvage commits are pushed or named; treating a salvage commit whose parent is not the reviewed head as resumable.

Constraints: no pattern may match text an agent could print in its own stdout (the reason the classifier reads verdict channels only); the refund cap and the auth/rate-limit exclusions in `execution.ts` stay as they are; the prompt change is a rollover and must register the outgoing generation or the gate refuses.

Acceptance: a `packages/api/src` test classifies a failure envelope carrying the capacity text as `TRANSIENT_PROVIDER` and shows the refund applied; a test shows the same text in stdout alone does not classify; the canonical-published-generations test passes with the new prompt generation registered; the runner test shows a claim after a salvaged Run carries the salvage commit and parent; `npm run test -w @anneal/api`, `npm run test -w @anneal/runner`, `npm run test -w @anneal/db`, `npm run lint`, `npm run typecheck` and `npm run test:snapshot-scan` pass.
