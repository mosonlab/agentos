Every durably recorded merge-integrator stop reaches its condition-specific Inbox question without manual database repair, including when a definitive result is followed by a failed completion call.

Route: implementation=senior-dev - transaction-boundary semantics between task-output ingestion, run completion and Inbox question creation are hazardous and the suite cannot fully witness every crash window.

Background: On 2026-09-01, chain `3d9d3e5b`, task `cmti9iqe20639mp02vvwd658r`, Run `cmticw97m0zjzmp02kxea2mg0` merged PR #359 as `8bfa2f08`, then lost GitHub connectivity while verifying the merge parents. The executor persisted a `merge-result` with `outcome: "stopped"`, condition `base-drift-post-merge`, and evidence naming the landed commit, followed by a SESSION-authored `mergeIntegrator.result` activity. The Run subsequently ended as retryable `PROTOCOL_ERROR`; automatic retry was refused, the Task remained in REVIEW, and only a TEXT refusal notice existed. There was no `MULTIPLE_CHOICE` row at `merge-stop:<stopId>`, even though this incident condition requires `accept` or `revert`. `POST /tasks/:taskId/retry` could not repair the state because `openRun` calls `stopStateFor` and refuses an unresolved stop (`packages/db/src/run-open.ts:654-668`), while normal chain Task status mutation is also guarded.

This is not a failure of `recordIntegratorStop`. That function creates a control-plane `mergeIntegrator.result`, sets REVIEW and the stop failure reason, and calls `openStopQuestion` in the same caller transaction for every stop except the existing ordinary `base-drift` automatic-recovery candidate (`packages/db/src/merge-integrator-db.ts:717-756`). `openStopQuestion` binds the card to the result activity through `merge-stop:<stopId>` and checks that dedupe key before insert (`packages/db/src/merge-integrator-db.ts:405-471`); `InboxMessage.dedupeKey` is database-unique (`packages/db/prisma/schema.prisma:1171-1188`).

The observed result took a different path. `runClaim` writes the replaceable output, then separately posts the append-only result activity, then calls completion (`packages/merge-executor/src/index.ts:159-173`). `persistSessionTaskOutput` only upserts `TaskStepOutput` and related canonical evidence; it does not land integrator stop state or open an Inbox question (`packages/api/src/canonical-task-output.ts:426-575`). `appendRunActivity` stamps a mechanical result with `sourceRunId`, writes it with `actorType` equal to the SESSION principal, and commits without updating the Task or opening a question (`packages/api/src/run-lifecycle.ts:367-410`). If the success completion request itself throws after those two writes, the broad executor catch reports a crash through a second completion attempt (`packages/merge-executor/src/index.ts:175-195`); `makeAgentOsClient.complete` encodes that attempt as exit 1, `terminalSuccess: false`, retryable `PROTOCOL_ERROR` (`packages/merge-executor/src/agentos.ts:170-195`).

The control plane nevertheless treats the SESSION activity as authoritative stop history. `latestRecordedStop` scans all `mergeIntegrator.result` activities without an `actorType` restriction, and `stopStateFor` keeps the newest valid stop active until a terminal disposition exists (`packages/db/src/merge-integrator-db.ts:194-257`). Run completion classifies the second request as a failed Run (`packages/api/src/run-completion.ts:488-505`) and attempts retry before stop landing (`packages/api/src/run-completion.ts:719-729`). The existing SESSION stop makes that `openRun` fail. The only call to `recordIntegratorStop` is inside `succeeded && mechanical` (`packages/api/src/run-completion.ts:739-755`), so the failed branch never opens the question; it instead parks the Task and emits the runner failure and TEXT retry-refusal notice (`packages/api/src/run-completion.ts:928-978`). Thus one writer creates guard-visible stop state while another writer alone owns the missing question, and a completion transport skew falls exactly between them.

Changes:
1. Establish one database-level stop-landing operation for a new or already-recorded `mergeIntegrator.result`. Under the integrator Task lock, it must bind to the exact result activity id, preserve that activity's condition, evidence, `sourceRunId`, Agent, and Session identities, set the Task to REVIEW with `Mechanical merge stopped: <condition>`, and ensure the condition's `MULTIPLE_CHOICE` question at `merge-stop:<stopId>`. Creating a new result activity and its question is one transaction; adopting an existing result ensures its missing question in the current ingestion/completion transaction. A question insert failure rolls back the new stop and Task transition rather than committing a guarded but unanswerable state. Preserve the current ordinary canonical `base-drift` deferral: its automatic worker remains the next idempotent pass that opens the abandon question when recovery becomes ineligible or exhausted.
2. Route every production stop writer through that operation. In particular, a valid stopped `mergeIntegrator.result` appended through the fenced SESSION activity route must land the stop and question before that request commits, using the SESSION activity itself as `stopId`. `recordIntegratorStop` and run completion must adopt a same-Task, same-`sourceRunId` stopped result instead of creating a duplicate control-plane result and a second question. If a run-owned stopped `merge-result` output exists but its result activity was never committed, completion must create and land the control-plane result atomically. A SESSION or executor path may not leave an operator-actionable recorded stop without its question.
3. Make a valid, run-owned mechanical `merge-result` authoritative over a later contradictory completion envelope. Before assigning `PROTOCOL_ERROR`, retryability, Run failure, or automatic retry, completion must parse the persisted output and verify that it belongs to the exact mechanical Run. A definitive stopped result settles the Run as protocol success, with no failure class or retry, then lands or reuses the recorded stop; `base-drift-post-merge` remains REVIEW with its stop failure reason and opens `accept`/`revert`, because the merge landed even though verification did not. A definitive merged result follows the existing successful merged path. Missing, malformed, foreign-Run, or non-mechanical outputs do not gain this precedence and retain fail-loud classification.
4. Add a one-off `@anneal/db` backfill function and committed CLI, exposed through workspace package scripts, that finds every unresolved, question-eligible latest recorded stop lacking `merge-stop:<stopId>` and applies the same locked, transactional question ensure. Report scanned, created, already-present, deliberately deferred ordinary-base-drift, and failed counts; exit non-zero if any candidate cannot be repaired. A standalone idempotent CLI is simpler than a permanent API startup mutation, avoids adding work and write authority to every process start, and can be rerun safely after interruption. Archived Tasks and stops with a terminal disposition are reported as skipped rather than resurrected.

Out of scope: changes to the `STOP_CONDITIONS` or `STOP_CHOICES` matrices; merge authorization semantics; the behavior of `packages/api/src/merge-base-drift-worker.ts` or its automatic recovery budget; `DEFENSE_EXACT`; gate attestation; runner Regression semantics covered by PR #355; web changes.

Constraints: Fail loudly; do not swallow an Inbox write failure, reinterpret malformed evidence as success, or fall back to a TEXT-only notice. The transaction and Task lock are the correctness boundary, while the unique `InboxMessage.dedupeKey` is the durable replay backstop. Replayed or concurrent completion/repair passes produce exactly one question for one stop and return or observe that winner without surfacing an avoidable unique-constraint failure. Preserve append-only result history, the existing disposition state machine, and the ordinary `base-drift` worker handoff. No Prisma schema change is required. Only an authenticated, fenced mechanical Run's own valid `merge-result` may override its later completion failure classification.
