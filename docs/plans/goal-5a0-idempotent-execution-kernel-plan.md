## Outcome and approach

Implement one PostgreSQL-authoritative Goal execution kernel. Goal-linked Task and Run creation goes through one module; all mutating paths take locks in the global Goal → Task → Run order; unique/check/foreign-key constraints remain the final backstop. Existing NOW Task queueing, runner claiming, lease generation, fencing, delivery, Session accounting, CRON/AT scheduling, templates, chains, and manual Task behavior are reused rather than replaced.

The work is ordered so no route can expose a transition before its durable schema, lock, idempotency, and event semantics exist. The feature flag is default-off. Production migration, enablement, public release, and service restart are not authorized by Goal 5a0.

## Non-negotiable gates

1. **Dependency fuse.** Before any code, schema, or migration edit, Control-plane A must be merged. Rebase on then-current `master`; record its SHA and the Control-plane A merge SHA; rerun the baseline audit in Step 1. If it changes the objective, scope, acceptance, evidence, authority, risk boundary, or Planned Critical route, stop for a new Product Contract version and product-owner approval.
2. **Route.** The implementation task uses `senior-dev` at high effort. It must not be downshifted without Product Contract approval under `docs/governance/task-routing-v1.md`.
3. **Migration fuse.** Preflight must fail closed on ambiguous or active historical Goal lineage. Goal 5a0 may build and rehearse against disposable/private PostgreSQL schemas, but may not run a production migration or restart.
4. **Evidence fuse.** A rerun is not a green gate until the first failure is explained and dispositioned. Every reviewer finding remains in the final disposition ledger.
5. **Rollback default.** Disable `GOAL_SAFETY_KERNEL_ENABLED` first. Prefer roll-forward with the flag off whenever live lineage must be retained; destructive down-migration requires an approved export and explicit operator approvals described in Step 14.
6. **Exclusion-protocol fuse.** Goal 5a0 joins the merged Review/Approval Convergence exclusion protocols; it does not fork them. No Goal-linked Task or Run may be created without holding the exact-grant mutex (`packages/db/src/workflow.ts::lockAgentRepoGrant`) and then the Agent-row mutex (`::lockAgentRow`) — in that direction, which is the direction current master's `POST /tasks/:taskId/start` takes them — and re-reading both under those locks. Any implementation path that creates a Goal Run outside the canonical row order in Step 4.3, or that takes the Agent row before the exact grant, is a stop condition, not a follow-up.
7. **Inbox 3a fuse.** Goal 5a0 owns and may change the symbols listed in the ownership table below; it must not implement Inbox 3a. Inbox 3a (issue #98) does not begin until every one of the following holds: the **merge-method precondition** was satisfied before the merge window opened — this repository currently enables all three merge methods (`gh api repos/mosonlab/agentos --jq '{allow_merge_commit,allow_squash_merge,allow_rebase_merge}'` returns all `true`, read at the round-7 head), so squash and rebase merging must be **disabled** and the merge-commit method left enabled, that observed triple captured as `mergeMethodPolicy` inside the authorized evidence tuple, and re-read live at closeout; the **actual Goal 5a0 implementation pull request** — the one recorded under "Implementation identity and durable handoff record", never issue #97 itself — has merged with a two-parent merge commit; the implementation task that produced it was found through the **external locator comment** on issue #97 rather than through any document inside that pull request; exactly one live `goal5a0.merge_handoff` record resolves on that task under the reference-graph resolution defined below; that handoff names the exact activity ID of a live `goal5a0.merge_authorization` record and carries a byte-identical copy of its **entire seven-key authorization tuple** plus its evidence digest, so the digest recomputes from exactly what was copied; the authorization is corroborated by its GitHub-server-bound half — a single unedited **authorization comment** on the implementation pull request, still retrievable at closeout, authored by an allowlisted login, posted before `mergedAt`, whose canonical marker carries the authorized head, base, evidence digest, in-scope `goal-5a0` delegation, and an unexpired delegation expiry byte-for-byte; and the recorded merge commit is proven an ancestor of a freshly fetched `origin/master`. The five dry checks in "Dependency-gate dry checks" below decide `STOPPED_FOR_REROUTE` versus `SAFE_TO_IMPLEMENT`; there is no third outcome and no partial credit. Closing issue #97 is not evidence of a merge; neither is an open or unmerged linked pull request, a document that names a merge commit, an AgentOS activity whose authorization half is missing or stale, or a green CI badge. An ambiguous, absent, duplicated, superseded, malformed, or drifted record is `STOPPED_FOR_REROUTE`, a stop condition rather than a follow-up. **Every stop names a recovery path.** A stop is a reroute, never a dead end: each `STOPPED_FOR_REROUTE` diagnostic in the dry checks below carries a named recovery procedure, and the four that would otherwise strand the work permanently — `MERGED_BY_UNSUPPORTED_METHOD`, `HANDOFF_TASK_MISSING`, `LOCATOR_SUPERSEDED_OR_DUPLICATE`, and `AUTHORIZATION_MARKER_MISSING` — are written out in full under "Recovery paths for every terminal stop". **Stage 1 — `goal5a0.implementation_identity`, while the implementation is active.** Payload beyond the envelope: `prNumber` (integer or the literal string `not yet opened`), `prUrl` (string or `not yet opened`), `implHead` (40-hex or `not yet pushed`). It records no authorization and no merge commit; the Agent Run completes before either exists. The same three fields are mirrored into the task output for human reading, and that mirror is explicitly **not authority** — see "Reset and successor pull request" below.

**Stage 2 — `goal5a0.merge_authorization`, before the merge.** This is the one-time delegated exact-head authorization required by `docs/governance/task-routing-v1.md` §"Human approval placement". Its payload is the **seven-key authorization tuple**, plus the digest over that tuple, plus the GitHub-authenticated artifact that carries the digest:

| Key | In the digest tuple | Value |
| --- | --- | --- |
| `prNumber`, `prUrl` | yes | the pull request being authorized; both must equal the live stage-1 record's values |
| `authorizedHead` | yes | the exact 40-hex head that was reviewed |
| `authorizedBase` | yes | the exact 40-hex base commit it was reviewed against |
| `requiredCheckPolicy` | yes | `{ source, names }` — the **authoritative required-check name set**, resolved as defined under "Authoritative required-check set" below. `names` is sorted, may be empty only when the empty set is the recorded governance decision, and is the completeness rule the gate enforces |
| `requiredChecks` | yes | array, sorted by `name`, of `{ name, conclusion, headSha }` read from `gh api repos/mosonlab/agentos/commits/<authorizedHead>/check-runs`; every element's `headSha` must equal `authorizedHead`, and the set of `name` values must equal `requiredCheckPolicy.names` **exactly** — not a subset |
| `mergeMethodPolicy` | yes | `{ allowMergeCommit, allowSquashMerge, allowRebaseMerge }` read from `gh api repos/mosonlab/agentos`, which must be exactly `{true, false, false}`: the merge-commit method enabled and squash and rebase merging **disabled** before the merge window opens. This is the precondition that makes the two-parent proof reachable at all — see "The merge method is a gate precondition" below |
| `delegationScope` | no | the literal `goal-5a0`. Bounds what the delegation authorizes; any other value is an out-of-scope delegation and a stop. Copied into stage 3 and re-matched against the marker comment's `delegation-scope` at closeout |
| `delegationExpiresAt` | no | an RFC 3339 instant after which the delegation no longer authorizes anything. `mergedAt` at or after it is an expired delegation and a stop. Copied into stage 3 and re-matched against the marker comment's `delegation-expires-at` at closeout |
| `evidenceDigest` | no (it is the digest *of* the tuple) | the 64-hex digest defined below over exactly the seven tuple keys |
| `authorization` | no | `{ commentId, commentUrl, commentCreatedAt, authorizerLogin }` identifying the GitHub authorization comment defined below; `commentId` and `commentCreatedAt` are server-assigned by GitHub and `authorizerLogin` must equal that comment's `user.login` |
| `approvingReview` | no | optional. `{ reviewId, reviewerLogin, reviewState, reviewCommitId, submittedAt }` when a formal `APPROVED` review by a **second** allowlisted human exists at `authorizedHead`. It is accepted as additional corroboration and is **never a prerequisite** — see "Why the authorization is a comment and not a review" |

The **evidence digest** is computed from a canonical JSON document containing exactly the seven tuple keys `{prNumber, prUrl, authorizedHead, authorizedBase, requiredCheckPolicy, requiredChecks, mergeMethodPolicy}` and nothing else:

```sh
printf '%s' "$EVIDENCE_JSON" | jq -S -c . | shasum -a 256 | cut -d' ' -f1
```

`jq -S -c` sorts keys at every level and removes insignificant whitespace, so the digest is independent of key order and formatting; the pipeline including its trailing newline is part of the definition and must not be varied. Re-verified during the round-7 revision on `jq` 1.7.1 against the **new seven-key tuple**: two orderings of the same document, differing in top-level and nested key order, produced the identical digest `286cf9e821d41ba39fcdb1055738cb282359d6ba942a39c020d65bc416e255bd`. On Linux, `sha256sum` replaces `shasum -a 256`; the runbook records which was used.

**The digest preimage is exactly what stage 3 copies.** Round 7 found this broken: the preimage was `{prNumber, prUrl, authorizedHead, authorizedBase, requiredChecks, review}` while stage 3 copied only four fields and never copied `review`, so "the digest recomputed from the copied tuple" — the condition dry check 0's `unbound` clause stops on, and the condition Step 15.7 item 4 requires a negative test for — could never equal `evidenceDigest`, and **no handoff could ever pass**. The preimage and the copied tuple are now defined to be the same seven keys, so recomputation from the copied tuple is literally true and the tamper-detection claim below is exactly as strong as it says. The prose that called this "exactly the five keys above" was also wrong about its own arity: it is **seven**, and the same miscount is corrected in `docs/reviews/2026-08-17-goal-5a0-plan-review.md` §Round-6 disposition.

**Why the authorization is a comment and not a review.** Round 7 established live that a formal `APPROVED` review is unreachable in this repository: PR #94's author and head owner is `mosonlab`; `gh api repos/mosonlab/agentos/collaborators` returns exactly one collaborator, `mosonlab`, with `admin`; `gh api repos/mosonlab/agentos/pulls/94/reviews` returns an empty array; and GitHub forbids a pull request's author from approving their own pull request. The repository is private with no readable branch protection, and D1 is expressly out of scope, so requiring a review would have made the authorization half impossible for the single authorized operator to produce and would have smuggled an unscheduled identity prerequisite into issue #97. The GitHub-authenticated artifact of record is therefore an **authorization comment** on the implementation pull request, which is equally server-authenticated and is reachable:

```text
goal5a0-merge-authorization: v1
pr: <number>
head: <40-hex authorizedHead>
base: <40-hex authorizedBase>
merge-method-policy: merge-commit-only
delegation-scope: goal-5a0
delegation-expires-at: <RFC 3339 instant>
evidence-digest: <64-hex evidenceDigest>
```

It is fetched with `gh api repos/mosonlab/agentos/issues/<prNumber>/comments` — pull-request conversation comments are issue comments — whose elements carry `id`, `user`, `body`, `created_at`, `updated_at`, `author_association`, `html_url`, and `node_id`, all confirmed live on `gh` 2.89.0 during this revision. GitHub authenticates `user.login`; the AgentOS writer is not authenticated, which is exactly why this half exists.

**The marker binds the person and the head to the authorized bundle.** Round 7 found that the previous design authenticated *a person* and *a head* but left every other field of the stage-2 bundle freely assertable by any shared-`OPERATOR_TOKEN` holder (`packages/api/src/auth.ts:25-33`, `packages/api/src/app.ts:2717-2728`), so a holder could pair a genuine allowlisted exact-head approval with a freshly asserted base, required-check set, and evidence digest and still pass every later objective comparison — violating `docs/governance/task-routing-v1.md`'s rule that base, required-check, or material-evidence drift invalidates authorization. The marker closes that: it is authored inside GitHub by the allowlisted human and carries `head`, `base` **and** `evidence-digest`, and the evidence digest covers the required-check policy, the observed required checks, and the merge-method policy. Dry check C verifies all four marker fields byte-for-byte against the stage-2 record, so a forged bundle paired with a real authorization fails there.

**A delegation has a scope and an end date, and both are GitHub-authenticated.** An authorization with neither is unbounded: it says who approved which head, but not *what work* it authorizes or *for how long*, so a marker written for one merge window silently keeps authorizing after the window has passed. Two fields close that, and they are carried in the marker comment — where the allowlisted human authors them and GitHub attests them — as well as in the stage-2 record:

| Field | Stage-2 key | Rule |
| --- | --- | --- |
| Delegation scope | `delegationScope` | the literal `goal-5a0`. Any other value is an **out-of-scope delegation** and a stop; the delegation authorizes this merge and nothing else |
| Delegation expiry | `delegationExpiresAt` | an RFC 3339 instant. `mergedAt` at or after it is an **expired delegation** and a stop |

Both are **copied byte-for-byte into stage 3** alongside the seven-key tuple and `evidenceDigest`, and both are **re-fetched from the marker comment and re-matched at closeout**, exactly like `head`, `base`, and `evidence-digest`. They are deliberately **not** added to the digest preimage: U2's closure defines the preimage and the copied tuple as the same seven keys and its key-order independence was verified against that arity, so widening it would invalidate a verified digest without adding strength. Their binding comes from the marker comment's byte-for-byte match, which is the same authenticated mechanism that binds the base and the digest — an unedited comment by an allowlisted login cannot be forged with an AgentOS token, whether or not a hash covers the field.

The comment is accepted only when **all** of the following hold, each a stop when it does not:

- `user.login` is on the runbook's allowlist; an author outside it is an **author mismatch** and a stop, and it is never repaired by an AgentOS record asserting a different `authorizerLogin`;
- `created_at == updated_at` — the comment is **unedited**, so its body is byte-for-byte as its authenticated author wrote it. GitHub sets `updated_at` ahead of `created_at` on every edit; this was confirmed live during the revision against a public repository, where unedited comments returned equal values and an edited one returned `2024-04-29T12:56:41Z` created against `2024-04-29T13:04:57Z` updated. An **edited** comment is a stop, and it is never repaired by editing it back, because `updated_at` cannot be reset;
- the comment is still **retrievable at closeout**. A marker that was **deleted** after it was written is a stop with `AUTHORIZATION_MARKER_MISSING`, not a pass on the strength of the stage-2 copy: the AgentOS half is a copy of GitHub's attestation, and a copy of a withdrawn attestation is not evidence;
- the comment is on the **correct pull request** — its `issue_url` resolves to the pull request being merged. A marker on a different pull request is a **wrong-pull-request** stop even when every other field matches;
- `created_at` is strictly earlier than the pull request's `mergedAt`;
- `delegation-scope` is the literal `goal-5a0`; any other value is an **out-of-scope delegation** and a stop;
- `mergedAt` is strictly earlier than `delegation-expires-at`; at or after it is an **expired delegation** and a stop;
- exactly one marker comment exists on the pull request; zero is `AUTHORIZATION_MARKER_MISSING`. Two or more identical markers are **duplicate authorizations** and a stop with no "latest wins" rule; two or more markers disagreeing on `head`, `base`, `merge-method-policy`, `delegation-scope`, `delegation-expires-at`, or `evidence-digest` are **conflicting authorizations** and a stop, which is the stronger of the two because it means two authenticated statements about the same merge do not agree;
- the marker's `pr`, `head`, `base`, `evidence-digest`, `delegation-scope`, and `delegation-expires-at` equal the stage-2 record's `prNumber`, `authorizedHead`, `authorizedBase`, `evidenceDigest`, `delegationScope`, and `delegationExpiresAt` byte-for-byte, and `merge-method-policy` is the literal `merge-commit-only`;
- **when both authorization forms are present and disagree, that is a stop, not a preference.** A formal `APPROVED` review by a second allowlisted human remains **optional corroboration** and is never a prerequisite — that ruling is unchanged. But if such a review exists and its `commit_id` or its allowlisted author contradicts the marker comment's `head` or the stage-2 bundle, the gate has two authenticated statements that do not agree about the same merge, and it stops rather than choosing the one it prefers.

**Authoritative required-check set.** Round 7 found `requiredChecks` had no completeness rule at all: the check-runs endpoint reports which runs *exist*, never which are *required*, so an empty or selectively omitted array passed vacuously and "an added failing required check stops" was asserted with no algorithm behind it. The authoritative source is resolved in this precedence order, and the first readable one wins:

1. `gh api repos/mosonlab/agentos/branches/master/protection/required_status_checks` — its `contexts`/`checks[].context` names, when readable;
2. `gh api repos/mosonlab/agentos/rulesets` and the required-status-check rules it expands to, when readable;
3. the **`required-checks` governance block in the runbook**, which is the recorded product-owner decision naming the exact required-check names — including, explicitly, the **approved empty set**.

Failing to read sources 1 and 2 is not a pass: when neither is readable **and** the runbook carries no `required-checks` block, the gate stops with `REQUIRED_CHECK_SOURCE_UNREADABLE`. `requiredCheckPolicy.source` records which of the three answered, and its raw response is captured in the evidence. **Read live at the round-7 head:** `gh api repos/mosonlab/agentos/branches/master/protection` and `.../rulesets` both return HTTP 403 (`Upgrade to GitHub Pro or make this repository public to enable this feature`), and `gh api repos/mosonlab/agentos/commits/24c328861f8ebb1f9d07fdd67f4d87e8e0947db8/check-runs` returns `{"total_count":0,"checks":[]}`. On this repository as it stands, source 3 is therefore the operative one and the currently recorded decision is the **explicitly approved empty set** — and the plan says plainly what that means rather than implying strength it does not have: with an empty `names`, "no required check is failing" is **vacuously true and proves nothing about CI**, so the empty set must be re-decided and recorded in the runbook before the merge window opens, and the merge gate's strength on this axis is exactly the strength of that recorded decision. Set equality, not subset membership, is the rule: `{requiredChecks[].name}` must equal `requiredCheckPolicy.names` exactly, so an omitted required check is a stop, and any check run at `authorizedHead` whose `name` is in `names` and whose conclusion is not the recorded one — including a newly failing one that was never recorded — is a stop.

**The merge method is a gate precondition.** Round 7's most serious finding: gate 7 required a two-parent merge commit, the classifier stopped on `(.parents | length) != 2`, and the merged-success conjunction required exactly two parents — while `gh api repos/mosonlab/agentos --jq '{allow_merge_commit,allow_squash_merge,allow_rebase_merge}'` returned all three `true`, nothing constrained the method, and no path existed after a squash merge had already happened. An operator clicking GitHub's default "Squash and merge" would have made dry check A return `STOPPED_FOR_REROUTE` forever, leaving issue #98 permanently dependency-held and PR #95 permanently unmergeable, with no recovery defined. The precondition is therefore:

- Before the merge window opens, the delegated operator disables squash and rebase merging and confirms the merge-commit method is enabled:

  ```sh
  gh api -X PATCH repos/mosonlab/agentos \
    -F allow_merge_commit=true -F allow_squash_merge=false -F allow_rebase_merge=false
  gh api repos/mosonlab/agentos --jq '{allow_merge_commit,allow_squash_merge,allow_rebase_merge}'
  ```

- The observed triple is captured as `mergeMethodPolicy` inside the authorization tuple, so it is covered by the evidence digest and by the marker comment;
- Dry check C re-reads it live at closeout and stops on any disagreement;
- A merge that nonetheless happened by an unsupported method stops with the distinct diagnostic `MERGED_BY_UNSUPPORTED_METHOD` and follows the named recovery under "Recovery paths for every terminal stop". It is a reroute, not a dead end.

Head, base, required-check, merge-method, or material-evidence drift invalidates a stage-2 record. Re-authorization is a **new** record whose `supersedesActivityId` names the old one, with a **new** marker comment; no field, digest, or marker is carried forward. The authorization authorizes the merge only; it is neither implementation authorization nor the handoff.

**Stage 3 — `goal5a0.merge_handoff`, after the merge.** The single durable handoff issue #98 consumes. Payload beyond the envelope:

| Key | Value |
| --- | --- |
| `governingAuthorizationActivityId` | the exact `TaskActivity.id` of the live `goal5a0.merge_authorization` that authorized this merge |
| `prNumber`, `prUrl`, `authorizedHead`, `authorizedBase`, `requiredCheckPolicy`, `requiredChecks`, `mergeMethodPolicy` | the **entire seven-key authorization tuple, copied byte-for-byte** from that record — this is exactly the digest preimage, which is what makes recomputation from the copy meaningful |
| `delegationScope`, `delegationExpiresAt` | copied byte-for-byte from that record. They are outside the digest preimage by design (see the delegation-bounds table above), and are bound instead by byte-equality with the marker comment's `delegation-scope` and `delegation-expires-at`, re-fetched at closeout |
| `evidenceDigest` | copied byte-for-byte from that record; it must recompute from the seven copied keys above |
| `mergeCommit` | the exact 40-hex merge commit |
| `mergeParents` | the merge commit's parent SHAs in order, from `gh api repos/mosonlab/agentos/commits/<mergeCommit>`; exactly two are required |
| `mergedAt` | the pull request's `mergedAt`, verbatim from `gh` |
| `masterSha` | `origin/master` observed at closeout after `git fetch origin master` |
| `ancestryVerified` | `ANCESTOR`, from `git merge-base --is-ancestor <mergeCommit> origin/master` run freshly at closeout |
| `reconstructedFrom` | optional, and present **only** on a handoff rebuilt after `HANDOFF_TASK_MISSING`: `{ markerCommentId, mergeCommit, rebuiltAt }`. See "Recovery paths for every terminal stop" |

Reference **and** copy are both required, and this is the point of the design: the reference proves *which* authorization governed the merge, while the copy makes drift detectable in one fetch and makes tampering self-evident, because a change to either copy breaks equality with the other **and** breaks the digest recomputed from the copied tuple — which is a real claim now that the copied tuple is the whole preimage. The merge may proceed only on an exact-head match — the head actually merged must equal the governing `authorizedHead` — and `mergeParents[1]` is the executable proof of that match, which is why the merge method is pinned. `prNumber` and `prUrl` are additionally required to be equal across the live stage-1, stage-2, and stage-3 records; two records naming different pull requests is a stop with the diagnostic `PR_IDENTITY_DISAGREEMENT`, closing the round-7 finding that nothing compared them at all.

**`goal5a0.merge_invalidated`.** Payload beyond the envelope: `invalidatesActivityId` (the exact `TaskActivity.id` being killed, which must be a kept record on this task; it is resolved as a graph edge, with no requirement about its position in any sort order), `abandonedPrNumber`, and `reason`. It is the only way to retract a record, because no route can edit or delete one.

#### External, non-circular locator

Issue #98 must find issue #97's implementation task **without** reading anything inside the pull request it is gating on, or the locator would be circular. The locator of record is a fenced block in a **comment** on GitHub issue #97, authored by an allowlisted login:

```text
agentos-implementation-task: <AgentOS task ID>
agentos-implementation-task-name: <the recorded implementation-task name>
supersedes-comment: <numeric comment ID, or the literal none>
```

**Only a comment is authoritative; the issue body is context, never authority.** Round 7 found the previous rule unprovable: `gh issue view 97 --json author,body,comments,updatedAt` exposes `author`, `body`, `comments`, and `updatedAt`, and the REST issue object exposes `user` and `updated_at` — none of which identifies who wrote the *current* body text. `author`/`user` identifies who **opened** the issue, and no supported field attributes a body edit, so a body locator proves nothing about the login that supplied the text a consumer is about to trust. A comment is different: `gh api repos/mosonlab/agentos/issues/97/comments` returns `id`, `user`, `body`, `created_at`, `updated_at`, `author_association`, `html_url`, and `node_id`, GitHub authenticates `user.login` as the comment's author, and `created_at == updated_at` proves the body is byte-for-byte as that author wrote it. A locator block found only in the issue body is `STOPPED_FOR_REROUTE`, not a fallback.

**No credential destination ever comes from GitHub-controlled text.** Round 7 found the previous locator carried `agentos-api-base: https://<host>` — an API authority supplied inside text anyone who can comment on or edit issue #97 controls — while the checks were never told whether to reject, ignore, or use it. Either reading was a defect: attaching the shared `OPERATOR_TOKEN` bearer to that URL would let whoever edits the locator exfiltrate the credential, and ignoring it left an undefined field in a schema the plan calls exact. **The field is removed from the locator entirely.** The rules are standing:

- The AgentOS origin is taken **only** from the operator's own configured environment — the session manifest / `AGENTOS_API_BASE` value the operator already holds, currently `http://localhost:3000`, not an issue-supplied HTTPS host.
- Before any request, the harness compares the URL it is about to call against that configured origin **byte-for-byte on scheme, host, and port**, and attaches the `Authorization` header only after that comparison passes. The credential is never attached to a URL derived from issue text, and the comparison happens *before* the header exists, not after.
- A locator block containing an `agentos-api-base:` line — or any other key not in the three above — is `STOPPED_FOR_REROUTE` with the diagnostic `LOCATOR_FIELD_NOT_PERMITTED`. It is never silently ignored, because a silently ignored field is an untestable one.

**Task-ID grammar, taken from the API's own rule rather than from today's ID shape.** Round 7 found the previous `<40-char AgentOS task ID>` grammar factually wrong and dangerously SHA-shaped, and replaced it with `^c[a-z0-9]{20,32}$`. That replacement was correct about the defect and still wrong in kind: it bakes in the current `cuid()` shape — a leading `c`, lowercase alphanumerics, a 20-to-32 length band — none of which the API promises. The authority is the API's own validation rule: **`packages/api/src/app.ts:93` validates every path ID as `const id = z.string().min(1)`** — a non-empty string and nothing more — and live AgentOS task IDs are 25-character Prisma CUIDs (`Task.id` at `packages/db/prisma/schema.prisma:467` and `TaskActivity.id` at `:562` are both `@default(cuid())`), a length Prisma does not fix. The locator rule is therefore three layers, none of them a length assertion:

1. **The API's rule**: a non-empty string, per `app.ts:93`.
2. **A conservative shape**: `^[A-Za-z0-9_-]+$` — a superset of the current CUID form, chosen so the value cannot carry a scheme, host, path separator, query, or whitespace. It is a **character class with no maximum**. Round 7's `{1,64}` bound is **removed as a round-8 correction**, because a maximum of 64 *is* a length assertion and contradicted this rule's own "no length is asserted" claim: a 65-character ID that AgentOS issues and can retrieve would have been rejected as `MALFORMED_TASK_ID`, holding issue #98 forever on a document rule the API does not impose — the exact fail-dead class every round of this review has been about. The URL-safety property the bound was standing in for is carried entirely by the character class, and identity is proved by byte-equality in rule 3. A value failing it is `MALFORMED_TASK_ID`.
3. **Byte-equality with the retrieved task's own `id`**: `GET /tasks/<taskId>` must return 200 whose `id` is byte-equal to the locator value. **No length is asserted at any layer.**

This is what resolves the 40-character case correctly. A 40-hex value in the task-ID slot is no longer rejected by a length rule that would also reject a legitimate future 40-character task ID; it passes the shape filter, is carried to `GET /tasks/<value>`, and stops there — 404 as `HANDOFF_TASK_MISSING`, or a returned `id` that is not byte-equal. The retrieval, not the grammar, is the authority, and the negative fixture for a 40-hex SHA in the task-ID slot is kept and now asserts the stop it actually produces.

**Credential ordering is part of the locator schema, and it is proved at the destination.** The request URL is constructed as `new URL("/tasks/" + encodeURIComponent(taskId), TRUSTED_ORIGIN)`, where `TRUSTED_ORIGIN` comes only from the operator's own configured environment; its `origin` must be byte-equal to the configured origin's `origin`; and only after that comparison passes may an `Authorization` header be attached. Any scheme, host, or port difference is `ORIGIN_DRIFT` and stops with **zero bytes sent**.

It is non-circular because issue #97 exists before the implementation pull request, is outside the merged tree, and names the task; the task's activities then name the pull request.

**Resolution and corroboration.** Collect every comment on issue #97 containing an `agentos-implementation-task:` block; keep only those whose `user.login` is allowlisted and whose `created_at == updated_at`. Among the kept blocks, a comment is dead if a later kept comment's `supersedes-comment` names its `id`; exactly one live locator must remain. Then corroborate against AgentOS: `GET /tasks/<taskId>` must return 200 with that exact ID, and `GET /tasks?projectId=<recorded project>&archived=all` must contain exactly one task whose `name` equals the locator's `agentos-implementation-task-name`. `STOPPED_FOR_REROUTE` when: no live locator comment exists; two live ones name different task IDs (diagnostic `LOCATOR_SUPERSEDED_OR_DUPLICATE`, which has a named recovery); a block appears only in the issue body; the comment's author is not allowlisted; the comment was edited (`created_at != updated_at`); the ID is empty or fails the conservative shape `^[A-Za-z0-9_-]+$` (`MALFORMED_TASK_ID`); the retrieved task's `id` is not byte-equal to the locator value; the constructed request origin differs from the configured origin in scheme, host, or port (`ORIGIN_DRIFT`); the block carries a non-permitted key; `GET /tasks/<taskId>` returns 404 (diagnostic `HANDOFF_TASK_MISSING`); the list query returns zero or more than one task with the recorded name; or the two sides disagree. The allowlist of authorized logins lives in the runbook as a governance artifact; it is not supplied at check time by whoever is running the check.

The `supersedes-comment` line is what keeps this from failing dead. Without it, publishing a corrected locator — which the `HANDOFF_TASK_MISSING` recovery below requires — would create a permanent duplicate stop. With it, a correction is an ordinary append: post a new allowlisted comment naming the old comment's `id`, and the old locator is dead by explicit reference rather than by a timestamp comparison.

#### Reference-graph resolution, and what the total order is *not* for

`GET /tasks/:taskId/activity` orders only by `createdAt`, and `createdAt` is a PostgreSQL `timestamp(3)` (`packages/db/prisma/schema.prisma:561-571`; `packages/db/prisma/migrations/20260815000000_phase0_init/migration.sql:278-287`), so two records written in the same millisecond come back in an order the database is free to vary between calls. The consumer therefore re-sorts client-side into **`(createdAt ASC, id ASC)`**.

**That order is a deterministic *presentation* order. It is not a causal order, and no liveness rule may rest on it.** Round 7 found the previous algorithm requiring every `supersedesActivityId` / `invalidatesActivityId` target to appear *earlier* in that sort. `TaskActivity.id` is a unique CUID, and uniqueness gives a total order — but it does not prove that a record written later has a lexically larger `id`. Prisma documents ULID, not CUID, as lexicographically sortable. So a legitimate correction or invalidation written **later** within the same millisecond could sort **before** its target, be classified as a permanent forward reference, and poison the append-only log; and the promised invalidation-before-target negative was not observable from these fields at all. Resolution is therefore **graph-based and independent of any lexical or temporal claim about `id`**:

The rule set is stated **explicitly and completely**, so an implementer has nothing to infer. Nine rules, each a statement about identity, kind, or edges, and none about time:

1. **Same task, and kept.** Keep only activities whose `metadata` is an object with a `kind` in the four literals. Everything else on the task — "Task created", runner completion notes, ordinary agent progress — is ignored. For every kept record, `schemaVersion` must be `1`, `issueNumber` must be `97`, and `implementationTaskId` must equal the task being read; otherwise stop (`SCHEMA_VERSION`, `ISSUE_NUMBER`, `FOREIGN_TASK`).
2. **Single edge.** Each kept record carries **at most one** edge: `supersedesActivityId` **or** `invalidatesActivityId`, never both (`TWO_EDGES_ON_ONE_RECORD`). A `goal5a0.merge_invalidated` record must carry `invalidatesActivityId` and must not carry `supersedesActivityId` (`INVALIDATION_WITHOUT_TARGET`, `ILLEGAL_EDGE_INVALIDATED_SUPERSEDES`); no other kind may carry `invalidatesActivityId` (`ILLEGAL_EDGE_NON_INVALIDATOR`). Because every record has at most one outgoing edge, the reference graph is **functional**, which is what makes rule 7's cycle test a single pointer walk rather than a general search.
3. **Non-dangling.** An edge whose target is not a kept record on this task is `DANGLING_REFERENCE`, a stop.
4. **Non-self.** An edge from a record to itself is `SELF_REFERENCE`, a stop.
5. **Same-kind supersession, and cross-kind legality.** A `supersedesActivityId` must name a record of the **same** kind (`CROSS_KIND_SUPERSESSION`) — an identity supersedes an identity, an authorization an authorization, a handoff a handoff. An `invalidatesActivityId` is the one legal cross-kind edge: it may name a record of any of the three stage kinds, and must not name another `goal5a0.merge_invalidated` (`INVALIDATES_INVALIDATION`), because a tombstone for a tombstone has no meaning the gate can act on.
6. **Non-contested.** At most one record may name a given target, across both edge fields. Two records claiming to supersede or invalidate the same record is `CONTESTED_TARGET` — an explicit conflict, never a "latest wins" tie-break, because "which correction won" is then undecidable.
7. **Acyclic.** On a functional graph, a node lies on a cycle exactly when following its single edge returns to it. Any such node is `CYCLE`, a stop, reported as the **sorted** list of every node on a cycle so the diagnostic is itself order-independent. This is what replaces round 6's forward-reference rule: a pair of records superseding each other is caught as a cycle rather than mistaken for a legitimate later correction.
8. **Live selection by incoming edge alone.** A record is **dead** exactly when it is the target of an edge. The live set for a kind is its kept records that are not dead. No timestamp and no `id` comparison participates in this step. **No temporal or lexical relationship between a record and its target is required or checked.**
9. **Exactly one live record per singleton kind.** `goal5a0.implementation_identity`, `goal5a0.merge_authorization`, and `goal5a0.merge_handoff` each require exactly one live record: zero is `MISSING_LIVE_RECORD`, two or more — duplicate, conflicting, or merely repeated — is `MULTIPLE_LIVE_RECORDS`. `goal5a0.merge_invalidated` is a tombstone kind with no cardinality rule of its own. There is still no "latest wins" rule, and now there does not need to be one: liveness is decided by explicit reference, which the writer controls, not by a clock or an ID neither the writer nor the reader can order causally.

`(createdAt ASC, id ASC)` survives for exactly two purposes, and the plan states them so no future reader re-derives a causal claim from them: it makes the **reported transcript** byte-reproducible across runs, and it makes the fixtures' input orders enumerable — round 7 asserted them in both directions, and the round-7 graft strengthens that to every permutation. It decides nothing about which record governs. The one ordering comparison that remains load-bearing — the stage-2 activity's server-assigned `createdAt` strictly earlier than GitHub's `mergedAt`, and the authorization comment's `created_at` strictly earlier than the same — is a comparison against an **external** timestamp, not an intra-log causal claim, and it is never the only proof: `mergeParents[1] == authorizedHead` and the marker's `head == authorizedHead` bind the authorization to the merged head with no clock at all.

The safety argument therefore rests on **cardinality**, not on ordering: any ambiguity — two live records, a contested target, a cycle, a dangling edge, an illegal cross-kind or double edge — stops the gate, and the only way to retire a record is an explicit, unique, well-typed edge naming it. That property is invariant under **every** permutation of the input, which is exactly what the fixture suite must prove.

**The fixture suite proves order-independence structurally, not by sampling two orders.** Every fixture's records share **one** `createdAt` value, so presentation order carries no information at all, and each fixture must produce its stated outcome under **every permutation** of its record list — not merely in both directions — up to a bounded permutation count (720 orderings for a six-record fixture) with the bound recorded in the evidence. The suite is **at least nineteen fixtures**, enumerated so nothing is left to the implementer's discretion:

A moved head must in any case be recorded by superseding the identity record, which makes the stale one dead by explicit reference.

#### Retention, deletion, and archival

The handoff's durability is exactly the implementation Task's lifetime. No retention policy, TTL, or pruning job touches `TaskActivity`, and no route edits or deletes one — but `DELETE /tasks/:taskId` (`packages/api/src/app.ts:2374-2377`) is unguarded and cascades (`schema.prisma:569`), so a single operator call destroys the entire handoff with no trace. Because `GET /tasks/:taskId/activity` answers `200 []` for a deleted task, absence and destruction look identical on that endpoint. The rules are therefore:

- Every retrieval calls `GET /tasks/<taskId>` first. A 404 is `STOPPED_FOR_REROUTE` with the distinct diagnostic `HANDOFF_TASK_MISSING`, which is never reported as "no handoff yet".
- Archiving is not deletion: `archivedAt` only filters the list route, so the locator's corroborating list query uses `archived=all` and archived tasks keep their activities.
- The runbook records the standing operator rule that the Goal 5a0 implementation task must not be deleted, and the evidence packet records its task ID so a deletion is detectable after the fact.
- Goal 5a0 does **not** add a delete guard, a soft-delete, or an audit trail for deletion; that is out of scope for this contract and is recorded below as an accepted residual risk with a named remedy, not silently absorbed.
- Deletion is **detected and recoverable**, not detected and terminal. Round 7's should-fix S5 is adopted: `HANDOFF_TASK_MISSING` now carries a written recovery procedure under "Recovery paths for every terminal stop" below, because the handoff's fields are re-derivable from evidence that survives outside AgentOS — the authorization marker comment on the pull request, the merge commit and its parents in the commit graph, and `origin/master` ancestry.

#### Reset and successor pull request

This section covers a pull request closed unmerged or superseded. A pull request that was **correctly merged by the wrong method** is a different case with its own procedure — see `MERGED_BY_UNSUPPORTED_METHOD` under "Recovery paths for every terminal stop"; round 7 found that the reset rule below covered only the first two cases, which is why a squash merge had no way forward at all.

Round 5's reset rule said the stage-1 fields "return to their placeholders", which required rewriting the AgentOS task output — a write only a live Run with a valid fencing token can perform (`app.ts:3218-3234`), and by then the implementation Run has completed. The reset is therefore expressed entirely by appending:

1. The delegated operator appends `goal5a0.merge_invalidated` naming the abandoned pull request and the exact activity ID of each record being killed — the stage-1 identity and, if one exists, the stage-2 authorization and stage-3 handoff.
2. The successor pull request gets a **new** `goal5a0.implementation_identity` record, written by the successor implementation Agent Run if one is active, or by the delegated operator through `POST /tasks/:taskId/activity` if none is. No completed Run is asked to write anything.
3. A fresh stage-2 authorization — with a **new** marker comment on the successor pull request — is required for the successor head; no reviewed head, check conclusion, merge-method reading, evidence digest, marker, merge commit, or handoff is carried forward.
4. The task-output mirror may be refreshed by the operator through `PUT /tasks/:taskId/output` for human convenience, or left stale. It is never authority, no gate reads it, and its staleness can never make a stopped gate pass — the resolution algorithm reads activities only.

#### Recovery paths for every terminal stop

Round 7's unifying finding: the gate failed **closed**, which is safe, and in several places it also failed **dead** — a correct, honest, well-executed sequence reached a stop with no defined way forward. A stop is a reroute. Every `STOPPED_FOR_REROUTE` diagnostic below names what to do next, and none of these recoveries grants implementation, merge, migration, activation, or production authority; each ends in the ordinary dry checks being rerun from the top.

**`MERGED_BY_UNSUPPORTED_METHOD` — the pull request was correctly merged, but with the squash or rebase method.** Detected by a merge commit with fewer than two parents, or by `mergeMethodPolicy` disagreeing with the live repository settings. The head-to-merge graph binding genuinely is not recoverable from a squashed or rebased commit, so the recovery restores it rather than pretending it survived:

1. Apply the merge-method precondition immediately — disable squash and rebase merging — so the same mistake cannot repeat during the recovery.
2. Append `goal5a0.merge_invalidated` naming the stage-3 handoff (if one was written) and the stage-2 authorization, and record the abandoned merge commit in `reason`.
3. Re-establish the change as a **successor pull request**: revert the squash/rebase commit on `master` through an ordinary revert pull request, then reopen the change as a new pull request whose head is a new commit. The revert is an ordinary reviewed change on `master`, not a history rewrite, and it is the only step of this recovery that touches `master`.
4. The successor pull request gets a **new** `goal5a0.implementation_identity` record, a **fresh** stage-2 authorization at the successor head with a **new** marker comment, and — after a two-parent merge — a new stage-3 handoff. Nothing is carried forward: not the reviewed head, not a check conclusion, not the evidence digest, not the abandoned merge commit.
5. Rerun all five dry checks from the top.

An alternative exists and is deliberately **not granted here**: a distinct, explicitly *weaker* evidence class for a squash or rebase merge, resting on the allowlisted unedited marker comment at `authorizedHead`, plus `gh api repos/mosonlab/agentos/commits/<mergeCommit>/pulls` associating the merge commit with the authorized `prNumber` (confirmed live on `gh` 2.89.0 to return the associated pull request's `number` and `merge_commit_sha`), plus the single parent equal to `authorizedBase`, plus `headRefOid == authorizedHead`, plus ancestry — recorded with `mergeParents` of length 1 and an explicit `evidenceClass: "squash-weak"`. It is weaker because no commit in the graph then contains `authorizedHead` as a parent, so the binding rests entirely on GitHub's own association records rather than on the commit graph. **Using it requires a new Product Contract version and product-owner approval.** v1.2 names it so that a future operator has a decision to make rather than a wall to hit; it does not authorize it, and the gate as written rejects a single-parent merge commit.

A second, differently shaped alternative is recorded here for the same reason — so a product owner can choose it later without rediscovering it — and is likewise **named but not granted**. Instead of pinning the merge method, it drops the two-parent requirement entirely and proves the head binding from `refs/pull/<n>/head` resolving to `authorizedHead`, plus `authorizedBase` being an ancestor of `authorizedHead`, plus **either** a parent proof (a two-parent merge commit whose `parents[1]` is `authorizedHead`) **or** a tree proof (a single-parent commit whose tree equals the authorized head's tree), stopping with the diagnostic `HEAD_BINDING_UNPROVED` when neither establishes it. Its operational advantage is real and worth recording: it bans no enabled merge method and therefore requires **no repository-settings change** before the merge window opens, which makes it reachable in situations where the pinning precondition is not. **The accepted decision stands unchanged**: this plan pins the merge-commit method, and nothing in this alternative is authorized, acted on, or treated as a fallback the gate may take on its own.

**`HANDOFF_TASK_MISSING` — the implementation task was deleted, cascading its whole handoff.** `DELETE /tasks/:taskId` is unguarded and `Task.activity` cascades, so this is reachable by any shared-token holder. It is recoverable because the handoff's evidence does not live only in AgentOS:

1. Confirm it is deletion, not absence: `GET /tasks/<taskId>` returns 404 while `GET /tasks/<taskId>/activity` returns `200 []`. Never report this as "not yet merged".
2. Create a **replacement** implementation task, and publish a new allowlisted locator comment on issue #97 whose `supersedes-comment` names the dead locator's comment ID. This is exactly why `supersedes-comment` exists.
3. The delegated operator rewrites stage 1, stage 2, and stage 3 on the replacement task **from the surviving GitHub evidence**: the authorization marker comment on the pull request (which carries `head`, `base`, and `evidence-digest`), the pull request's `number`/`url`/`headRefOid`/`mergedAt`/`mergeCommit`, the merge commit's two parents, the live merge-method and required-check policy reads, and a fresh ancestry check.
4. The stage-3 record carries `reconstructedFrom: { markerCommentId, mergeCommit, rebuiltAt }`, and the reconstruction is only accepted when the rebuilt seven-key tuple **recomputes to the digest carried in the surviving marker comment**. That is what makes reconstruction verifiable rather than asserted: the operator cannot invent a tuple, because the digest was fixed inside GitHub by the allowlisted human before the merge.
5. If the marker comment did **not** survive — it was deleted or edited — the merge cannot be re-authorized after the fact. The recovery is then the `MERGED_BY_UNSUPPORTED_METHOD` path: invalidate, revert, and re-merge a successor pull request under a fresh exact-head authorization.
6. Rerun all five dry checks from the top.

**`LOCATOR_SUPERSEDED_OR_DUPLICATE` — two live locator comments name different task IDs.** The allowlisted operator posts one further comment whose `supersedes-comment` names the wrong locator's `id`, which kills it by explicit reference; if both are wrong, supersede both and post a correct one. Rerun dry check L. An unallowlisted or edited locator comment is not superseded but simply never kept, so it needs no action.

**`AUTHORIZATION_MARKER_MISSING` — no marker comment, or it was edited after posting.** Before the merge, the recovery is trivial and complete: the allowlisted human posts a fresh marker comment and the operator appends a new stage-2 record superseding the old one; an edited marker is never repaired by editing it back, because `updated_at` cannot be reset. After the merge, an absent or edited marker means the merge has no authenticated authorization at all, and the recovery is the `MERGED_BY_UNSUPPORTED_METHOD` path.

**`REQUIRED_CHECK_SOURCE_UNREADABLE` — no authoritative required-check source answered.** Record the 403s (or other failures) from the branch-protection and ruleset reads as evidence, then obtain a recorded product-owner decision for the runbook's `required-checks` block — an explicit name set, or an explicitly approved empty set with its consequences stated. That decision, not the unreadable endpoint, is the authority. Rerun dry check C.

**`PR_IDENTITY_DISAGREEMENT` — stage 1, stage 2, and stage 3 do not all name the same pull request.** Determine which record is wrong from GitHub, append `goal5a0.merge_invalidated` against it, append a correct replacement of that kind, and rerun dry checks 0, A, and C. If the disagreement means the merge was authorized against a different pull request than the one that merged, this is the `MERGED_BY_UNSUPPORTED_METHOD` path instead: the authorization does not govern that merge.

**`LOCATOR_FIELD_NOT_PERMITTED` — the locator carries a key outside the permitted three.** Supersede the offending comment with a conforming one. If the offending key was `agentos-api-base`, additionally treat it as a possible credential-exfiltration attempt: no request was made to it, because the harness validates the origin before attaching any `Authorization` header, but the event is recorded in the evidence packet and reported to the operator.

#### Dependency D1 — server-derived operator identity

The stage-2 record's `actorId` and `authorizerLogin` are client-supplied strings on a shared token. Binding them to a human inside AgentOS requires all of:

1. A delegated-principal store and per-principal tokens replacing the single shared secret in `packages/api/src/auth.ts::authenticate`, with `Principal` gaining an identified operator variant.
2. `POST /tasks/:taskId/activity` deriving `actorId` from the authenticated principal and **rejecting** a client-supplied `actorId` (`packages/api/src/app.ts:2717-2728`, `activityInput` at `:277-282`).
3. A typed-record surface that validates `metadata.kind`/`schemaVersion` against a registered schema and refuses a second non-superseding record of a singleton kind.
4. `GET /tasks/:taskId/activity` accepting a `kind` filter, so consumers are not forced to fetch and filter the whole log. (Round 7 removed the `[{ createdAt }, { id }]` server ordering from D1's motivation: server-side `(createdAt, id)` ordering would still not be a causal order, and liveness no longer rests on ordering at all. A *proved* causal order is the separate dependency **D2** above.)

D1 is **not** Goal 5a0 implementation scope, is not scheduled by this plan, and is deliberately not given an invented issue number. Neither is D2. Until D1 exists, the GitHub-server-bound half of the authorization is mandatory, not optional — and it stays mandatory afterwards, because two independent authorities are stronger than one. **Neither D1 nor D2 is a prerequisite for the gate as written:** every check above runs against the current API surface, and round 7 verified that the authorization half in particular is reachable today by the single authorized operator.

### Dependency-gate dry checks

Any work stream that believes the Goal 5a0 dependency is discharged — issue #98 first, and any other consumer of this handoff — runs all five checks in order and records their raw output, exit statuses, and outcome tokens before touching code. All five are read-only. The only outcome tokens are `STOPPED_FOR_REROUTE` and `SAFE_TO_IMPLEMENT`; there is no partial credit and no third outcome. Checks L and 0 require operator authentication, which an Agent Run does not have (`packages/api/src/auth.ts:48-53`), so they are executed by the delegated operator and their raw transcripts are handed to issue #98's task as inputs; issue #98's Agent Run never authenticates as operator and never re-derives the outcome from a document.

**Artifact hygiene and signal safety — one validated temporary root, a validated destination, recorded exit statuses, and an outcome no signal can turn into success.** Every artifact of every check is written under a single `mktemp -d` root; nothing is written to the repository, the working tree, or a fixed path such as `pr-view.json` in the current directory. Round 7's should-fixes S2 and S3 are both adopted, and the harness below is the corrected version: the shebang is explicit `bash` because `set -o pipefail` is not portable under `#!/bin/sh`; `TMPDIR` is allowlisted *before* `mktemp` rather than only its output; the evidence destination is validated before the temporary root exists, so the copy target is always usable; the cleanup handler is installed **immediately** after `mktemp -d` so a signal in the following lines cannot leak the root; and `INT`/`TERM` no longer destroy evidence, because the round-6 version installed the same immediate `rm -rf` for `EXIT`, `INT`, and `TERM` before any check ran, so a signal deleted the artifacts before they were copied and — with no `set -e` — execution could continue against a directory that no longer existed.

**Installing `INT` and `TERM` handlers is not by itself sufficient, and this was established by execution rather than by review.** The round-6 shape was run with a check in flight and `INT` sent to the **supervisor process alone**: it reached `SAFE_TO_IMPLEMENT` and exited `0`. The mechanism is a property of the shell, not of the handler: a POSIX shell defers a trapped `SIGINT` while a foreground child is running, and then **discards** it when that child exits normally, so the handler is never entered and execution resumes straight through to the success path. No reviewer described this; adding handlers to the round-6 shape would have left it intact. The harness is therefore restructured so that the outcome does not depend on trap delivery at all:

- **The outcome file defaults to `STOPPED_FOR_REROUTE` at creation.** A successful verdict is never the fallthrough value; `SAFE_TO_IMPLEMENT` is written explicitly by the success path and by nothing else.
- **The checks run as a child process under an explicit `wait`**, so the supervisor is never blocked inside a foreground command that swallows the signal.
- **A terminal exit-status guard treats any recorded status of `128` or greater as signal death** and forces the stopped outcome, catching a command killed by a signal even when no handler ran at all.
- **The `INT` and `TERM` handlers record which signal arrived**, force a non-zero terminal outcome, copy whatever partial evidence exists to the already-validated destination, and exit without returning.
- **The destination is validated before the temporary root is created**, so a handler always has somewhere safe to copy.
- **Exactly one `EXIT` handler**, removing only the validated `mktemp` root and nothing else.

```bash
#!/usr/bin/env bash
set -u
set -o pipefail

# 1. Validate the destination FIRST, so a signal handler always has somewhere safe to copy to.
EVIDENCE_DIR="${1:?evidence dir required}"
case "$EVIDENCE_DIR" in /*) ;; *) echo "STOPPED_FOR_REROUTE evidence dir must be absolute"; exit 1 ;; esac
mkdir -p "$EVIDENCE_DIR" 2>/dev/null || { echo "STOPPED_FOR_REROUTE evidence dir uncreatable"; exit 1; }
[ -d "$EVIDENCE_DIR" ] && [ -w "$EVIDENCE_DIR" ] || { echo "STOPPED_FOR_REROUTE evidence dir unusable"; exit 1; }

# 2. Allowlist TMPDIR itself, before mktemp consumes it; then validate mktemp's own output.
TMPROOT="${TMPDIR:-/tmp}"
case "$TMPROOT" in
  /tmp|/tmp/|/var/folders/*|/private/var/folders/*) ;;
  *) echo "STOPPED_FOR_REROUTE untrusted TMPDIR: $TMPROOT"; exit 1 ;;
esac
GATE_DIR="$(mktemp -d "${TMPROOT%/}/goal5a0-gate.XXXXXXXX")" || { echo STOPPED_FOR_REROUTE; exit 1; }
case "$GATE_DIR" in
  /tmp/*|/var/folders/*|/private/var/folders/*) ;;
  *) echo "STOPPED_FOR_REROUTE untrusted temp root: $GATE_DIR"; exit 1 ;;
esac
[ -d "$GATE_DIR" ] && [ -w "$GATE_DIR" ] || { echo "STOPPED_FOR_REROUTE unusable temp root"; exit 1; }
export GATE_DIR

STATUS_LOG="$GATE_DIR/exit-status.tsv"; printf 'label\texit\n' > "$STATUS_LOG"
OUTCOME="$GATE_DIR/outcome.txt"
printf 'STOPPED_FOR_REROUTE incomplete\n' > "$OUTCOME"   # SAFE is never the fallthrough value

capture() { [ -d "$GATE_DIR" ] || return 1; cp -R "$GATE_DIR/." "$EVIDENCE_DIR/" 2>/dev/null || return 1; }

CHECKS_PID=""
on_signal() {                        # record, force a stop, preserve, clean — in that order, and never return
  printf 'signal-%s\t1\n' "$1" >> "$STATUS_LOG" 2>/dev/null
  printf 'STOPPED_FOR_REROUTE interrupted by SIG%s\n' "$1" > "$OUTCOME" 2>/dev/null
  [ -n "$CHECKS_PID" ] && kill -TERM "$CHECKS_PID" 2>/dev/null
  capture; cap=$?
  trap - EXIT INT TERM; rm -rf "$GATE_DIR"
  echo "STOPPED_FOR_REROUTE interrupted by SIG$1 (evidence-copy rc=$cap)"; exit 1
}
trap 'on_signal INT'  INT
trap 'on_signal TERM' TERM
trap 'rm -rf "$GATE_DIR"' EXIT       # the ONLY cleanup handler; it removes the validated root and nothing else

# 3. Run checks L, 0, A, C, B as a CHILD under an explicit wait, so the supervisor is never blocked
#    inside a foreground command that could defer and then discard the signal.
#    record() { label="$1"; shift; "$@" > "$GATE_DIR/$label.out" 2> "$GATE_DIR/$label.err"; rc=$?
#               printf '%s\t%d\n' "$label" "$rc" >> "$GATE_DIR/exit-status.tsv"; return "$rc"; }
GATE_CHECKS="${GATE_CHECKS:?checks entry point required}"   # runs L, 0, A, C, B, each through record()
"$GATE_CHECKS" & CHECKS_PID=$!
wait "$CHECKS_PID"; crc=$?
printf 'checks\t%d\n' "$crc" >> "$STATUS_LOG"

# 4. Terminal exit-status guard: any recorded status >= 128 is signal death, handler or no handler.
BADSIG=$(awk -F'\t' 'NR>1 && ($2+0)>=128 {n++} END{print n+0}' "$STATUS_LOG")
if [ "$crc" -ge 128 ] || [ "$BADSIG" -gt 0 ]; then
  printf 'STOPPED_FOR_REROUTE signal-terminated command (checks rc=%d, signalled=%d)\n' "$crc" "$BADSIG" > "$OUTCOME"
  capture; cat "$OUTCOME"; exit 1
fi
[ "$crc" -eq 0 ] || { printf 'STOPPED_FOR_REROUTE checks rc=%d\n' "$crc" > "$OUTCOME"; capture; cat "$OUTCOME"; exit 1; }

printf 'SAFE_TO_IMPLEMENT\n' > "$OUTCOME"                # written only here, by the success path alone
capture || { echo "STOPPED_FOR_REROUTE evidence capture failed"; exit 1; }
cat "$OUTCOME"
```

`SAFE_TO_IMPLEMENT` is reachable on exactly one path: the checks child exited `0`, no recorded status is a signal death, and the evidence copy succeeded. Every other path — including both signal paths and the no-handler-ran path — writes a `STOPPED_FOR_REROUTE` outcome, copies whatever evidence exists to the already-validated destination, and exits non-zero. Only `EXIT` removes the root, and it removes only the `mktemp`-validated path.

### Cancellation fence and non-scope

The fence is Step 9.5: a cancelled, completed, failed, paused, or stale-generation Goal can never regain Inbox resume authority, because `applyInboxDecisionTx` takes the Goal lock first and consults `goalRunResumeAuthority` before the resume writes.
