# AgentOS v0.1.0 — Developer Preview

> **Correction (2026-08-19).** The published install outline omitted the required
> runtime build, the verification section omitted host-path isolation, the
> release commit was left as a placeholder, and several support claims exceeded
> their evidence. These instructions and claims are corrected below; the
> `v0.1.0` tag and its historical bytes remain unchanged.

This page is the release notes for `v0.1.0`, and the source text for the GitHub
Release body of the same tag.

AgentOS is a local, single-operator control plane for handing scoped software
tasks to coding CLIs already installed on your own machine, and for keeping what
they did observable and durable: tasks, agents, repository and file grants,
isolated run records, provider event streams, human questions, review gates and
git delivery, in one workflow.

It orchestrates coding CLIs you have already installed and signed into. It
bundles no subscription, resells no capacity, never logs you into a provider and
never reads a credential store. Your provider account, its plan limits, its rate
limits and its availability remain yours.

**What this release is for.** Evaluating AgentOS on a machine you own, against
repositories you are willing to have an agent write to. It is not a production
install, and the sections below are the actual envelope rather than a
disclaimer.

A full list of what is in this release, by area, is in
[`CHANGELOG.md`](../../CHANGELOG.md).
[`v0.1.0-support-matrix.md`](v0.1.0-support-matrix.md) states what is supported
and on what evidence.

## Before you install

| Requirement | Exact expectation |
| --- | --- |
| Machine | An Apple Silicon Mac running macOS. Linux is unverified. Windows is unsupported — the runner relies on POSIX process-group, path and command behaviour. |
| Node.js | Use `22.17.0`, recorded in `.nvmrc`. The top-level checks accept a wider range that is not covered by every locked development dependency. |
| npm | 10.9.2 or newer — the npm that generated `package-lock.json`. |
| Docker | Docker with Docker Compose, for the PostgreSQL service this repository defines. |
| Git | Any recent version, with an author identity and non-interactive clone/push authentication for the runner account. The source must be a `git clone`; generated source archives are for hash verification, not installation. |
| A coding CLI | The official Codex CLI, already installed **and already signed in**, under the same macOS account that will run the AgentOS runner. The runner uses a fixed `PATH`; see the corrected quickstart. Claude Code is optional; Pi is outside the supported surface. |
| GitHub CLI | Optional for branch-only delivery; required, installed and authenticated as the runner account for automatic pull-request creation. |

The starter agent a fresh installation creates runs on Codex, so Codex is the
only provider CLI a complete installation requires.

## Installing

[`v0.1.0-developer-preview.md`](v0.1.0-developer-preview.md) is the install
sequence, written to be followed literally. In outline:

```sh
git clone https://github.com/mosonlab/agentos.git
cd agentos
git checkout v0.1.0
npm ci
npm run setup:local
npm run build
docker compose up -d postgres
until docker compose exec -T postgres \
  sh -c 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
do
  sleep 1
done
export GOAL5A0_MASTER_SHA=485fb118db96e3977006a2edc866a38b751ff0e2
export GOAL5A0_CONTROL_PLANE_A_SHA=c671439831b075568420b92f4494227fa7fc392b
npm run db:migrate:release -- --fresh
```

Then run `npm run dev:api`, `npm run dev:runner` and `npm run dev:web`, in that
order, in three terminals and open `http://127.0.0.1:5173`. A database with no
projects in it opens the five-screen installation wizard, and finishing it
creates your project, environment, starter agent, repository and grant in one
transaction.

These points about the sequence are worth reading rather than skimming:

- **It has to be a `git clone`.** The generated source archives attached to this
  release carry no `.git`, and parts of the release path read the checkout's
  history and tracked-file list. They are there so you can verify the published
  `SHA256SUMS`, not to install from.
- **`npm ci` must be allowed to run lifecycle scripts.** The `postinstall` in
  this repository generates the database client; `--ignore-scripts` is not
  supported, and an install done that way looks successful and fails later
  somewhere unrelated. The immutable tag's lockfile resolves packages through
  `registry.npmmirror.com`; that third-party host remains part of the tag's
  install trust boundary even though the maintained branch now uses the official
  npm registry.
- **`npm run setup:local` writes `.env` exactly once**, at mode `0600`, with
  values it generates. It prints a class rather than a value and refuses to
  rewrite an invalid existing file. The later `--upgrade` form preserves every
  assignment and adds only missing safe-to-generate keys; it reports named
  repairs but never rotates weak credentials automatically. There is no
  overwrite or rotation flag. `.env.example` documents the keys; it is not a
  file to copy.
- **`npm run build` is required.** The public checkout ships no `dist/`
  artifacts; API and runner workspace imports and the Codex MCP server resolve
  to built files.
- **PostgreSQL must be ready, not merely running.** The readiness loop above
  must succeed before the release migration starts.
- **`npm run db:migrate:release` is the only supported migration command.** It
  proves its target, proves the target is empty, and runs the migration only
  behind its preflight. `npm run db:migrate` is `prisma migrate dev` — a
  development command that runs no preflight and will rewrite migration history.
  Never point that one at a database you would miss.

The Inbox service is optional. No launchd definition is shipped or supported in
v0.1.0. Remote access and this repository's task-chain templates are also
outside the supported sequence.

### What the guarded migration checks

`npm run db:migrate:release -- --fresh` takes an exclusive maintenance lock
before it inspects any schema state and holds it across the emptiness census, the
migration-set check, the preflight, the deploy, the status check and the drift
check. The preflight it runs refuses to migrate without evidence that this
migration set passed review; a release clone carries that evidence as
`release-authority.pub` and `release-authority.json` at the repository root, and
an export without a valid attestation stops rather than defaulting to trusted.

`--existing`, the mode for migrating an installation that already holds data, is
a separate matter and stops at `oss-d-interface-unavailable`: the verified-backup
attestation producer its safety story rests on has not merged. Migrating an
existing installation is not supported in this release.

None of these refusals may be worked around by taking the preflight out of the
path. [`v0.1.0-migration-and-recovery.md`](v0.1.0-migration-and-recovery.md)
describes every refusal condition and how the attestation is provisioned.

## Upgrading

- **There is no upgrade path between preview builds.** A new preview is a fresh
  install. Nothing here is packaged, notarized or self-updating.
- **There is no down migration**, and rolling back code does not roll back the
  database: an earlier commit leaves every applied migration applied. An older
  build against a newer schema is its own failure mode, not a recovery.
- **Restore is only ever to an isolated target.** Restoring over a database
  something is still using is not a supported operation of this release, and the
  restore interface itself is separate work.
- **Rotating secrets is a human recovery, not a command.** In particular,
  rotating the secret encryption key while encrypted rows exist destroys them
  unrecoverably.

On the Developer Preview, the recovery story for a database you care about is:
do not put it here yet.

## Verifying what you installed

Run repository verification only in a separate worktree or clone with all
AgentOS services stopped. Before any test, isolate every host path a test process
can resolve:

```sh
export RUNNER_WORKSPACE_ROOT="$(mktemp -d)"
export CONTROL_PLANE_STATE_DIR="$(mktemp -d)"
export FILES_ROOT="$(mktemp -d)"
```

Never run the test suite against paths used by a live installation.

```sh
npm run db:validate
npm run typecheck
npm run lint
npm run build
npm test
npm run agentos -- help
docker compose config --quiet
npm run test:dependency-gate
npm run test:snapshot-scan
npm run snapshot:scan
```

`npm test` needs no database and no running service, but it provisions real
workspace paths and needs `npm run build` first. `npm run test:db` is deliberately
separate: it drops and recreates the target schema on a scratch PostgreSQL you
supply — never one holding anything you want to keep.

## Known limitations

Read these before deciding what to point this at.
[`v0.1.0-security.md`](v0.1.0-security.md) states each boundary and what is and
is not checked.

- **It is not a sandbox.** The provider adapters launch the coding CLI with
  non-interactive permission-bypass flags. With the shipped same-user default the
  agent runs with your own user's authority on your own machine. AgentOS grants
  constrain AgentOS's own APIs — a real authorization and audit boundary — but
  they are not operating-system containment. An agent that reads a file outside
  its grant by running a shell command is stopped only by what its OS account
  cannot do.
- **No network isolation is enforced.** The environment a fresh installation
  creates is labelled open because it is.
- **Loopback only, and there is no remote authentication design** — no login, no
  per-user identity, no session model for anyone but the machine's own operator.
  Putting a tunnel or a reverse proxy in front of it does not add one. Exposing
  any of these services is unsupported.
- **The repository access level does not gate delivery's push.** Treat any
  repository you register as writable by the agent.
- **The Files path walk can be raced** by an adversary who can already write
  inside the Files Root. Path strings, symlinks and hardlinks are refused, but an
  intermediate directory can be swapped after the walk has checked it and before
  the open; closing that needs a native helper.
- **Runner separation is partial.** Launching the CLI under a dedicated,
  minimally privileged account separates runners from each other; one runner's
  account still owns every workspace it has created.
- **The unguarded migration path bypasses the preflight**, and that bypass is
  procedural rather than technically closed.
- **Goals are stored but not executed.** The control plane holds a goal, its
  definition of done, its progress log and its limits, and the console edits
  them; nothing schedules work from a goal, measures its spend, or stops it on
  spend, time or stall.
- **The command-line interface exposes only `agentos help`.**
- **Five of the surfaces in this release merged without an independent
  implementation review.** Four carry a review of the plan but not of the code
  that was written from it — the control plane's workspace ownership change
  (Control-plane A), the closed-by-default public snapshot mechanism (OSS-A),
  the templates release closure (OSS-C), and the documentation factual-accuracy
  pass over the READMEs (OSS-E). One carries no review at all: the
  verified-backup attestation producer that `--existing` migrations depend on
  (OSS-D). This is accepted debt, not a closed item. The release was cut with
  the gap recorded rather than with the record rewritten to say a review
  happened; each surface is reviewed after the cutover, and anything found is
  corrected as a `v0.1.1` rather than by changing this release.
- **The snapshot you are reading was assembled by hand, and its reproducibility
  rests on recomputation rather than on a tool.** The release plan calls for a
  deterministic builder that reads allowlisted bytes out of Git objects and emits
  a provenance manifest; that builder is not in this release and is deferred to
  `v0.1.1`. What was done instead: the published file list came from the
  repository's own snapshot scanner, the export was built twice into two
  independent directories, each was turned into a parentless Git commit and the
  two commit ids had to agree, and an independent reviewer recomputed the tree
  hash separately. That is evidence that this one build is deterministic. It is
  not the same thing as a tool you can re-run to check.
- **The OSS-B0 and OSS-F0 automated harnesses are not shipped in v0.1.0.** The
  immutable tag still exposes four package commands whose target files are
  absent; do not run them. The maintained branch removed those entries so its
  package scripts expose only shipped targets. The snapshot scanner,
  `npm run snapshot:scan`, and merge gate, `scripts/merge-gate.sh`, are shipped
  and runnable.
- **Some files in the immutable tag name paths that are not published.** A file
  may point at a runbook, sample capture, design note, or deploy script held back
  from the snapshot. Following that reference finds nothing; a path name does not
  disclose the held-back content. The maintained branch removes the four broken
  package commands and the unsupported launchd plist reference; the tag remains
  byte-for-byte historical.
- **Platform evidence is what it says it is.** Codex and Claude Code adapters are
  verified; Claude subscription authentication is maintainer-verified on macOS
  Apple Silicon. A complete clean-machine installation is still pending. Linux
  is unverified and Windows is unsupported.
  [`v0.1.0-support-matrix.md`](v0.1.0-support-matrix.md) gives the evidence
  boundary for every row.
