### R5-MF-1 — the GitHub dry check named a JSON field `gh` does not support, so the gate could not run

**Status: closed.**

Round 4's dry check A ran `gh pr view <ACTUAL_IMPL_PR_NUMBER> --json number,state,merged,mergeCommit,headRefOid,url`. `gh pr view --json` has no `merged` field: running `gh pr view --json` with no value on the installed `gh` 2.89.0 prints the supported set, and `merged` is absent from it while `number`, `state`, `mergedAt`, `mergeCommit`, `headRefOid`, and `url` are all present. Closed by:

- **Supported field list.** Dry check A now requests `number,state,mergedAt,mergeCommit,headRefOid,url` only, and merged-ness is read from `state == "MERGED"` — the value that replaces the missing boolean — never from a `merged` field. A standing rule requires re-reading `gh pr view --json` with no value and using only the names it prints before any future change to the list, and Step 14.5 records the authoring-time `gh --version` next to the list so a later reader knows when to recheck.
- **Null-safe commit extraction.** `mergeCommit` is `null` on every unmerged pull request, so the commit is extracted as `(.mergeCommit // {}) | (.oid // "")` rather than indexed directly. A `MERGED` response whose `mergeCommit` is `{}` is a stop, not a throw.
- **Explicit merged-success definition.** Success is the conjunction: `state == "MERGED"`, `mergedAt` non-null, `mergeCommit.oid` matching `^[0-9a-f]{40}$`, and `number`/`url`/`headRefOid`/`mergeCommit.oid`/`mergedAt` all equal to the durable handoff record's `prNumber`/`prUrl`/`authorizedReviewedHead`/`mergeCommit`/`mergedAt`. A `headRefOid` that no longer equals the authorized reviewed head is head drift and therefore a disagreement.
- **Every failure mode mapped.** Nonexistent pull request, CLI failure (auth, network, unsupported field), JSON parse or schema error, missing key, `OPEN`, `CLOSED` with a null `mergedAt`, and any field disagreement all yield `STOPPED_FOR_REROUTE`. A non-zero `jq` exit is treated as unparseable output and stops as well.

None depends on an unsupported field. ### R5-MF-2 — the three-copy identity record was self-referential and could never be written

**Status: closed.**

Round 4 required issue #97's implementation task output, `docs/reviews/goal-5a0-implementation-evidence.md`, and the runbook to carry the same four fields — including `ACTUAL_MERGE_COMMIT` — with identical values. Two of those three are files inside the pull request whose merge commit they would have to name, and a file cannot contain the commit that merges the tree containing it. The third, the task output, is written by an Agent Run that has already completed by the time the merge happens, so the producer named for the merge commit could never write it either. The requirement was therefore unsatisfiable in all three copies at once, and the nearest reading — rewrite the merged files afterwards, or predict the commit — would either invent a SHA or make the merged tree disagree with itself. Closed by:

- **Lifecycle-separated authority.** "Implementation PR identity of record" is replaced by "Implementation identity and durable handoff record", which splits the facts across three records with three lifetimes and names a producer for each. **Stage 1**, while the implementation is active: issue #97's implementation Agent Run records `ACTUAL_IMPL_PR_NUMBER`, `ACTUAL_IMPL_PR_URL`, and `ACTUAL_IMPL_HEAD` in its own AgentOS task output, and records no authorization and no merge commit. **Stage 2**, before the merge: the delegated exact-head authorizer writes an AgentOS TaskActivity on that implementation task recording the exact reviewed head, the base it was reviewed against, the required-check names and conclusions at that head, and the review evidence; drift invalidates it and a re-authorization is a new activity. **Stage 3**, after an exact-head match merge: the same delegated operator writes one AgentOS TaskActivity of the stable kind `implementation_merge_handoff`.
- **One durable handoff.** The stage-3 payload carries `issueNumber`, `implementationTaskId`, `prNumber`, `prUrl`, `authorizedReviewedHead`, `mergeCommit`, `mergedAt`, `masterSha`, and `ancestryVerified` (the freshly verified `git merge-base --is-ancestor` result against a just-fetched `origin/master`). It is the single durable handoff issue #98 consumes. Because it is an activity on the task rather than a file in the merged tree, and because the merge-closeout step runs after the merge, nothing is self-referential.
- **Producer explicitly assigned.** Stage 3 is assigned to the delegated operator at the merge-closeout step — not to the implementation Agent Run, which has completed by then. Step 15.6 states each stage, its producer, and what that producer cannot know, so the impossible assignment cannot recur.
- **Documents hold procedure, not records.** The evidence document and the runbook's "Inbox 3a handoff" section define the procedure, the producers, and the payload schema. They may retain the stage-1 placeholders indefinitely, they never claim to contain the merge commit, and they are explicitly **not required to be rewritten after the merge**; where they reference a post-merge value, they reference the activity that carries it.
- **Consumption and invalidation.** New dry check 0 retrieves the latest `implementation_merge_handoff` activity for the exact `implementationTaskId` and yields `STOPPED_FOR_REROUTE` on a missing, duplicate, conflicting, superseded, mismatched, or malformed record, or one attached to another task; only then do checks A and B recheck GitHub and ancestry, and only all three passing yields `SAFE_TO_IMPLEMENT`.
