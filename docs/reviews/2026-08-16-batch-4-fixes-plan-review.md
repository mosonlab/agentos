## must-fix

1. **[Feasibility; focused feasibility pass — WI-3 cannot run under the repository's Prisma version.]** The plan awaits ``tx.$queryRaw`SELECT pg_advisory_xact_lock(...)` `` at `docs/plans/batch-4-fixes-usage-correctness-plan.md@3720d74:457-473` and only anticipates bound-parameter typing failure at `:492-496`. The repository pins Prisma 6.19.0 (`packages/db/package.json:29-36`), and a direct probe against the dedicated `agentos_test` schema using the plan's exact query shape failed before any event read: `{"ok":false,"name":"PrismaClientKnownRequestError","code":"P2010",..."Failed to deserialize column of type 'void'"}`. The same parameterized query with `pg_advisory_xact_lock(...)::text AS locked` returned `{"ok":true,"rows":[{"locked":""}]}`. Thus every recompute would throw, the ingest catch would suppress every cache update, and the backfill would report every session failed. **Remedy:** keep the parameterized form but cast the function result to a Prisma-supported type (the verified `::text AS locked` form), add this exact real-DB call to WI-6, and document the `void` deserialization failure separately from the numeric-parameter fallback.

2. **[Scope + coherence — WI-1 does not implement the spec's per-payload cost rejection and lets one invalid event erase valid cost from the session total.]** The spec requires cost to be accepted only when it is finite, non-negative, and `< 10^8`, otherwise omitted (`docs/specs/batch-4-fixes-usage-correctness.md:356-361`). The plan's `costAmount`, however, accepts every finite non-negative number (`docs/plans/batch-4-fixes-usage-correctness-plan.md@3720d74:268-273`) and defers the upper-bound/rounding rejection until `costColumn` after all events have been summed (`:294-300`). The actual aggregation adds every surviving event cost into one value (`packages/db/src/usage.ts:72-79`). Consequently `{total_cost_usd: 1e9}` plus a valid `{total_cost_usd: 0.05}` becomes one out-of-range sum and stores `null`, instead of omitting the invalid event and preserving `0.05`; it also leaves `extractUsage` outside its specified contract. **Remedy:** perform the rounded `Decimal(12,4)` storable-range check in `costAmount` so an invalid event is omitted before `sumUsage`, retain an aggregate `costColumn` guard for overflow across individually valid events, and add a mixed invalid-plus-valid-event regression.

3. **[Feasibility — WI-6's required backfill-failure test injects the error at the wrong client layer.]** WI-3 moves the write to `tx.session.update` inside `$transaction` (`docs/plans/batch-4-fixes-usage-correctness-plan.md@3720d74:457-473`), but WI-6 test 3 says only to proxy `session.update` on the outer client (`:714-719`). The repository's proven transaction instrumentation explicitly intercepts outer `$transaction`, wraps the callback's transaction client, and replaces the delegate on that inner client (`packages/api/src/chain.dbtest.ts:218-239`). Without that inner wrapper, `recomputeSessionUsage` receives Prisma's native `tx`, bypasses the injected outer `session.update`, and the planned `{scanned: 3, updated: 2, failed: 1}` assertion instead sees no injected failure. **Remedy:** specify the same Proxy-over-`$transaction` pattern for test 3, replacing `tx.session.update` only for the selected session id; bind all other outer client methods as the prior art does, then keep the second plain-client repair pass.

4. **[Coherence — the acceptance matrix claims to verify the backfill's non-zero process exit, while WI-6 explicitly declines to execute it.]** The spec requires the three-session check to prove both the summary and a non-zero process exit (`docs/specs/batch-4-fixes-usage-correctness.md:667-670`), and the current CLI is a module-scope client/top-level script (`packages/db/prisma/backfill-session-usage.ts:7-29`) invoked by the workspace command at `packages/db/package.json:21`. The plan says the exit code is “covered by reading it, not by spawning a process” (`docs/plans/batch-4-fixes-usage-correctness-plan.md@3720d74:714-721`) but maps WI-6 test 3 to “summary, non-zero exit” in traceability (`:911-915`). Reading `process.exitCode = 1` is not an executable acceptance check and does not catch wrapper/import/finally regressions. **Remedy:** make the thin wrapper's main function testable with injected `backfillSessionUsage`/client or spawn it against the dedicated scratch schema, assert exit code 1 plus the full summary on partial failure, and assert exit code 0 after repair; update traceability to name the test that actually executes the wrapper.

5. **[Scope — the plan weakens the mandatory deploy/rollback rehearsal into an optional disclosure.]** The authoritative spec requires the complete sequence to be rehearsed end to end on a scratch database (`docs/specs/batch-4-fixes-usage-correctness.md:672-688`) and makes a rehearsed, versioned runbook part of the definition of done (`:757-766`). The repository supplies a bounded harness that refuses `public` and rebuilds only its dedicated schema (`packages/api/src/testdb.ts:12-14,18-55`); in this review `npm run test:db` successfully rebuilt `agentos_test`, applied all 12 migrations, and passed the existing database suites. The plan nevertheless permits a final header that says “not rehearsed” when no scratch database is reachable (`docs/plans/batch-4-fixes-usage-correctness-plan.md@3720d74:854-861`). That can advance an unproven rollback procedure directly toward production despite the spec's safety gate. **Remedy:** keep honest header wording, but make “not rehearsed” a failed implementation gate rather than an acceptable completion state; require the full §7.3 rehearsal and recorded result before the implementation step can finish, or explicitly return FAIL/open question without waiving the DoD.

6. **[Feasibility + coherence — the operator migration command corrupts URLs that already have query parameters, including the repository's own URL convention.]** WI-8 prescribes `DATABASE_URL="${DATABASE_URL}?options=..."` (`docs/plans/batch-4-fixes-usage-correctness-plan.md@3720d74:803-813`, repeated at `:996-999`). The repository's test URL is already query-bearing (`...?schema=agentos_test`) and reads its `schema` parameter explicitly (`packages/api/src/testdb.ts:6-10`). A URL-only probe using that shape returned `{"searchParams":{"schema":"public?options=-c lock_timeout=3s"},"hasOptions":false}`: the second `?` is absorbed into the schema value, so `lock_timeout` is not installed and the target schema is changed. **Remedy:** have the runbook construct the URL with `URL.searchParams.set("options", "-c lock_timeout=3s")` (or use the correct `&` only after explicitly detecting an existing query), verify the resulting parameter names without printing credentials, and rehearse both a bare URL and a `?schema=...` URL.

## should-fix

1. **[Feasibility — the diff-surface checks are neither portable nor failing gates.]** The plan uses a PCRE negative lookahead with `grep -E` at `docs/plans/batch-4-fixes-usage-correctness-plan.md@3720d74:973-980`; running that expression with the workspace's grep produced `grep: repetition-operator operand invalid`. The other two commands use `grep ... && echo "VIOLATION"`, which exits zero when a forbidden path or credential is found, so automation can report success on the violation path. This matters because the actual constraints exclude `apps/web`, `schema.prisma`, and new migration folders (`docs/specs/batch-4-fixes-usage-correctness.md:565-593`). **Remedy:** replace the negative lookahead with two explicit filters (or `rg`), and wrap every check so a match prints the offending paths and exits non-zero; add a no-match success message only after the guard passes.

2. **[Coherence — WI-6 test 2 cannot settle the uncertainty that §13 assigns to it.]** Test 2 only opens a transaction, takes a lock directly, and checks for one granted `pg_locks` row (`docs/plans/batch-4-fixes-usage-correctness-plan.md@3720d74:709-712`), while §13 says that same test must hold the lock, start a second *recompute*, time the failure, and record `55P03` versus `P2028` (`:1036-1042`). The repository's existing two-client DB-test pattern already supplies the necessary lifecycle and `finally` disconnect (`packages/api/src/chain.dbtest.ts:67-92`). A focused review probe on this environment observed `P2010` wrapping PostgreSQL `55P03` after about 279 ms with `lock_timeout=200ms`, proving the experiment is practical. **Remedy:** extend test 2 to invoke the real `recomputeSessionUsage` on a second client under a deliberately shorter local timeout, assert/record the nested PostgreSQL code and a bounded elapsed time, and keep the granted-lock visibility assertion as a separate preliminary check.
