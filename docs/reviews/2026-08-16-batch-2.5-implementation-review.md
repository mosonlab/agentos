## 2. The highest-risk change, verified rather than trusted

Spec §5.3 says the code review must verify the parked-successor guard
explicitly. It holds:

- `packages/db/src/workflow.ts:181-192` returns early for an archived or
  `BACKLOG` successor **before** the CAS loop, and `:285-297` repeats the check
  **inside** the loop after each re-read — which is the branch that actually
  matters, because the operator can park the row between the read and the claim.
- `parkedReason` covers every value the CAS predicate does not: the CAS matches
  `TODO|DOING|REVIEW`, `DONE` returns earlier at `:233`, and `BACKLOG`/archived
  are the two remaining cases. There is no reachable fifth state.
- The test is real, not decorative: `chain.dbtest.ts:288-296` bounds the hang with
  a **Prisma interactive-transaction timeout on a disposable client**, not with
  `Promise.race` — a lost race would not cancel the database operation, an
  expired transaction does. `chain.dbtest.ts:322-357` drives the between-read-and-claim
  race with a `Proxy` around `tx.task.updateMany`, asserts `parked === true`, and
  then asserts zero runs. All three ran green here in 20 s ceilings.

`fireAtTask` (`scheduler.ts:159-187`) also gained a genuine production fix, not
just a guard: before the row lock, two concurrent callers were prevented from
double-firing only by accident (both derived the same `runNumber` and one lost
to the dedupe key). Serialised by the lock, the loser would have observed run 1
and queued run 2. The `_count.runs > 0` re-check under the lock closes it. That
was found by the implementer and fixed in the right place.

## 4. Must-fix

### M1 — `POST /tasks/:taskId/start` does not implement the spec's `startable`; it starts gated `REVIEW` steps, starts `DOING` steps, and returns 500 when the task has no repo

**Lens:** feasibility + coherence. **Section:** §4.3, §5.2.

Spec §4.3 is a binding definition: a step is startable when *all* of —
`assigneeType = AGENT`, an assignee agent exists and is not archived, **a repo is
set**, **status is `TODO` or `BACKLOG`**, not archived, no active run, and
`runs.length < maxSessionsPerTask`. `packages/api/src/chain.ts:107-115` implements
exactly that, and its own docstring at `chain.ts:100-106` claims it is *"the
single source for both the API guard and the button's enabled state — the web app
reads this boolean rather than re-deriving it, so the two cannot disagree."*

The route never calls it. `packages/api/src/app.ts:1838-1860` checks only: exists
(404), archived (409), `DONE` (409), non-`AGENT` (409), active run (409), budget
(409). Three of the seven conditions are missing — status, repo, and the archived
assignee (the last is recovered accidentally, by `enqueueTaskRun` throwing
`ArchivedAssigneeError` and being mapped at `:1868`).

**Failure scenario, reproduced.** I ran each of these through `createApp(db)`
against the migrated test schema:

```
REVIEW task, approvalGate=true, an OPEN InboxMessage on gateTaskId
  POST /tasks/:id/start -> 201 {"runId":"…","runNumber":1};  runs after: 1
  (the subsequent archive correctly refuses: 409 "Cannot archive a task with an active run")

DOING task, no active run (its last run FAILED)
  POST /tasks/:id/start -> 201 {"runId":"…","runNumber":1}

AGENT task with repoId = null
  POST /tasks/:id/start -> 500 {"error":"Internal server error"}
  server log: Error: Task … cannot be queued without an agent and repo
```

Consequences, in severity order:

1. **A run is enqueued on a step whose approval gate is still open.** The agent
   starts work on a step no human has approved; when that run completes,
   `advanceTemplateTask` runs again and can open a second gate card for the same
   task. Spec §5.5 lists gate semantics under "what must not change".
2. **A 500 on a documented endpoint.** `enqueueTaskRun` (`workflow.ts:72-74`)
   throws a plain `Error` for a missing repo, and the route's `catch`
   (`app.ts:1865-1874`) only maps `ArchivedAssigneeError` and `P2002`.
3. `DOING` is `Retry`'s territory, not `Start now`'s.

**Reachability.** The chain card renders `Start now` only where the API said
`startable`, so this is primarily an API-contract defect — but it is not
theoretical: the card is drawn from a poll up to 2.5 s stale, so a step that
becomes `REVIEW`-with-a-gate between the poll and the click is startable in the
UI and accepted by the route.

**Remedy.** Make the route use the function that already exists. Inside the
transaction, after `lockTask`, read the row with the fields `StartableRow` needs
(`assigneeType`, `assigneeAgentId`, `repoId`, `archivedAt`, `assigneeAgent:
{archivedAt}`) plus the run facts already gathered, call `startable(...)`, and
keep the existing specific 409 messages (S3–S6) as a reason ladder in front of it
so the spec's error strings are preserved; add `409 "Only Todo and Backlog steps
can be started"` and `400 "This task has no repository"` for the two uncovered
cases. Add three dbtests to `tasks.dbtest.ts`: gated `REVIEW` → 409 with zero
runs created; `DOING` → 409; missing repo → 400, never 500.

## 5. Should-fix

### S1 — A quarantined automation renders a confident, wrong English description of the cron expression the control plane just rejected

**Lens:** feasibility. **Section:** §4.7, §5.4 [A9], E10.

`apps/web/src/lib/schedule.ts:14-23` falls back to the raw expression only when
`cronstrue` **throws**. `cronstrue` does not throw on expressions the control
plane's own parser rejects — it silently reinterprets them. Measured directly:

```
"*/5 * * * * 7 9" | cron-parser REJECT: Invalid cron expression, too many fields
                  | cronstrue: "Every 5 seconds, only on Sunday, only in 1909"
"not a cron"      | cron-parser REJECT | cronstrue THROW  (the fallback works here)
```

Rendered live at `/automations`, the row for such a task reads, simultaneously:

```
Every 5 seconds, only on Sunday, only in 1909      Quarantined
*/5 * * * * 7 9 · UTC                              Fix the cron expression
```

Spec [A9] is explicit that `cronProse` "must degrade to the raw expression rather
than mis-describe one". The operator is told to fix an expression while the same
row fluently describes what it supposedly does — the failure mode [A9] exists to
prevent.

**Remedy.** The page already knows: `automationState(task) === "quarantined"`
means the server refused the expression. In `Automations.tsx:110`, render
`task.cron` verbatim when the state is quarantined and reserve `cronProse` for
`active`/`paused`. Same in the `CronEditor` preview (`:82`) is optional — there
the operator is mid-edit and prose is useful. Add a `schedule.test.tsx` case
pinning the quarantined branch.

### S2 — The Endpoint card's copy button yields a relative path, which no external system can post to

**Lens:** feasibility. **Section:** §4.6.

`apps/web/src/pages/Triggers.tsx:125` builds `POST ${apiBase}${endpointPath}`, and
`apiBase` is `/api` unless `VITE_API_URL` is set (`lib/api.ts:16`). Rendered live,
the card shows `POST /api/hooks/templates/tpl1`, and `Copy` puts
`/api/hooks/templates/tpl1` on the clipboard. The card exists to hand an outside
system a URL; a relative path is not one, and `/api` is the Vite dev proxy prefix
rather than a control-plane path at all.

This matches the spec's literal wording (`POST <apiBase>/hooks/templates/<id>`),
so it is a defect in the spec's assumption as much as in the code — flagged, not
silently narrowed.

**Remedy.** Resolve against the page origin when `apiBase` is relative:
`new URL(apiBase + endpointPath, window.location.origin).toString()`, so the
operator copies something postable, and keep the visible text as-is if the full
URL is too long for the card.

### S3 — `POST /task-templates/:id/fire` returns 500 on a malformed JSON body

**Lens:** feasibility. **Section:** §5.2.

`app.ts:1464-1465` calls bare `JSON.parse(raw)` outside any `try`. Every other
body-reading route in the file goes through `readJson`, which answers 400.
Reproduced: `POST /task-templates/:id/fire` with body `{not json` →
`500 {"error":"Internal server error"}`, `SyntaxError` on the server.

The UI always sends `{}` so this is API-callers only, but a 500 is the wrong
surface for a client error.

**Remedy.** Wrap the parse and return `400 {"error":"Invalid JSON payload"}` —
the same string the webhook route already uses at `app.ts:568-571` — keeping the
existing empty-body branch.

### S4 — Two spec-mandated *render* tests were delivered as source-text greps, and one assertion asserts nothing

**Lens:** coherence / quality. **Section:** §7.

Spec §7 items 8 and 10 are render assertions ("Board renders five columns in
order; a `BACKLOG` task lands in the first", "`Archive All` is absent when `Done`
is empty, present when it is not"). What shipped reads the component's own source
text:

- `tasks-board.test.tsx:41-45` — greps `const COLUMNS` for `label:`/`status:` literals.
- `tasks-board.test.tsx:53` — greps for the literal JSX condition
  `column.status === "DONE" && columnTasks.length > 0`; any reformat breaks it and
  no render is exercised.
- `tasks-board.test.tsx:49` — `assert.doesNotMatch(source, /status !== "BACKLOG"/)`
  **asserts nothing**: it checks that a string nobody would ever write is absent.
  It cannot fail and cannot detect the regression it names (E16).
- `chain-list.test.tsx:89-94` — same technique for `fatal(error, task)` and the
  chain-card condition.

Source-grep tests are a pre-existing repo idiom (`task-detail.test.tsx:70-72`
predates this batch), so this is a continuation, not an invention — but it is
still a coverage gap where the spec asked for rendered proof, and `:49` is dead
weight regardless of idiom.

Two more in `triggers.test.tsx:99-110` are near-tautological: both construct an
`<ErrorNotice message="…literal…" />` and assert the literal appears. They prove
`ErrorNotice` renders its prop, not that `TriggerDetailPage` routes the API's
`error` string into it.

**Remedy.** Export `COLUMNS` and the column head as a small component (or render
`TasksPage` with the poll stubbed, as the other suites do) and assert the five
`<th>`-equivalents and a `BACKLOG` card's placement from markup; delete `:49` or
replace it with a positive assertion that the Backlog column body carries the
drop handler. For the two trigger tests, render `TriggerDetailPage` with a
stubbed 400 and assert the names reach the DOM.

### S5 — The global `GET /tasks` poll now runs two extra whole-database queries for enrichment its only caller does not read

**Lens:** feasibility (efficiency). **Section:** §5.2, E4.

`apps/web/src/pages/Projects.tsx:75` polls `/tasks` **globally**, every 2.5 s,
purely to count tasks per project. That request now additionally:

1. collects every distinct `chainId` in the response and re-queries
   `db.task.findMany({ where: { chainId: { in: chainIds } } })` with **no project
   filter** (`app.ts:1376-1385`) — effectively the whole task table again;
2. builds a position map per chain by filtering `chainRows` once per chain
   (`app.ts:1387-1397`), i.e. O(chains × rows);
3. runs a third `groupBy` over cron copies (`app.ts:1403-1410`).

E4 ("computed once per request from a single grouped query, not N+1") is
satisfied in the sense that matters — the cost is constant in task count, not
quadratic in it — so this is efficiency, not correctness, and it is invisible at
dogfood scale. But it is a hot poll paying for `chainProgress`,
`recurringLastFiredAt` and `position` that the Projects page never renders.

**Remedy.** Gate the enrichment behind the caller: compute `chainProgress` /
`recurringLastFiredAt` only when `projectId` is present, or add an explicit
`?enrich=false` (or `fields=`) that `Projects.tsx:75` passes. Keep the
project-scoped behaviour exactly as it is.

### S6 — Dead code and a wire/type mismatch

**Lens:** coherence / quality.

- `apps/web/src/pages/Automations.tsx:154` filters `task.archivedAt === null`
  after polling `/tasks?projectId=…` with no `archived` param — the API already
  defaulted to `archived=false` (`app.ts:1355-1364`), so the predicate can never
  remove a row. Harmless, but it reads as a guard that is doing work.
- `apps/web/src/lib/types.ts:273-279` declares `ChainProgress` **without
  `position`**, while `GET /tasks` sends it (`app.ts:1418-1420`) because spec
  §5.2 requires it. Nothing on the web side consumes it. Either the field is
  genuinely unused — in which case say so where it is produced — or the type is
  wrong. Right now a future consumer would have to discover it by reading the
  API.

**Remedy.** Delete the redundant predicate; add `position: number | null` to the
web `ChainProgress` with a one-line note that only the API-side ordinal is
authoritative, or drop it from the response and amend §5.2.

### S7 — An empty-string default makes the `required` badge and the fire route disagree

**Lens:** coherence. **Section:** §4.6.

`Triggers.tsx:168` badges a variable `required` when `path === "" && fallback ===
""`. The manual-fire route treats `""` as a resolved value: `app.ts:1477-1480`
accepts any `typeof fallback === "string"`, so `defaults: { reporter: "" }`
resolves rather than 400s. Rendered live, `reporter` carries a red `required`
badge on a trigger that fires successfully.

The UI strips empty values before saving (`Triggers.tsx:242-243`), so `""` only
arrives via a direct `PATCH` or a hand-seeded template — narrow, but the badge is
supposed to mean "every fire that does not carry it will 400", and here it does
not.

**Remedy.** Pick one meaning and apply it in both places: either treat `""` as
absent server-side (`typeof fallback === "string" && fallback !== ""` at
`app.ts:1478`), or stop badging when a default key exists at all. The first is
the safer reading — an empty prompt variable is almost never intended.
