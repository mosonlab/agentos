## must-fix

1. **[Feasibility, Coherence] WI-3 cannot build in the declared order, and its formatter callback has the wrong type.** The plan makes WI-3 independent and says it calls `setFormatLocale` (`docs/plans/batch-1-settings-i18n-plan.md:488-515`), but that export is not added until the dependent WI-4 (`docs/plans/batch-1-settings-i18n-plan.md:548-558`), and the current formatter has no such export (`apps/web/src/lib/format.ts:1-29`). Even after WI-4, the proposed `translate(locale, key, vars)` signature (`docs/plans/batch-1-settings-i18n-plan.md:496-503`) cannot be passed directly where `(key, vars) => string` is required. **Remedy:** either land the formatter registration API in WI-3 or move provider registration into WI-4, pass a locale-bound closure such as `(key, vars) => translate(locale, key, vars)`, and require build/typecheck at the WI-3 commit boundary.

2. **[Feasibility, Coherence] The sweep guard cannot prove the extraction it is designated to accept.** WI-8 scans only JSX text, four literal attributes, and `window.confirm` (`docs/plans/batch-1-settings-i18n-plan.md:699-735`). It misses common user-visible forms already present in the named source set: component props such as `label` and `hint` (`apps/web/src/pages/Secrets.tsx:40-61`), object-literal labels (`apps/web/src/pages/Tasks.tsx:36-40`; `apps/web/src/pages/Secrets.tsx:126-127`), and returned/template-literal copy (`apps/web/src/pages/Automations.tsx:25-27`). A single JSX-text fixture can therefore pass while hundreds of untranslated literals survive. **Remedy:** use a TypeScript/JSX AST scan, or explicitly cover every user-copy prop/object key plus conditional and template literals; add failing fixtures for each syntax category and scan user-facing helper modules as well as pages/components.

3. **[Scope] User-visible schedule prose is explicitly dropped despite the full-UI localization requirement.** The plan knowingly leaves `cronstrue` output in English and calls it a follow-up (`docs/plans/batch-1-settings-i18n-plan.md:1517-1521`), while the spec requires no English in the Chinese UI and extraction of every user-visible string (`docs/specs/batch-1-settings-i18n.md:175-190`). This is live UI output: `cronProse` requests the library's default English prose and `nextRunLabel` emits English fragments (`apps/web/src/lib/schedule.ts:7-22,25-36`). **Remedy:** put locale-aware cron prose and the future-time fragments into WI-4/WI-6, load/use the library's Chinese locale where supported, and add English/Chinese schedule tests.

4. **[Scope, Coherence] Invalid optional telemetry is allowed to stop task claiming.** WI-9 deliberately expects a 400 for the whole claim (`docs/plans/batch-1-settings-i18n-plan.md:814-820,1506-1511`), directly contradicting the accepted test requirement that out-of-range telemetry be rejected without failing the claim (`docs/specs/batch-1-settings-i18n.md:432-436`). The actual handler validates before any claim work (`packages/api/src/app.ts:2270-2275`), so the planned behavior can idle the entire runner because one observational field is bad. **Remedy:** parse the claim's operational fields strictly and telemetry fields independently, discard only invalid telemetry, then continue claiming; test both a 204/no-work and a successful claim with an invalid optional field.

5. **[Feasibility, Coherence] The in-process daemon registry will accumulate dead daemon rows and can report stale telemetry as current.** The plan never evicts entries and assumes the map will hold only one or two keys; it also retains old values when a later observation omits a field (`docs/plans/batch-1-settings-i18n-plan.md:765-771`). The actual default identity includes the process id (`packages/runner/src/config.ts:24-35`), so each restart normally creates another permanent row and corrupts `N of M`; with a stable configured id, an older daemon inherits the prior daemon's version/disk/root instead of showing the spec's missing-value state (`docs/specs/batch-1-settings-i18n.md:391-395`). **Remedy:** define an incarnation/retirement policy (for example, stable daemon identity plus boot id, or bounded stale-entry eviction), replace rather than merge omitted telemetry on a new incarnation, and test repeated restarts plus downgrade to a telemetry-less daemon.

6. **[Scope, Feasibility] WI-17 keeps the Foundation field in the create request and preserves a known divergent prompt.** The spec explicitly removes `foundationalPrompt` from the create form because per-agent divergence is a bug (`docs/specs/batch-1-settings-i18n.md:264-273`), but the plan keeps posting today's constant (`docs/plans/batch-1-settings-i18n-plan.md:1307-1313,1522-1526`). That constant is a one-sentence web default (`apps/web/src/pages/Agents.tsx:32-36`) and is not the authoritative foundation loaded by seed (`agents/foundational.md:4-30`; `packages/db/prisma/seed.ts:55-57,121-142`); the API merely spreads the supplied body into the new row (`packages/api/src/app.ts:780-785`). **Remedy:** make agent creation obtain the canonical foundation server-side from one authoritative source, omit the field from the web request, and test both request absence and equality of the created row to the canonical foundation.

7. **[Feasibility, Coherence] The Tools card cannot resolve Custom models using `INHERIT` or `AUTO`.** The picker deliberately permits all five preferences for Custom models (`docs/plans/batch-1-settings-i18n-plan.md:1153-1162`), but WI-16 computes the displayed runner as `runnerForModel(model) ?? runnerPreference` (`docs/plans/batch-1-settings-i18n-plan.md:1231-1233`). For an uncatalogued model this yields `INHERIT`/`AUTO`, while `ENFORCED_BY` is defined only for the three concrete runners (`docs/plans/batch-1-settings-i18n-plan.md:989-1000`); runtime actually resolves those preferences through the model heuristic (`packages/db/src/workflow.ts:22-30`). The honesty tags can therefore be wrong or unrenderable precisely on the escape-hatch path. **Remedy:** add a pure web resolver matching `runnerFor(preference, model)`, use its concrete result in the card, and test Custom + explicit, Custom + `INHERIT`, and Custom + `AUTO` cases including codex/pi-shaped ids.

8. **[Coherence] The chosen single `/runners` fetch has neither a provider mount nor an acceptance check.** WI-13 defines `useRunners()` as its own `usePoll` (`docs/plans/batch-1-settings-i18n-plan.md:1027-1032`); WI-14 correctly observes that a second consumer doubles the interval and then says to lift it into context (`docs/plans/batch-1-settings-i18n-plan.md:1117-1124`). It never specifies the provider API/mount that must enclose both the sidebar and routed Settings page, and its five tests do not count requests (`docs/plans/batch-1-settings-i18n-plan.md:1126-1136`). The current Shell owns the sidebar and wraps routed children (`apps/web/src/components/Shell.tsx:57-99`), so placement is load-bearing. **Remedy:** define `RunnersProvider`, mount it once at the Shell boundary, make both consumers read that context, and add a fake-timer/fetch-count test proving Settings does not start a second poll.

9. **[Feasibility, Coherence] Model-picker validation cannot disable the existing create/detail buttons through the proposed interface.** The shared picker exposes only `{model, runnerPreference, onChange}` while claiming validation remains inside it (`docs/plans/batch-1-settings-i18n-plan.md:1153-1178`). Both action buttons live in parent components and currently know only their own simple conditions (`apps/web/src/pages/Agents.tsx:45-53,389-414`), yet the plan requires both forms to block save on picker errors (`docs/plans/batch-1-settings-i18n-plan.md:1192-1203`). **Remedy:** make validation a shared pure function consumed by both parents, or expose validity/error through the picker contract; wire it into both button `disabled` expressions and test the actual Create and Save buttons, not only picker markup.

## should-fix

1. **[Coherence] The component-generation test proves one `data-slot` per file, not one per exported part.** The required transform applies to every exported part (`docs/plans/batch-1-settings-i18n-plan.md:415-435`), but verification only requires each file to render/export at least one part containing `data-slot` (`docs/plans/batch-1-settings-i18n-plan.md:461-470`). Multi-part files such as `card.tsx`, `dropdown-menu.tsx`, and `table.tsx` could remain partially v3 while the test passes. **Remedy:** enumerate exported component parts per file and assert each part's static/source form has its expected slot.

2. **[Feasibility, Coherence] The Settings page's “last successful poll” value has no defined data source or test.** WI-14 requires the timestamp (`docs/plans/batch-1-settings-i18n-plan.md:1110-1114`), but the current polling contract exposes only data/error/loading/missing/reload (`apps/web/src/lib/hooks.ts:9-16,19-64`), and the planned Settings tests omit timestamp behavior (`docs/plans/batch-1-settings-i18n-plan.md:1126-1136`). **Remedy:** add an explicit `lastSuccessAt` to the relevant shared health hook/state and test that a later failed poll preserves the last successful timestamp while changing health to unreachable.

3. **[Feasibility] Autosaving the entire denied-tool array can lose rapid changes.** WI-16 PATCHes `disabledTools` on every toggle and reloads afterward (`docs/plans/batch-1-settings-i18n-plan.md:1222-1230`), but all toggles derive from the same polled `agent.disabledTools`; two requests started before the first reload can each overwrite the other. The existing `useAction` only provides a pending bit and does not serialize or merge writes (`apps/web/src/lib/hooks.ts:66-89`). **Remedy:** keep an optimistic local denied set and serialize writes, or disable the entire card while a write is pending; add a rapid two-toggle test that persists the union of both changes.

4. **[Coherence] The daemon-version verification accepts any semver-shaped string rather than proving the reported package version.** WI-10 requires the real package version but tests only a non-empty semver regex (`docs/plans/batch-1-settings-i18n-plan.md:837-853`); the authoritative value is available at `packages/runner/package.json:1-4`. A hardcoded but plausible wrong version would pass. **Remedy:** assert exact equality with the package metadata and that both claim and heartbeat bodies carry that same value.
