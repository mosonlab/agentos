## Must-fix

1. **[Feasibility, focused pass / chain semantics; spec §4.8-B1, §5.2] The Backlog guard is not atomic with `Start now`, so it can strand a live queued run.** `PATCH /tasks/:id` counts active runs outside a transaction at `packages/api/src/app.ts:1706-1712`, then performs the status write much later at `packages/api/src/app.ts:1751-1770`. `POST /tasks/:id/start` correctly locks the Task row and inserts a run at `packages/api/src/app.ts:1841-1866`, but the PATCH never participates in that mutex. The runner only claims tasks in `TODO|DOING` at `packages/api/src/app.ts:2157-2163`, so the lost race does not “resolve on completion” as the comment claims: a `QUEUED` run attached to a `BACKLOG` task is never claimed and therefore never completes. A synchronized scratch-DB request produced `{"startStatus":201,"backlogPatchStatus":200,"finalTaskStatus":"BACKLOG","runs":["QUEUED"]}`. **Remedy:** move the Backlog transition into a transaction that locks the Task row before checking `ACTIVE_RUN_STATUSES`, using the same mutex as `start`/`retry`/archive; add the synchronized start-vs-Backlog regression and assert exactly one operation succeeds.

2. **[Feasibility, focused pass / chain semantics and blast radius; spec §4.9, §5.3] Rejecting a gate can requeue an archived predecessor, bypassing the advertised one-exclusion protocol.** Gate resolution loads `previousTask` at `packages/db/src/workflow.ts:420-425`, then the reject path unconditionally moves that predecessor to `TODO` and calls `enqueueTaskRun` at `packages/db/src/workflow.ts:484-506`. `enqueueTaskRun` checks the assignee's archive state but never the Task's `archivedAt` at `packages/db/src/workflow.ts:62-77`. The runner claim predicate likewise omits task archive state at `packages/api/src/app.ts:2157-2163`. A scratch-DB rejection returned `gateAction:"rejected"` while leaving `predecessorArchived:true`, changing it to `TODO`, and adding run 2 as `QUEUED`; the production claim predicate then selected that archived queued run. **Remedy:** make gate rejection join the Task-row mutex and refuse/park while the redo task is archived, leaving the Inbox decision open via transaction rollback; also add `task.archivedAt: null` to the runner claim as defense in depth and add a real DB regression.

3. **[Feasibility, focused pass / API correctness; spec §4.9-A1/A2, §5.2] `archive-done` can archive a task that is no longer `DONE`.** Candidate selection checks `status=DONE` at `packages/api/src/app.ts:1915-1918`, but the later locking query rechecks only id and `archivedAt IS NULL` at `packages/api/src/app.ts:480-485`; the survivors are archived without another status read at `packages/api/src/app.ts:1922-1938`. A synchronized scratch-DB run changed the selected task to `TODO` before the lock and still returned `{"archived":1,"skipped":0}`, with final state `TODO` plus `archivedAt != null`. That silently hides work the operator explicitly moved back to the board. **Remedy:** include project and `status='done'` in the ordered locking query (or re-read every locked row and repartition) before updating; add a status-change-vs-archive-all race test.

4. **[Scope and coherence / API correctness; spec §6-E2 and §5.2 trigger fires] Trigger fire history can link to and summarize another project's chain.** The fires route queries every task sharing a `chainId` without the trigger template's `projectId` at `packages/api/src/app.ts:1424-1430`, then keys `firstByChain` and owner lookup by `chainId` alone at `packages/api/src/app.ts:1431-1438`. This contradicts the module's own rule that chain identity is `(projectId, chainId)` at `packages/api/src/chain.ts:55-68`. With one fire owned by project A and a disjoint-index chain collision in project B, an authenticated scratch request returned project B's task as `firstTask` and project B's progress (`activeStepName:"FOREIGN PROJECT TASK"`). **Remedy:** load/verify the fire ledger's template project, constrain the task query by that project, and key every intermediate map by `chainKey`; add the same cross-project collision coverage already present for `GET /tasks`/`GET /tasks/:id/chain`.

5. **[Coherence and risk / partial rollback; spec §9] Code rollback silently re-enables paused triggers and removes replay protection, but the runbook calls rollback safe and only mitigates automations.** Pausing works solely because authentication rejects `webhookPausedAt` at `packages/api/src/hooks.ts:47-54`; replay suppression works solely through current-code ledger lookup at `packages/api/src/app.ts:575-586`. The rollback runbook says code-only rollback is safe at `docs/runbooks/batch-2.5-rollback.md:55-59` and gives pre-rollback parking instructions only for automations/AT tasks at `docs/runbooks/batch-2.5-rollback.md:61-69`. Rolling back the API therefore lets external traffic create chains from every paused trigger and lets redeliveries create duplicates. **Remedy:** make rollback conditional on quiescing webhook ingress; explicitly disable or detach credentials for every template with `webhookPausedAt IS NOT NULL`, preserve a restore list, and document the replay-window loss/drain period before old code starts.

6. **[Coherence and risk / destructive rollback; spec §5.1 and §9] “Undoing just the backfill” deletes live webhook ledger rows, not just backfilled rows.** The runbook executes `DELETE FROM "TriggerFire" WHERE source='webhook'` at `docs/runbooks/batch-2.5-rollback.md:89-94`. New webhook fires use that same source and table at `packages/api/src/templates.ts:117-123`; those rows are also the replay guard queried at `packages/api/src/app.ts:579-586`. Thus the command erases post-deploy history and can immediately permit duplicate chains inside an active replay window. **Remedy:** remove this command unless backfilled rows gain a durable provenance/deterministic identifier; otherwise state that selective rollback is impossible and leave the additive ledger intact.

## Should-fix

1. **[Feasibility, focused pass / migration-backfill; spec §5.1] The backfill is sequentially re-runnable but not concurrency-idempotent.** It performs an unlocked `findFirst` followed by `create` at `packages/db/src/task-source.ts:104-116`, with no unique/deterministic key for a historical fire in `packages/db/prisma/schema.prisma:524-534`. Two synchronized invocations against one historical activity produced `{"concurrentBackfills":2,"ledgerRowsForOneHistoricFire":2}`. This corrupts fire counts but does not start work, so it is survivable. **Remedy:** derive a deterministic row id/backfill key from `(templateId,firedAt)` and use `upsert`/`createMany(skipDuplicates)`, then test simultaneous invocations rather than only a completed second pass.

2. **[Feasibility and risk / migrations; spec §5.1] Both indexes on the existing `Task` table are built with ordinary blocking `CREATE INDEX`.** The migration uses non-concurrent index creation at `packages/db/prisma/migrations/20260816180100_tasks_visibility/migration.sql:44-48`, while the deploy runbook keeps the old API active through migrate/build/restart at `docs/runbooks/batch-2.5-rollback.md:7-27`. At current dogfood volume this likely finishes quickly, but ordinary index builds can stall Task inserts/updates and therefore chain completion or scheduler work during deploy. **Remedy:** either build the two Task indexes concurrently in an execution shape that permits it, or document/measure a maintenance window with bounded lock wait and an abort/retry procedure.

3. **[Coherence / chain API; spec §6-E1] Broken null-`chainIndex` rows have different progress on the board and detail API.** The detail route explicitly treats the subject as a singleton and excludes null-index siblings at `packages/api/src/app.ts:1655-1664`, but `GET /tasks` includes every same-`chainId` row in its progress query at `packages/api/src/app.ts:1532-1543`; `chainProgress` sorts null as zero at `packages/api/src/chain.ts:33-46`. A malformed row can therefore inflate and reorder every sibling's board marker while its own detail says `1/1`. **Remedy:** apply the singleton/exclusion rule consistently when assembling list progress and add an E1 assertion against `GET /tasks`, not only the detail route.
