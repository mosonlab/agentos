1. **[Filesystem ownership — the persistent lock inode is stored in a directory that the supported default runner principal can unlink.]** The plan makes `.agentos-control-plane.lock` a regular `0600` file inside `RUNNER_WORKSPACE_ROOT` and relies on its inode never being replaced (`docs/plans/control-plane-workspace-ownership-v1.md:87-110,491-492`). File mode does not protect a directory entry from a process that can write the parent directory. The repository explicitly says that, with the shipped empty `RUNNER_RUN_AS_PREFIX`, model CLIs run as the runner's OS user and can write anywhere in a run workspace (`.env.example:36-42,64-68`); runner cleanup is intentionally authorized beneath the same root (`packages/runner/src/workspace.ts:158-169`). If that principal, an operator cleanup, or a bug unlinks or replaces the lock while API A still holds the old inode, API B opens a new inode at the same pathname and also acquires `flock`. Both control planes can then reconcile and listen, directly violating the invariant. “Normal code never unlinks it” is not enforcement. **Remedy:** establish an API-only, non-runner-writable lock location or make OS-principal separation/parent-directory permissions a required and executable prerequisite; key that lock to the canonical root and keep root-local JSON as evidence if desired. In either design, define `assertHeld()` to compare the open descriptor's device/inode with the authoritative pathname and fail closed on replacement, add an unlink/rename/recreate adversarial real-process test, and document that manual deletion is never recovery.

2. **[Filesystem semantics — “local POSIX only” is an unenforced assumption, while the proposed dependency explicitly does not supply the required NFS guarantee.]** The plan narrows execution to local POSIX filesystems in prose (`docs/plans/control-plane-workspace-ownership-v1.md:73-82`) and later asks only that operators select an absolute local-looking path (`:403-408`). An absolute path can still be an NFS/SMB/FUSE mount. `fs-ext`'s own `flock` documentation warns that `flock()` does not lock files over NFS. On such a root, the copied-DB case can admit both processes even though every planned local-temp test passes. The Product Contract excludes remote/distributed control planes, but it does not authorize silently weakening the same-root invariant when a local process is pointed at a network mount. **Remedy:** either obtain a Product Contract revision that makes a verified local-filesystem precondition authoritative, then implement a fail-closed mount/filesystem preflight with unit and real-process refusal tests, or choose a primitive with the required semantics for every admitted filesystem. The runbook must name the exact supported filesystem evidence; pathname shape is not evidence.

3. **[Lock lifecycle — close-on-exec and inheritance are not normative or tested.]** The protocol says the lock belongs to the kernel-held open file description (`docs/plans/control-plane-workspace-ownership-v1.md:18-22`) but Step 1 tests only contention and later kills an owner that has no long-lived descendant (`:244-256,366-371`). A descriptor inherited across `exec` keeps the same flock alive after the recorded owner PID is dead. The successor then sees lock contention forever while the liveness evidence says `ESRCH`, so the promised dead-owner recovery cannot run. The focused host probe found today's Node `fs.open` descriptor has `FD_CLOEXEC`, but the plan neither requires that property nor detects a regression if the open/wrapper implementation changes. **Remedy:** require and verify `FD_CLOEXEC` on the lock descriptor (or an equivalently non-inheritable open), and add a process test in which the owner starts a long-lived child, the owner is `SIGKILL`ed, the child remains alive, and the successor still acquires and recovers. A test that kills a childless owner does not cover inheritance.

4. **[Canonicalization evidence — the tests do not wire a symlink/lexical alias through two production entrypoints.]** Step 1 separately proposes a unit canonicalization test and a child-process lock probe (`docs/plans/control-plane-workspace-ownership-v1.md:244-256`), while both Step 3 production processes receive the same shared root string (`:327-340`). That arrangement can pass if `canonicalizeWorkspaceRoot()` is correct but `index.ts` accidentally opens the lock under the original lexical path, or if one later call re-reads the environment. The acceptance claim is ownership of the canonical physical root, so the verification must detect mis-wiring, not only helper correctness. **Remedy:** make at least one real production-entrypoint conflict case use two distinct spellings of the same physical root (real path versus symlink, and preferably a lexical `..` alias), assert both emitted roots are the same canonical path, and retain the database/directory no-change sentinels. Also test a root symlink retarget or authoritative lock-path identity change as a fail-closed condition rather than allowing a stale capability to authorize GC.

5. **[Startup lifecycle — the plan does not define how asynchronous listen success/failure joins the ownership state machine.]** Current `index.ts` calls `serve()`, starts the scheduler immediately after the call returns, and only learns that the socket is listening in a callback (`packages/api/src/index.ts:34-44`). Its shutdown calls `server.close()` without awaiting the callback and then exits (`:46-51`). The plan says “create/listen” before starting the scheduler and promises one cleanup path for startup exceptions (`docs/plans/control-plane-workspace-ownership-v1.md:181-195,280-286`), but it does not require awaiting the server's `listening` event or handling its asynchronous `error` event. An `EADDRINUSE` can therefore bypass the intended startup-failure cleanup, or the scheduler can start before the claimed listening marker. Immediate `process.exit(75)`/`process.exit(0)` can also truncate markers captured through child-process pipes. **Remedy:** specify a Promise that resolves only on `listening` and rejects on pre-listen `error`; start the scheduler only after resolution; route rejection through the idempotent cleanup; await `server.close`/drain when a server exists; and emit/flush the terminal marker before setting `process.exitCode` and allowing handles to close. Add real-process tests for `EADDRINUSE`, signal during startup reconciliation, and marker/exit ordering.

## should-fix

1. **[Liveness evidence — `kill(pid, 0)` cannot distinguish the recorded owner from a reused PID.]** The plan correctly fails closed whenever the PID probe succeeds (`docs/plans/control-plane-workspace-ownership-v1.md:151-163`), so PID reuse does not permit takeover. However, the proposed “live/reused PID” test and runbook instruction to stop “on PID reuse” (`:248-252,414-416`) claim an observation the record cannot make: stable/incarnation UUIDs are not bound to an OS process birth identity, and `kill(pid, 0)` proves only that some process currently occupies the number. **Remedy:** either add a recorded and validated process-birth fingerprint supported on the target OS, or rename the state/evidence to `pid-present-owner-identity-ambiguous` and stop claiming PID reuse was detected. Keep `EPERM` and every successful probe fail closed.

2. **[Recovery records — the malformed/partial-state matrix is incomplete.]** The decision table clearly refuses malformed owner evidence, root mismatch, and identity mismatch (`docs/plans/control-plane-workspace-ownership-v1.md:151-163`), but the tests do not explicitly cover malformed/missing stable-ID evidence, an owner record with no stable-ID file, a released record whose root/ID mismatches, or a crash between stable-ID creation and owner-record rename (`:244-252`). Those are the realistic crash and operator-damage shapes created by the two-file protocol. **Remedy:** specify the full pairwise state matrix for the stable-ID and owner files; only the documented first-start and completed atomic-write states may advance, every mismatch remains byte-for-byte unchanged, and the post-stable-ID/pre-owner crash case must deterministically retain the stable ID.

3. **[Operator evidence — atomic rename can leave more than the documented three files after a crash.]** The plan describes exactly three root-local files (`docs/plans/control-plane-workspace-ownership-v1.md:87-103`) while requiring temp-file-plus-rename writes (`:98-100`). A process/power failure before rename can leave a same-directory temp file. GC safely ignores it because current reconciliation filters to directories (`packages/api/src/reconcile.ts:267-287,315-325`), but the runbook and rollback inventory become false and unbounded stale temp files can accumulate. **Remedy:** define a bounded temp naming convention, recovery-time handling while the lock is held, and tests for a leftover temp file; document it as possible crash debris or clean it safely without ever touching the persistent lock inode.
