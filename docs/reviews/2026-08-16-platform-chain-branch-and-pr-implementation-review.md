## must-fix

1. **[Feasibility + Scope + Correctness + Risk; spec §§2, 5.2, 5.3, 6/S1, 12] The real API creation path eagerly queues every `NOW` chain step, so a normally created chain snapshots the wrong base before step ① can publish the shared branch.** `POST /tasks` creates an inline run for every agent task with `scheduleKind = NOW`, with no chain-position guard (`packages/api/src/app.ts:1702-1732`). The new acceptance test explicitly evades that production behavior by posting only step ① and inserting steps ②+ directly with Prisma (`packages/api/src/chain-branch.dbtest.ts:121-134`, `:165-175`), despite S1 requiring the chain to be created through `POST /tasks` (`docs/specs/platform-chain-branch-and-pr.md:375-383`). A scratch-schema reproduction posted indices 0 and 1 through the route; both returned 201 and produced two `QUEUED` runs with the same shared head but `targetBranch = master`. When step ① later completes, successor activation sees step ②'s queued run and declines to recompute it (`packages/db/src/workflow.ts:377-384`). Even with one runner executing serially, step ② clones `master`, recreates the already-published shared name, and can be rejected non-fast-forward. **Remedy:** make API chain creation leave non-first steps without runs (or add an atomic chain-creation API that queues only the minimum index), and replace the Prisma shortcut with a ≥3-step all-HTTP test that asserts only step ① is initially queued and each successor's base is resolved after its predecessor publishes.

2. **[Feasibility + Risk; spec §§5.3, 5.4, 11] `pushedBranch` is not durable at the moment of publication, leaving a runner-loss window that recreates the same non-fast-forward wedge it was added to prevent.** The remote push completes inside `deliverWorkspace` (`packages/runner/src/delivery.ts:109-116`), but the runner then performs PR work, cleanup, and only afterwards sends the completion (`packages/runner/src/runner.ts:232-265`); the database writes `pushedBranch` only in that terminal request (`packages/api/src/app.ts:2794-2818`). If the runner dies after the push but before completion, lost-lease reconciliation calls the resolver with no publication evidence (`packages/api/src/reconcile.ts:129-176`), and the resolver falls back to the task/default base (`packages/db/src/workflow.ts:168-185`). A scratch reproduction of that indistinguishable database state produced run 1 `LOST` and run 2 `QUEUED`, both on the shared head but both based on `master`, with `pushedBranch = null`. The runbook's diagnosis that null means “nothing was published” is therefore false (`docs/runbooks/platform-chain-branch-and-pr-rollback.md:168-175`). **Remedy:** persist the repo-scoped publication fact through a fenced API call immediately after `git push` returns, before PR commands and cleanup, and add a test that loses the lease after that persistence point and proves the retry clones the shared branch. The runbook must also describe the unavoidable ambiguous-push case instead of equating null with remote absence.

3. **[Feasibility + Risk + Coherence; spec §§8, 9] The documented physical rollback cannot execute.** The runbook says to drop the four columns and then run `prisma migrate resolve --rolled-back 20260817020000_chain_branch_and_pr` (`docs/runbooks/platform-chain-branch-and-pr-rollback.md:77-98`). I applied all migrations to an isolated schema, dropped exactly those columns, and ran that command; Prisma exited 1 with `P3012: Migration ... cannot be rolled back because it is not in a failed state.` Thus the promised forward proof at lines 89-90 is unreachable. **Remedy:** document and verify a supported compensating/forward migration that drops the columns, or keep the successful migration recorded and provide an explicitly tested manual recovery/roll-forward procedure; do not prescribe `migrate resolve --rolled-back` for a successfully applied migration.

4. **[Coherence + Correctness + Risk; spec §§3, 5.1/R4, 6/S10] A `chainIndex = null` row that the platform defines as its own 1/1 chain can join and contaminate an indexed chain's git branch.** The frozen behavior test says such a row “never joins another” and isolates it from siblings sharing the same `chainId` (`packages/api/src/chain.dbtest.ts:438-455`). The implementation nevertheless derives only from `(projectId, chainId)` (`packages/db/src/chain-branch.ts:29-37`) and explicitly lets null-index rows share publication evidence with indexed rows (`packages/db/src/workflow.ts:164-174`). A scratch reproduction created an indexed chain, recorded its shared publication, then started a null-index row with the same project/chain id; the row received both `branch` and `targetBranch` equal to the indexed chain's shared branch. That silently mixes work the API/UI calls unrelated. **Remedy:** either reject/quarantine executable null-index chain rows, or give them an identity/branch key that cannot collide with indexed chains and scope evidence the same way; add a regression test using the exact E1 collision, not a fresh unique `chainId` as T8 currently does (`packages/api/src/chain-branch.dbtest.ts:347-355`).

5. **[Scope + Coherence; spec §7.2] The accepted template-step create-route requirement is still missing.** The spec requires template-step create and patch routes to accept `opensPullRequest` (`docs/specs/platform-chain-branch-and-pr.md:480-489`). The implementation adds only `PATCH /task-templates/:templateId/steps/:stepId` (`packages/api/src/app.ts:1292-1308`), and the revised plan explicitly says the create half was not built and was left for a human decision (`docs/plans/platform-chain-branch-and-pr-plan.md:1526-1535`). No decision amended the accepted spec before implementation. **Remedy:** implement a bounded, validated create surface that includes the required step fields and the new boolean, with ownership/API tests, or obtain and commit an explicit spec revision that removes this requirement before acceptance.

6. **[Feasibility + Quality; spec §12.2] The mandatory database gate is red on the reviewed tree.** On a workspace-private schema, one unretried `npm run test:db` run completed with 123 pass / 1 fail: `concurrent webhook fires retry serialization conflicts and create independent chains` returned one 503 where the test requires six 201 responses (`packages/api/src/hooks.dbtest.ts:94-101`). `npm run build`, `npm test` (132 + 185 + 5 + 31 passing; one pre-existing skip), `npm run typecheck`, and `npm run db:drift-check` passed, but §12.2 explicitly requires every listed gate green (`docs/specs/platform-chain-branch-and-pr.md:699-710`). Calling the failure pre-existing does not turn a red acceptance gate into evidence that the final artifact passes. **Remedy:** make the serialization retry/test deterministic enough to pass the required full suite once without rerun, or formally revise the acceptance gate with a separately enforceable quarantine; then rerun the complete gate set.

7. **[Risk + Coherence; spec §§8.2, 9] The mixed-chain recovery instruction stops working after the first shared-branch publication.** The runbook tells the operator to set each remaining task's `targetBranch` to its real predecessor (`docs/runbooks/platform-chain-branch-and-pr-rollback.md:100-110`). But once any post-restart run records the shared branch, the resolver always selects that shared branch and ignores every later task override (`packages/db/src/workflow.ts:168-190`). If the first post-restart step was based on the wrong old branch, following the runbook for the next step does not reintroduce the missing work. **Remedy:** split recovery into pre-publication and post-publication procedures: before publication, repoint the first new shared run; after publication, explicitly merge/cherry-pick the missing predecessor work into the shared branch (or provide a controlled evidence/override mechanism). Add both cases to the detection/recovery proof.

## should-fix

1. **[Risk + Coherence] A chain based on a non-default branch still opens its PR against the repository default.** `deliverWorkspace` hardcodes `--base claim.repo.defaultBranch` (`packages/runner/src/delivery.ts:147-153`), while the plan itself records that an operator-selected chain base will therefore produce a PR against a different target and leaves the question unresolved (`docs/plans/platform-chain-branch-and-pr-plan.md:1490-1498`). Default-based chains survive, but a custom-base chain can show an unrelated or misleading diff. **Remedy:** define the PR-base contract, persist/transport the chain's initial base independently of later runs' shared `targetBranch`, and test the `gh pr create` arguments for a custom-base chain; alternatively reject non-default chain bases explicitly.

2. **[Coherence] The implementation follows justified revised-plan deviations, but the authoritative spec was never updated and now directs a future maintainer toward regressions.** The spec says two columns and no branch-name column (`docs/specs/platform-chain-branch-and-pr.md:455-478`) and tells the runner to read `claim.task.opensPullRequest` (`:495-503`); the shipped schema has four columns including `Run.pushedBranch` (`packages/db/prisma/schema.prisma:653-665`) and the runner correctly reads the run snapshot (`packages/runner/src/delivery.ts:99-108`). **Remedy:** revise the spec to capture the accepted history-signal column, five run creators, repo-scoped evidence, and run-level PR snapshot, while retaining the unresolved requirements called out above.

3. **[Feasibility + Quality] Step 5's commit inventory does not describe the reviewed branch range.** Fetching the declared ref produced the declared head and merge-base, but `git rev-list --count 084704c..450e7de` returned 14, not the 11 entries in “Commits, oldest first”; the omitted ancestors are the spec, initial plan, and revised plan. The full range is 21 files / 3,820 insertions / 23 deletions, while the 11-commit implementation-only range `66d2d29..450e7de` is 19 files / 1,436 insertions / 23 deletions. **Remedy:** report both the full branch range and the explicitly named implementation subrange so later reviewers can reproduce the claimed count and diffstat without guessing.
